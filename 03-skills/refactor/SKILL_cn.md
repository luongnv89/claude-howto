# 代码重构技能

基于 Martin Fowler 的《*重构：改善既有代码的设计*》（第2版）的系统性代码重构方法。本技能强调由测试支撑的安全、增量变更。

> "重构是在不改变代码外部行为的前提下，改善其内部结构的过程。" — Martin Fowler

## 核心原则

1. **行为保留**：外部行为必须保持不变
2. **小步推进**：做微小的、可测试的变更
3. **测试驱动**：测试是安全网
4. **持续进行**：重构是持续的过程，而非一次性事件
5. **协作完成**：每个阶段都需要用户批准

## 工作流概述

```
第1阶段：研究与分析
    ↓
第2阶段：测试覆盖率评估
    ↓
第3阶段：代码异味识别
    ↓
第4阶段：重构计划创建
    ↓
第5阶段：增量实施
    ↓
第6阶段：审查与迭代
```

---

## 第1阶段：研究与分析

### 目标
- 了解代码库结构和目的
- 确定重构范围
- 收集业务需求背景

### 向用户提问
在开始之前，需要澄清：

1. **范围**：哪些文件/模块/函数需要重构？
2. **目标**：您想解决什么问题？（可读性、性能、可维护性）
3. **约束**：有哪些区域不应该更改？
4. **时间压力**：这是否阻塞了其他工作？
5. **测试状态**：测试是否存在？是否通过？

### 行动
- [ ] 阅读并理解目标代码
- [ ] 识别依赖项和集成
- [ ] 记录当前架构
- [ ] 注意现有的技术债务标记（TODOs、FIXMEs）

### 输出
向用户展示发现：
- 代码结构摘要
- 已识别的问题区域
- 初步建议
- **请求批准以继续**

## 第2阶段：测试覆盖率评估

### 为什么测试很重要
> "没有测试的重构就像不系安全带开车。" — Martin Fowler

测试是安全重构的**关键支撑**。没有测试，就有引入 bug 的风险。

### 评估步骤

1. **检查现有测试**
   ```bash
   # 查找测试文件
   find . -name "*test*" -o -name "*spec*" | head -20
   ```

2. **运行现有测试**
   ```bash
   # JavaScript/TypeScript
   npm test

   # Python
   pytest -v

   # Java
   mvn test
   ```

3. **检查覆盖率（如果可用）**
   ```bash
   # JavaScript
   npm run test:coverage

   # Python
   pytest --cov=.
   ```

### 决策点：询问用户

**如果测试存在且通过：**
- 继续第3阶段

**如果测试缺失或不完整：**
提供选项：
1. 先编写测试（推荐）
2. 在重构过程中逐步添加测试
3. 无测试继续（有风险——需要用户确认）

**如果测试失败：**
- 停止。在重构之前修复失败的测试
- 询问用户：我们是否应该先修复测试？

### 测试编写指南（如果需要）

对于每个被重构的函数，确保测试覆盖：
- 正常路径（正常操作）
- 边界情况（空输入、null、边界值）
- 错误场景（无效输入、异常）

使用"红-绿-重构"循环：
1. 编写失败的测试（红）
2. 使其通过（绿）
3. 重构

## 第3阶段：代码异味识别

### 什么是代码异味？
代码中更深层问题的症状。它们不是 bug，但表明代码可以改进。

### 要检查的常见代码异味

完整目录请参见 [references/code-smells.md](references/code-smells.md)。

#### 快速参考

| 异味 | 迹象 | 影响 |
|------|------|------|
| **长方法** | 方法 > 30-50 行 | 难以理解、测试、维护 |
| **重复代码** | 多处相同逻辑 | bug 修复需要在多处进行 |
| **大类** | 职责过多的类 | 违反单一职责原则 |
| **特性依恋** | 方法更多使用另一个类的数据 | 封装性差 |
| **基本类型偏执** | 过度使用基本类型而非对象 | 缺失领域概念 |
| **过长参数列表** | 方法有 4+ 个参数 | 难以正确调用 |
| **数据泥团** | 相同数据项总是一起出现 | 缺失抽象 |
| **switch 语句** | 复杂的 switch/if-else 链 | 难以扩展 |
| **过度设计** | "以防万一"的代码 | 不必要的复杂性 |
| **死代码** | 未使用的代码 | 造成混乱，增加维护负担 |

### 分析步骤

1. **自动化分析**（如果有脚本）
   ```bash
   python scripts/detect-smells.py <file>
   ```

2. **手动审查**
   - 系统地检查代码
   - 记录每个异味的位置和严重性
   - 按影响程度分类（严重/高/中/低）

3. **优先级排序**
   重点关注以下异味：
   - 阻碍当前开发
   - 导致 bug 或混乱
   - 影响最常变更的代码路径

### 输出：异味报告

向用户展示：
- 已识别的异味列表及位置
- 每个异味的严重性评估
- 建议的优先顺序
- **请求批准优先级**

## 第4阶段：重构计划创建

### 选择重构方法

对于每种异味，从目录中选择适当的重构方法。

完整列表请参见 [references/refactoring-catalog.md](references/refactoring-catalog.md)。

#### 异味到重构的映射

| 代码异味 | 推荐重构方法 |
|----------|-------------|
| 长方法 | 提取方法、以查询替代临时变量 |
| 重复代码 | 提取方法、上移方法、形成模板方法 |
| 大类 | 提取类、提取子类 |
| 特性依恋 | 移动方法、移动字段 |
| 基本类型偏执 | 以对象替代基本类型、以类替代类型码 |
| 过长参数列表 | 引入参数对象、保持完整对象 |
| 数据泥团 | 提取类、引入参数对象 |
| switch 语句 | 以多态替代条件表达式 |
| 过度设计 | 折叠继承体系、内联类、移除死代码 |
| 死代码 | 移除死代码 |

### 计划结构

使用 [templates/refactoring-plan.md](templates/refactoring-plan.md) 中的模板。

对于每次重构：
1. **目标**：哪些代码将变更
2. **异味**：解决什么问题
3. **重构**：应用哪种技术
4. **步骤**：详细的微步骤
5. **风险**：可能出什么问题
6. **回滚**：如何撤销（如果需要）

### 分阶段方法

**关键**：逐步分阶段引入重构。

**A 阶段：快速见效**（低风险，高价值）
- 重命名变量以提高清晰度
- 提取明显的重复代码
- 删除死代码

**B 阶段：结构改进**（中等风险）
- 从长函数中提取方法
- 引入参数对象
- 将方法移至适当的类

**C 阶段：架构变更**（较高风险）
- 以多态替代条件表达式
- 提取类
- 引入设计模式

### 决策点：向用户展示计划

在实施之前：
- 展示完整的重构计划
- 解释每个阶段及其风险
- 获得每个阶段的明确批准
- **询问**："我应该继续 A 阶段吗？"

---

## 第5阶段：增量实施

### 黄金法则
> "变更 → 测试 → 通过？→ 提交 → 下一步"

### 实施节奏

对于每个重构步骤：

1. **预检查**
   - 测试通过（绿）
   - 代码编译

2. **做一个小变更**
   - 遵循目录中的机制
   - 保持变更最小化

3. **验证**
   - 立即运行测试
   - 检查编译错误

4. **如果测试通过（绿）**
   - 使用描述性消息提交
   - 进入下一步

5. **如果测试失败（红）**
   - 立即停止
   - 撤销变更
   - 分析出了什么问题
   - 如果不清楚，询问用户

### 提交策略

每次提交应该是：
- **原子性**：一个逻辑变更
- **可回滚**：易于回退
- **描述性**：清晰的提交消息

示例提交消息：
```
refactor: 从 processOrder() 中提取 calculateTotal()
refactor: 将 'x' 重命名为 'customerCount' 以提高清晰度
refactor: 移除未使用的 validateOldFormat() 方法
```

### 进度报告

每个子阶段后，向用户报告：
- 已做的变更
- 测试是否仍然通过？
- 遇到的任何问题
- **询问**："继续下一批吗？"

---

## 第6阶段：审查与迭代

### 重构后检查清单

- [ ] 所有测试通过
- [ ] 无新警告/错误
- [ ] 代码编译成功
- [ ] 行为未变（手动验证）
- [ ] 如有需要，文档已更新
- [ ] 提交历史整洁

### 指标对比

重构前后运行复杂度分析：
```bash
python scripts/analyze-complexity.py <file>
```

展示改进：
- 代码行数变化
- 圈复杂度变化
- 可维护性指数变化

### 用户审查

展示最终结果：
- 所有变更摘要
- 代码前后对比
- 指标改进
- 剩余技术债务
- **询问**："您对这些变更满意吗？"

### 下一步

与用户讨论：
- 是否还有其他异味要处理？
- 安排后续重构？
- 在其他地方应用类似变更？

## 重要指南

### 何时停止并询问

遇到以下情况时，始终暂停并咨询用户：
- 对业务逻辑不确定
- 变更可能影响外部 API
- 测试覆盖率不足
- 需要做重大架构决策
- 风险等级提高
- 遇到意外的复杂性

### 安全规则

1. **永远不要在没有测试的情况下重构**（除非用户明确确认风险）
2. **永远不要做大变更** - 分解成微小步骤
3. **永远不要跳过测试运行** - 每次变更后都要运行
4. **如果测试失败，永远不要继续** - 先修复或回滚
5. **永远不要假设** - 有疑问就问

### 不该做的事

- 不要将重构与功能添加结合
- 不要在生产紧急情况下重构
- 不要重构您不理解的代码
- 不要过度设计 - 保持简单
- 不要一次性重构所有内容

## 快速入门示例

### 场景：带有重复的长方法

**重构前：**
```javascript
function processOrder(order) {
  // 150 行代码，包含：
  // - 重复的验证逻辑
  // - 内联计算
  // - 混合职责
}
```

**重构步骤：**

1. **确保测试存在** 用于 processOrder()
2. **提取**验证为 validateOrder()
3. **测试** - 应该通过
4. **提取**计算为 calculateOrderTotal()
5. **测试** - 应该通过
6. **提取**通知为 notifyCustomer()
7. **测试** - 应该通过
8. **审查** - processOrder() 现在协调 3 个清晰的函数

**重构后：**
```javascript
function processOrder(order) {
  validateOrder(order);
  const total = calculateOrderTotal(order);
  notifyCustomer(order, total);
  return { order, total };
}
```
