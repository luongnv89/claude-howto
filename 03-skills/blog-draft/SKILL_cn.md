## 用户输入

```text
$ARGUMENTS
```

在继续之前，您**必须**考虑用户输入。用户应提供：
- **想法/主题**：博客文章的主要概念或主题
- **资源**：研究用的 URL、文件或参考资料（可选但推荐）
- **目标读者**：博客文章面向的对象（可选）
- **语气/风格**：正式、休闲、技术性等（可选）

**重要**：如果用户请求更新**现有博客文章**，跳过步骤 0-8，直接从**步骤 9** 开始。先读取现有草稿文件，然后进行迭代。

## 执行流程

按顺序执行以下步骤。**在指定位置等待用户批准，不要跳过步骤。**

### 步骤 0：创建项目文件夹

1. 使用以下格式生成文件夹名：`YYYY-MM-DD-short-topic-name`
   - 使用今天的日期
   - 从主题创建简短、URL 友好的 slug（小写、连字符、最多 5 个词）

2. 创建文件夹结构：
   ```
   blog-posts/
   └── YYYY-MM-DD-short-topic-name/
       └── resources/
   ```

3. 在继续之前向用户确认文件夹创建。

### 步骤 1：研究与资源收集

1. 在博客文章目录中创建 `resources/` 子文件夹

2. 对于每个提供的资源：
   - **URL**：获取并将关键信息保存为 `resources/` 中的 markdown 文件
   - **文件**：读取并在 `resources/` 中摘要
   - **主题**：使用网络搜索收集最新信息

3. 为每个资源在 `resources/` 中创建摘要文件：
   - `resources/source-1-[short-name].md`
   - `resources/source-2-[short-name].md`
   - 等等

4. 每个摘要应包含：
   ```markdown
   # 来源：[标题/URL]

   ## 要点
   - 要点 1
   - 要点 2

   ## 相关引文/数据
   - 引文或统计 1
   - 引文或统计 2

   ## 与主题的关联
   相关性的简要说明
   ```

5. 向用户呈现研究摘要。

### 步骤 2：头脑风暴与澄清

1. 基于想法和研究资源，呈现：
   - 从研究中识别的**主要主题**
   - 博客文章的**潜在角度**
   - 应涵盖的**关键要点**
   - 需要澄清的**信息缺口**

2. 提出澄清问题：
   - 您希望读者获得的主要收获是什么？
   - 是否有研究中您想强调的特定要点？
   - 目标长度是多少？（短：500-800 词，中：1000-1500 词，长：2000+ 词）
   - 有没有您想排除的要点？

3. **等待用户回答后再继续。**

### 步骤 3：提议大纲

1. 创建包含以下内容的结构化大纲：

   ```markdown
   # 博客文章大纲：[标题]

   ## 元信息
   - **目标读者**：[谁]
   - **语气**：[风格]
   - **目标长度**：[字数]
   - **主要收获**：[核心信息]

   ## 建议结构

   ### 引言/开头
   - 开篇钩子想法
   - 背景设置
   - 论点陈述

   ### 第 1 节：[标题]
   - 关键要点 A
   - 关键要点 B
   - 来自 [来源] 的支持证据

   ### 第 2 节：[标题]
   - 关键要点 A
   - 关键要点 B

   [继续所有章节...]

   ### 结论
   - 要点总结
   - 行动号召或最终想法

   ## 引用来源
   - 来源 1
   - 来源 2
   ```

2. 向用户呈现大纲，**请求批准或修改**。

### 步骤 4：保存已批准的大纲

1. 用户批准大纲后，将其保存到博客文章文件夹中的 `OUTLINE.md`。

2. 确认大纲已保存。

### 步骤 5：提交大纲（如果在 git 仓库中）

1. 检查当前目录是否为 git 仓库。

2. 如果是：
   - 暂存新文件：博客文章文件夹、资源和 OUTLINE.md
   - 创建提交消息：`docs: Add outline for blog post - [topic-name]`
   - 推送到远程

3. 如果不是 git 仓库，跳过此步骤并告知用户。

### 步骤 6：撰写草稿

1. 基于已批准的大纲，撰写完整的博客文章草稿。

2. 严格按照 OUTLINE.md 的结构。

3. 包含：
   - 带钩子的引人入胜的引言
   - 清晰的章节标题
   - 来自研究的支持证据和示例
   - 章节间的流畅过渡
   - 带收获的有力结论
   - **引文**：所有比较、统计数据、数据点和事实声明必须引用原始来源

4. 将草稿保存为博客文章文件夹中的 `draft-v0.1.md`。

5. 格式：
   ```markdown
   # [博客文章标题]

   *[可选：副标题或标语]*

   [带内联引文的完整内容...]

   ---

   ## 参考文献
   - [1] 来源 1 标题 - URL 或引文
   - [2] 来源 2 标题 - URL 或引文
   - [3] 来源 3 标题 - URL 或引文
   ```

6. **引文要求**：
   - 每个数据点、统计数据或比较必须有内联引文
   - 使用编号引用 [1]、[2] 等，或命名引用 [来源名称]
   - 将引文链接到末尾的参考文献部分
   - 示例："研究表明 65% 的开发者偏好 TypeScript [1]"

### 步骤 7：提交草稿（如果在 git 仓库中）

1. 检查是否在 git 仓库中。

2. 如果是：
   - 暂存草稿文件
   - 创建提交消息：`docs: Add draft v0.1 for blog post - [topic-name]`
   - 推送到远程

3. 如果不是 git 仓库，跳过并告知用户。

### 步骤 8：呈现草稿供审阅

1. 向用户呈现草稿内容。

2. 请求反馈：
   - 整体印象如何？
   - 需要扩展或缩减的章节？
   - 语气调整需要吗？
   - 缺少哪些信息？
   - 特定编辑或重写？

3. **等待用户回应。**

### 步骤 9：迭代或完成

**如果用户请求更改：**
1. 记录所有请求的修改
2. 带以下调整返回步骤 6：
   - 增加版本号（v0.2、v0.3 等）
   - 整合所有反馈
   - 保存为 `draft-v[X.Y].md`
   - 重复步骤 7-8

**如果用户批准：**
1. 确认最终草稿版本
2. 如果用户请求，可选择重命名为 `final.md`
3. 总结博客文章创作过程：
   - 创建的总版本数
   - 版本之间的关键变更
   - 最终字数
   - 创建的文件

## 版本追踪

所有草稿以递增版本保留：
- `draft-v0.1.md` - 初始草稿
- `draft-v0.2.md` - 第一轮反馈后
- `draft-v0.3.md` - 第二轮反馈后
- 等等

这允许追踪博客文章的演变，并在需要时回退。

## 输出文件结构

```
blog-posts/
└── YYYY-MM-DD-topic-name/
    ├── resources/
    │   ├── source-1-name.md
    │   ├── source-2-name.md
    │   └── ...
    ├── OUTLINE.md
    ├── draft-v0.1.md
    ├── draft-v0.2.md（如有迭代）
    └── draft-v0.3.md（如有更多迭代）
```

## 质量提示

- **钩子**：以问题、令人惊讶的事实或相关场景开头
- **流畅**：每段应与下一段相连
- **证据**：用研究数据支持主张
- **引文**：始终引用以下内容的来源：
  - 所有统计数据和数据点（例如"根据 [来源]，75% 的..."）
  - 产品、服务或方法之间的比较
  - 关于市场趋势、研究发现或基准测试的事实声明
- **声音**：始终保持一致的语气
- **长度**：尊重目标字数
- **可读性**：使用短段落，适当使用要点列表
- **行动号召**：以明确的行动号召或发人深省的问题结尾

## 注意事项

- 在指定的检查点始终等待用户批准
- 保留所有草稿版本以备历史参考
- 提供 URL 时使用网络搜索获取最新信息
- 如果资源不足，向用户请求更多资源或建议额外研究
- 根据目标读者调整语气（技术性、通用、商业等）
