## 用户输入

```text
$ARGUMENTS
```

在继续之前，您**必须**考虑用户输入（如果不为空）。用户可以指定：
- `create` - 从头创建新的 CLAUDE.md
- `update` - 改进现有的 CLAUDE.md
- `audit` - 分析并报告当前 CLAUDE.md 的质量
- 要创建/更新的特定路径（例如，`src/api/CLAUDE.md` 用于目录特定指令）

## 核心原则

**LLM 是无状态的**：CLAUDE.md 是每次对话中自动包含的唯一文件。它是 AI 代理进入代码库的主要入门文档。

### 黄金法则

1. **少即是多**：前沿 LLM 可以遵循约 150-200 条指令。Claude Code 的系统提示已使用约 50 条。保持 CLAUDE.md 专注简洁。

2. **普遍适用性**：只包含与每次会话相关的信息。特定任务的指令应放在单独的文件中。

3. **不要将 Claude 用作代码检查工具**：风格指南会膨胀上下文并降低指令遵循能力。改用确定性工具（prettier、eslint 等）。

4. **永远不要自动生成**：CLAUDE.md 是 AI 工具最高杠杆点。需要仔细考量，手动编写。

## 执行流程

### 1. 项目分析

首先分析当前项目状态：

1. 检查现有的 CLAUDE.md 文件：
   - 根目录：`./CLAUDE.md` 或 `.claude/CLAUDE.md`
   - 目录特定：`**/CLAUDE.md`
   - 全局用户配置：`~/.claude/CLAUDE.md`

2. 识别项目结构：
   - 技术栈（语言、框架）
   - 项目类型（monorepo、单一应用、库）
   - 开发工具（包管理器、构建系统、测试运行器）

3. 审查现有文档：
   - README.md
   - CONTRIBUTING.md
   - package.json、pyproject.toml、Cargo.toml 等

### 2. 内容策略（WHAT、WHY、HOW）

围绕三个维度构建 CLAUDE.md：

#### WHAT - 技术与结构
- 技术栈概述
- 项目组织（对 monorepo 尤为重要）
- 关键目录及其用途

#### WHY - 目的与背景
- 项目的功能
- 某些架构决策的原因
- 每个主要组件的职责

#### HOW - 工作流与约定
- 开发工作流（bun vs node、pip vs uv 等）
- 测试程序和命令
- 验证和构建方法
- 关键"陷阱"或非显而易见的要求

### 3. 渐进式披露策略

对于较大的项目，建议创建 `agent_docs/` 文件夹：

```
agent_docs/
  |- building_the_project.md
  |- running_tests.md
  |- code_conventions.md
  |- architecture_decisions.md
```

在 CLAUDE.md 中，使用如下指令引用这些文件：
```markdown
有关详细的构建说明，请参考 `agent_docs/building_the_project.md`
```

**重要**：使用 `文件:行` 引用而不是代码片段，以避免过时的上下文。

### 4. 质量约束

创建或更新 CLAUDE.md 时：

1. **目标长度**：300 行以内（理想情况下 100 行以内）
2. **无风格规则**：删除任何 linting/格式化指令
3. **无任务特定指令**：移至单独的文件
4. **无代码片段**：改用文件引用
5. **无冗余信息**：不要重复 package.json 或 README 中已有的内容

### 5. 必要章节

结构良好的 CLAUDE.md 应包含：

```markdown
# 项目名称

简短的一行描述。

## 技术栈
- 主要语言和版本
- 关键框架/库
- 数据库/存储（如有）

## 项目结构
[仅适用于 monorepo 或复杂结构]
- `apps/` - 应用程序入口点
- `packages/` - 共享库

## 开发命令
- 安装：`命令`
- 测试：`命令`
- 构建：`命令`

## 关键约定
[仅包含非显而易见的、高影响的约定]
- 约定 1 及简短说明
- 约定 2 及简短说明

## 已知问题 / 注意事项
[持续困扰开发者的问题]
- 问题 1
- 问题 2
```

### 6. 要避免的反模式

**不要包含：**
- 代码风格指南（使用 linter）
- 关于如何使用 Claude 的文档
- 对显而易见模式的长篇解释
- 复制粘贴的代码示例
- 通用最佳实践（"编写干净的代码"）
- 特定任务的指令
- 自动生成的内容
- 大量 TODO 列表

### 7. 验证清单

最终确定前，验证：

- [ ] 300 行以内（最好 100 行以内）
- [ ] 每一行都适用于所有会话
- [ ] 无风格/格式化规则
- [ ] 无代码片段（使用文件引用）
- [ ] 命令已验证可运行
- [ ] 复杂项目使用渐进式披露
- [ ] 关键注意事项已记录
- [ ] 与 README.md 无重复

## 输出格式

### 对于 `create` 或默认：

1. 分析项目
2. 按照上述结构起草 CLAUDE.md
3. 提交草稿供审查
4. 获得批准后写入相应位置

### 对于 `update`：

1. 读取现有的 CLAUDE.md
2. 根据最佳实践进行审查
3. 识别：
   - 要删除的内容（风格规则、代码片段、任务特定内容）
   - 要精简的内容
   - 缺失的必要信息
4. 提交变更供审查
5. 获得批准后应用变更

### 对于 `audit`：

1. 读取现有的 CLAUDE.md
2. 生成报告，包含：
   - 当前行数与目标行数对比
   - 普遍适用内容的百分比
   - 发现的反模式列表
   - 改进建议
3. 不修改文件，仅报告

## AGENTS.md 处理

如果用户请求创建/更新 AGENTS.md：

AGENTS.md 用于定义专用代理行为。与 CLAUDE.md（用于项目上下文）不同，AGENTS.md 定义：
- 自定义代理角色和能力
- 代理特定指令和约束
- 多代理场景的工作流定义

应用类似原则：
- 保持专注简洁
- 使用渐进式披露
- 引用外部文档而非嵌入内容

## 注意事项

- 在包含命令之前，始终验证命令是否有效
- 如有疑问，删除它——少即是多
- 系统提示告诉 Claude，CLAUDE.md "可能相关也可能不相关"——噪音越多，越容易被忽视
- Monorepo 最受益于清晰的 WHAT/WHY/HOW 结构
- 目录特定的 CLAUDE.md 文件应该更加专注
