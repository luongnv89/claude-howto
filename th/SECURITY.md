# นโยบายความปลอดภัย

## ภาพรวม

ความปลอดภัยของโปรเจกต์ Claude How To เป็นสิ่งสำคัญสำหรับเรา เอกสารนี้อธิบายแนวปฏิบัติด้านความปลอดภัยของเราและอธิบายวิธีการรายงานช่องโหว่ด้านความปลอดภัยอย่างรับผิดชอบ

## เวอร์ชันที่รองรับ

เราให้การอัปเดตด้านความปลอดภัยสำหรับเวอร์ชันต่อไปนี้:

| เวอร์ชัน | สถานะ | รองรับจนถึง |
|---------|--------|---------------|
| Latest (main) | ✅ Active | Current + 6 เดือน |
| 1.x releases | ✅ Active | จนถึงเวอร์ชัน major ถัดไป |

**หมายเหตุ**: ในฐานะโปรเจกต์คู่มือเชิงการศึกษา เราเน้นการรักษาแนวปฏิบัติที่ดีปัจจุบันและความปลอดภัยของเอกสารมากกว่าการรองรับเวอร์ชันแบบดั้งเดิม การอัปเดตถูกนำไปใช้กับ branch main โดยตรง

## แนวปฏิบัติด้านความปลอดภัย

### ความปลอดภัยของโค้ด

1. **การจัดการ dependencies**
   - dependencies ของ Python ทั้งหมด pin ไว้ใน `requirements.txt`
   - อัปเดตสม่ำเสมอผ่าน dependabot และการตรวจสอบด้วยตนเอง
   - สแกนความปลอดภัยด้วย Bandit ในทุก commit
   - pre-commit hooks สำหรับการตรวจสอบความปลอดภัย

2. **คุณภาพโค้ด**
   - การ lint ด้วย Ruff ตรวจจับปัญหาทั่วไป
   - การตรวจสอบประเภทด้วย mypy ป้องกันช่องโหว่ที่เกี่ยวกับประเภท
   - pre-commit hooks บังคับใช้มาตรฐาน
   - ตรวจสอบการเปลี่ยนแปลงทั้งหมดก่อน merge

3. **การควบคุมการเข้าถึง**
   - Branch protection บน branch `main`
   - ต้องมีการตรวจสอบก่อน merge
   - Status checks ต้องผ่านก่อน merge
   - จำกัดสิทธิ์การเขียนใน repository

### ความปลอดภัยของเอกสาร

1. **ไม่มี secrets ในตัวอย่าง**
   - API keys ทั้งหมดในตัวอย่างเป็น placeholder
   - ไม่มี credentials ที่ hardcoded
   - ไฟล์ `.env.example` แสดงตัวแปรที่จำเป็น
   - คำเตือนชัดเจนเกี่ยวกับการจัดการ secrets

2. **แนวปฏิบัติที่ดีด้านความปลอดภัย**
   - ตัวอย่างสาธิตรูปแบบที่ปลอดภัย
   - คำเตือนความปลอดภัยเน้นไว้ในเอกสาร
   - ลิงก์ไปยังคู่มือความปลอดภัยอย่างเป็นทางการ
   - การจัดการ credential อธิบายไว้ในส่วนที่เกี่ยวข้อง

3. **การตรวจสอบเนื้อหา**
   - เอกสารทั้งหมดได้รับการตรวจสอบสำหรับปัญหาความปลอดภัย
   - ข้อพิจารณาด้านความปลอดภัยในแนวทางการมีส่วนร่วม
   - การตรวจสอบลิงก์และการอ้างอิงภายนอก

### ความปลอดภัยของ dependencies

1. **การสแกน**
   - Bandit สแกนโค้ด Python ทั้งหมดสำหรับช่องโหว่
   - ตรวจสอบช่องโหว่ของ dependency ผ่าน GitHub security alerts
   - การตรวจสอบความปลอดภัยด้วยตนเองสม่ำเสมอ

2. **การอัปเดต**
   - แพทช์ความปลอดภัยถูกนำไปใช้ทันที
   - ประเมิน major versions อย่างรอบคอบ
   - Changelog รวมการอัปเดตที่เกี่ยวข้องกับความปลอดภัย

3. **ความโปร่งใส**
   - การอัปเดตความปลอดภัยถูกบันทึกไว้ใน commits
   - การเปิดเผยช่องโหว่ได้รับการจัดการอย่างรับผิดชอบ
   - security advisories สาธารณะเมื่อเหมาะสม

## การรายงานช่องโหว่

### ปัญหาความปลอดภัยที่เราให้ความสำคัญ

เราซาบซึ้งกับรายงานเกี่ยวกับ:
- **ช่องโหว่ของโค้ด** ใน scripts หรือตัวอย่าง
- **ช่องโหว่ของ dependency** ใน Python packages
- **ปัญหาการเข้ารหัส** ในตัวอย่างโค้ดใดๆ
- **ข้อบกพร่อง Authentication/Authorization** ในเอกสาร
- **ความเสี่ยงจากการเปิดเผยข้อมูล** ในตัวอย่างการกำหนดค่า
- **ช่องโหว่การ injection** (SQL, command เป็นต้น)
- **ปัญหา SSRF/XXE/Path traversal**

### ปัญหาความปลอดภัยที่อยู่นอกขอบเขต

สิ่งต่อไปนี้อยู่นอกขอบเขตของโปรเจกต์นี้:
- ช่องโหว่ใน Claude Code เอง (รายงานไปยัง Anthropic)
- ปัญหาบริการหรือไลบรารีภายนอก (รายงานไปยัง upstream)
- Social engineering หรือการให้ความรู้แก่ผู้ใช้ (ไม่เกี่ยวข้องกับคู่มือนี้)
- ช่องโหว่เชิงทฤษฎีที่ไม่มี proof of concept
- ช่องโหว่ใน dependencies ที่รายงานผ่านช่องทางอย่างเป็นทางการ

## วิธีการรายงาน

### การรายงานส่วนตัว (แนะนำ)

**สำหรับปัญหาความปลอดภัยที่ละเอียดอ่อน โปรดใช้การรายงานช่องโหว่ส่วนตัวของ GitHub:**

1. ไปที่: https://github.com/luongnv89/claude-howto/security/advisories
2. คลิก "Report a vulnerability"
3. กรอกรายละเอียดช่องโหว่
4. รวมถึง:
   - คำอธิบายชัดเจนของช่องโหว่
   - ส่วนประกอบที่ได้รับผลกระทบ (ไฟล์, ส่วน, ตัวอย่าง)
   - ผลกระทบที่อาจเกิดขึ้น
   - ขั้นตอนเพื่อทำซ้ำ (ถ้ามี)
   - การแก้ไขที่แนะนำ (ถ้ามี)

**สิ่งที่เกิดขึ้นต่อไป:**
- เราจะยืนยันการรับภายใน 48 ชั่วโมง
- เราจะสืบสวนและประเมินความรุนแรง
- เราจะร่วมมือกับคุณเพื่อพัฒนาการแก้ไข
- เราจะประสานงานกำหนดการเปิดเผย
- เราจะให้เครดิตคุณใน security advisory (เว้นแต่คุณต้องการไม่เปิดเผยตัวตน)

### การรายงานสาธารณะ

สำหรับปัญหาที่ไม่ละเอียดอ่อนหรือที่เปิดเผยต่อสาธารณะแล้ว:

1. **เปิด GitHub Issue** พร้อม label `security`
2. รวมถึง:
   - หัวข้อ: `[SECURITY]` ตามด้วยคำอธิบายสั้นๆ
   - คำอธิบายโดยละเอียด
   - ไฟล์หรือส่วนที่ได้รับผลกระทบ
   - ผลกระทบที่อาจเกิดขึ้น
   - การแก้ไขที่แนะนำ

## กระบวนการตอบสนองต่อช่องโหว่

### การประเมิน (24 ชั่วโมง)

1. เรายืนยันการรับรายงาน
2. เราประเมินความรุนแรงโดยใช้ [CVSS v3.1](https://www.first.org/cvss/v3.1/specification-document)
3. เราพิจารณาว่าอยู่ในขอบเขตหรือไม่
4. เราติดต่อคุณพร้อมการประเมินเบื้องต้น

### การพัฒนา (1-7 วัน)

1. เราพัฒนาการแก้ไข
2. เราตรวจสอบและทดสอบการแก้ไข
3. เราสร้าง security advisory
4. เราเตรียม release notes

### การเปิดเผย (ขึ้นอยู่กับความรุนแรง)

**Critical (CVSS 9.0-10.0)**
- release การแก้ไขทันที
- ออก advisory สาธารณะ
- แจ้งผู้รายงานล่วงหน้า 24 ชั่วโมง

**High (CVSS 7.0-8.9)**
- release การแก้ไขภายใน 48-72 ชั่วโมง
- แจ้งผู้รายงานล่วงหน้า 5 วัน
- advisory สาธารณะเมื่อ release

**Medium (CVSS 4.0-6.9)**
- release การแก้ไขในการอัปเดตปกติถัดไป
- advisory สาธารณะเมื่อ release

**Low (CVSS 0.1-3.9)**
- รวมการแก้ไขในการอัปเดตปกติถัดไป
- advisory เมื่อ release

### การเผยแพร่

เราเผยแพร่ security advisories ที่ประกอบด้วย:
- คำอธิบายของช่องโหว่
- ส่วนประกอบที่ได้รับผลกระทบ
- การประเมินความรุนแรง (CVSS score)
- เวอร์ชันที่แก้ไข
- วิธีแก้ปัญหาชั่วคราว (ถ้ามี)
- เครดิตให้ผู้รายงาน (โดยได้รับอนุญาต)

## แนวปฏิบัติที่ดีสำหรับผู้รายงาน

### ก่อนรายงาน

- **ยืนยันปัญหา**: คุณสามารถทำซ้ำได้อย่างสม่ำเสมอหรือไม่?
- **ค้นหา issues ที่มีอยู่**: มีการรายงานแล้วหรือไม่?
- **ตรวจสอบเอกสาร**: มีคำแนะนำเกี่ยวกับการใช้งานที่ปลอดภัยหรือไม่?
- **ทดสอบการแก้ไข**: การแก้ไขที่คุณแนะนำใช้งานได้หรือไม่?

### เมื่อรายงาน

- **ระบุให้ชัดเจน**: ให้ path ของไฟล์และหมายเลขบรรทัดที่แน่นอน
- **รวมบริบท**: ทำไมนี่จึงเป็นปัญหาความปลอดภัย?
- **แสดงผลกระทบ**: ผู้โจมตีสามารถทำอะไรได้?
- **ให้ขั้นตอน**: เราจะทำซ้ำได้อย่างไร?
- **แนะนำการแก้ไข**: คุณจะแก้ไขอย่างไร?

### หลังรายงาน

- **อดทน**: เรามีทรัพยากรจำกัด
- **ตอบสนอง**: ตอบคำถามติดตามผลอย่างรวดเร็ว
- **รักษาความลับ**: อย่าเปิดเผยต่อสาธารณะก่อนการแก้ไข
- **เคารพการประสานงาน**: ปฏิบัติตามกำหนดการของเราสำหรับการเปิดเผย

## Security Headers และการกำหนดค่า

### ความปลอดภัยของ Repository

- **Branch protection**: branch main ต้องมีการอนุมัติ 2 ครั้งสำหรับการเปลี่ยนแปลง
- **Status checks**: การตรวจสอบ CI/CD ทั้งหมดต้องผ่าน
- **CODEOWNERS**: ผู้ตรวจสอบที่กำหนดไว้สำหรับไฟล์สำคัญ
- **Signed commits**: แนะนำสำหรับผู้ร่วมพัฒนา

### ความปลอดภัยของการพัฒนา

```bash
# Install pre-commit hooks
pre-commit install

# Run security scans locally
bandit -c pyproject.toml -r scripts/
mypy scripts/ --ignore-missing-imports
ruff check scripts/
```

### ความปลอดภัยของ Dependency

```bash
# Check for known vulnerabilities
pip install safety
safety check

# Or use pip-audit
pip install pip-audit
pip-audit
```

## แนวทางด้านความปลอดภัยสำหรับผู้ร่วมพัฒนา

### เมื่อเขียนตัวอย่าง

1. **ห้าม hardcode secrets**
   ```python
   # ❌ Bad
   api_key = "sk-1234567890"

   # ✅ Good
   api_key = os.getenv("API_KEY")
   ```

2. **เตือนเกี่ยวกับผลกระทบด้านความปลอดภัย**
   ```markdown
   ⚠️ **Security Note**: Never commit `.env` files to git.
   Add to `.gitignore` immediately.
   ```

3. **ใช้ค่าเริ่มต้นที่ปลอดภัย**
   - เปิดใช้งานการยืนยันตัวตนโดยค่าเริ่มต้น
   - ใช้ HTTPS ที่เกี่ยวข้อง
   - ตรวจสอบและทำความสะอาด inputs
   - ใช้ parameterized queries

4. **บันทึกข้อพิจารณาด้านความปลอดภัย**
   - อธิบายว่าทำไมความปลอดภัยจึงสำคัญ
   - แสดงรูปแบบที่ปลอดภัยเทียบกับที่ไม่ปลอดภัย
   - ลิงก์ไปยังแหล่งข้อมูลที่เชื่อถือได้
   - รวมคำเตือนไว้อย่างเด่นชัด

### เมื่อตรวจสอบการมีส่วนร่วม

1. **ตรวจสอบ secrets ที่เปิดเผย**
   - สแกนหารูปแบบทั่วไป (api_key=, password=)
   - ตรวจสอบไฟล์การกำหนดค่า
   - ตรวจสอบตัวแปรสภาพแวดล้อม

2. **ยืนยันแนวปฏิบัติการเขียนโค้ดที่ปลอดภัย**
   - ไม่มี credentials ที่ hardcoded
   - การตรวจสอบ input ที่เหมาะสม
   - Authentication/Authorization ที่ปลอดภัย
   - การจัดการไฟล์อย่างปลอดภัย

3. **ทดสอบผลกระทบด้านความปลอดภัย**
   - สิ่งนี้สามารถถูกนำไปใช้ในทางที่ผิดได้หรือไม่?
   - กรณีเลวร้ายที่สุดคืออะไร?
   - มี edge cases หรือไม่?

## ติดต่อ

สำหรับคำถามที่เกี่ยวกับความปลอดภัยหรือเพื่อหารือเกี่ยวกับแนวปฏิบัติด้านความปลอดภัย:

1. **รายงานความปลอดภัยส่วนตัว**: ใช้การรายงานช่องโหว่ส่วนตัวของ GitHub
2. **คำถามความปลอดภัยทั่วไป**: เปิด discussion พร้อมแท็ก `[SECURITY]`
3. **ข้อเสนอแนะต่อนโยบายความปลอดภัย**: สร้าง issue พร้อม label `security`

## กิตติกรรมประกาศ

เราซาบซึ้งกับนักวิจัยด้านความปลอดภัยและสมาชิกชุมชนที่ช่วยให้โปรเจกต์นี้ปลอดภัย ผู้ร่วมพัฒนาที่รายงานช่องโหว่อย่างรับผิดชอบจะได้รับการยอมรับใน security advisories ของเรา (เว้นแต่พวกเขาต้องการไม่เปิดเผยตัวตน)

## การอัปเดตนโยบาย

นโยบายความปลอดภัยนี้ได้รับการตรวจสอบและอัปเดต:
- เมื่อค้นพบช่องโหว่ใหม่
- เมื่อแนวปฏิบัติที่ดีด้านความปลอดภัยพัฒนาไป
- เมื่อขอบเขตของโปรเจกต์เปลี่ยนแปลง
