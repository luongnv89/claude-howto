## ข้อมูลจากผู้ใช้

```text
$ARGUMENTS
```

**จำเป็นต้องพิจารณาข้อมูลจากผู้ใช้ก่อนดำเนินการ** ผู้ใช้ควรระบุ:
- **แนวคิด/หัวข้อ**: แนวคิดหลักหรือธีมของ blog post
- **ทรัพยากร**: URL, ไฟล์ หรือเอกสารอ้างอิงสำหรับการวิจัย (ไม่บังคับแต่แนะนำ)
- **กลุ่มเป้าหมาย**: บทความนี้เขียนสำหรับใคร (ไม่บังคับ)
- **น้ำเสียง/สไตล์**: เป็นทางการ, ลำลอง, เชิงเทคนิค ฯลฯ (ไม่บังคับ)

**สำคัญ**: หากผู้ใช้ขอแก้ไข **blog post ที่มีอยู่แล้ว** ให้ข้ามขั้นตอน 0-8 และเริ่มที่ **ขั้นตอน 9** โดยตรง อ่านไฟล์ draft ที่มีอยู่ก่อน จากนั้นดำเนินการ iteration

## ขั้นตอนการดำเนินการ

ปฏิบัติตามขั้นตอนเหล่านี้เป็นลำดับ **อย่าข้ามขั้นตอนหรือดำเนินการต่อโดยไม่ได้รับอนุมัติจากผู้ใช้ในจุดที่ระบุไว้**

### ขั้นตอน 0: สร้าง Project Folder

1. สร้างชื่อ folder ในรูปแบบ: `YYYY-MM-DD-short-topic-name`
   - ใช้วันที่ของวันนี้
   - สร้าง slug สั้น รองรับ URL จากหัวข้อ (ตัวพิมพ์เล็ก, ขีดกลาง, สูงสุด 5 คำ)

2. สร้างโครงสร้าง folder:
   ```
   blog-posts/
   └── YYYY-MM-DD-short-topic-name/
       └── resources/
   ```

3. ยืนยันการสร้าง folder กับผู้ใช้ก่อนดำเนินการต่อ

### ขั้นตอน 1: การวิจัยและรวบรวมทรัพยากร

1. สร้าง subfolder `resources/` ใน directory ของ blog post

2. สำหรับทรัพยากรแต่ละอย่างที่ได้รับ:
   - **URL**: ดึงข้อมูลและบันทึกข้อมูลสำคัญไปยัง `resources/` เป็นไฟล์ markdown
   - **ไฟล์**: อ่านและสรุปใน `resources/`
   - **หัวข้อ**: ใช้ web search เพื่อรวบรวมข้อมูลล่าสุด

3. สำหรับทรัพยากรแต่ละอย่าง สร้างไฟล์สรุปใน `resources/`:
   - `resources/source-1-[short-name].md`
   - `resources/source-2-[short-name].md`
   - ฯลฯ

4. แต่ละสรุปควรรวม:
   ```markdown
   # แหล่ง: [ชื่อ/URL]

   ## ประเด็นสำคัญ
   - ประเด็น 1
   - ประเด็น 2

   ## ข้อความอ้างอิง/ข้อมูลที่เกี่ยวข้อง
   - อ้างอิงหรือสถิติ 1
   - อ้างอิงหรือสถิติ 2

   ## ความเกี่ยวข้องกับหัวข้อ
   คำอธิบายสั้นถึงความเกี่ยวข้อง
   ```

5. นำเสนอสรุปการวิจัยให้ผู้ใช้

### ขั้นตอน 2: ระดมความคิดและชี้แจง

1. จากแนวคิดและทรัพยากรที่วิจัยแล้ว นำเสนอ:
   - **ธีมหลัก** ที่พบจากการวิจัย
   - **มุมมองที่เป็นไปได้** สำหรับ blog post
   - **ประเด็นสำคัญ** ที่ควรครอบคลุม
   - **ช่องว่าง** ในข้อมูลที่ต้องชี้แจง

2. ถามคำถามชี้แจง:
   - อะไรคือสิ่งที่คุณต้องการให้ผู้อ่านจดจำ?
   - มีประเด็นใดจากการวิจัยที่คุณต้องการเน้น?
   - ความยาวเป้าหมาย? (สั้น: 500-800 คำ, กลาง: 1,000-1,500, ยาว: 2,000+)
   - มีประเด็นใดที่คุณต้องการยกเว้น?

3. **รอการตอบสนองจากผู้ใช้ก่อนดำเนินการต่อ**

### ขั้นตอน 3: เสนอ Outline

1. สร้าง outline ที่มีโครงสร้างรวมถึง:

   ```markdown
   # Outline ของ Blog Post: [ชื่อ]

   ## ข้อมูล Meta
   - **กลุ่มเป้าหมาย**: [ใคร]
   - **น้ำเสียง**: [สไตล์]
   - **ความยาวเป้าหมาย**: [จำนวนคำ]
   - **สาระสำคัญ**: [ข้อความหลัก]

   ## โครงสร้างที่เสนอ

   ### Hook/บทนำ
   - แนวคิด opening hook
   - การวางบริบท
   - thesis statement

   ### หัวข้อที่ 1: [ชื่อ]
   - ประเด็นสำคัญ A
   - ประเด็นสำคัญ B
   - หลักฐานสนับสนุนจาก [แหล่ง]

   ### หัวข้อที่ 2: [ชื่อ]
   - ประเด็นสำคัญ A
   - ประเด็นสำคัญ B

   [ดำเนินการต่อสำหรับทุกหัวข้อ...]

   ### บทสรุป
   - สรุปประเด็นสำคัญ
   - call to action หรือความคิดสุดท้าย

   ## แหล่งที่จะอ้างอิง
   - แหล่ง 1
   - แหล่ง 2
   ```

2. นำเสนอ outline ให้ผู้ใช้และ**ขอการอนุมัติหรือการแก้ไข**

### ขั้นตอน 4: บันทึก Outline ที่อนุมัติแล้ว

1. เมื่อผู้ใช้อนุมัติ outline แล้ว บันทึกไปยัง `OUTLINE.md` ใน folder ของ blog post

2. ยืนยันการบันทึก outline

### ขั้นตอน 5: Commit Outline (ถ้าอยู่ใน git repo)

1. ตรวจสอบว่า directory ปัจจุบันเป็น git repository

2. ถ้าใช่:
   - Stage ไฟล์ใหม่: folder ของ blog post, resources และ OUTLINE.md
   - สร้าง commit ด้วยข้อความ: `docs: Add outline for blog post - [topic-name]`
   - Push ไปยัง remote

3. ถ้าไม่ใช่ git repo ข้ามขั้นตอนนี้และแจ้งผู้ใช้

### ขั้นตอน 6: เขียน Draft

1. จาก outline ที่อนุมัติแล้ว เขียน blog post draft ฉบับเต็ม

2. ปฏิบัติตามโครงสร้างจาก OUTLINE.md อย่างเคร่งครัด

3. รวมถึง:
   - บทนำที่น่าสนใจพร้อม hook
   - หัวข้อหัวข้อที่ชัดเจน
   - หลักฐานและตัวอย่างสนับสนุนจากการวิจัย
   - การเปลี่ยนผ่านที่ลื่นไหลระหว่างหัวข้อ
   - บทสรุปที่แข็งแกร่งพร้อมข้อคิด
   - **การอ้างอิง**: การเปรียบเทียบ สถิติ ข้อมูล และข้ออ้างข้อเท็จจริงทุกอย่างต้องอ้างอิงแหล่งต้นฉบับ

4. บันทึก draft เป็น `draft-v0.1.md` ใน folder ของ blog post

5. รูปแบบ:
   ```markdown
   # [ชื่อ Blog Post]

   *[ไม่บังคับ: คำอธิบายย่อหรือ tagline]*

   [เนื้อหาทั้งหมดพร้อม inline citation...]

   ---

   ## อ้างอิง
   - [1] ชื่อแหล่ง 1 - URL หรือการอ้างอิง
   - [2] ชื่อแหล่ง 2 - URL หรือการอ้างอิง
   - [3] ชื่อแหล่ง 3 - URL หรือการอ้างอิง
   ```

6. **ข้อกำหนดการอ้างอิง**:
   - ทุกข้อมูล สถิติ หรือการเปรียบเทียบต้องมี inline citation
   - ใช้การอ้างอิงแบบตัวเลข [1], [2] ฯลฯ หรือการอ้างอิงชื่อ [ชื่อแหล่ง]
   - เชื่อมโยงการอ้างอิงไปยังหัวข้ออ้างอิง (References) ที่ท้ายบทความ
   - ตัวอย่าง: "การศึกษาแสดงว่านักพัฒนา 65% ชอบ TypeScript [1]"
   - ตัวอย่าง: "React มีความเร็วในการ render สูงกว่า Vue 20% [React Benchmarks 2024]"

### ขั้นตอน 7: Commit Draft (ถ้าอยู่ใน git repo)

1. ตรวจสอบว่าอยู่ใน git repository

2. ถ้าใช่:
   - Stage ไฟล์ draft
   - สร้าง commit ด้วยข้อความ: `docs: Add draft v0.1 for blog post - [topic-name]`
   - Push ไปยัง remote

3. ถ้าไม่ใช่ git repo ข้ามและแจ้งผู้ใช้

### ขั้นตอน 8: นำเสนอ Draft เพื่อตรวจสอบ

1. นำเสนอเนื้อหา draft ให้ผู้ใช้

2. ขอ feedback:
   - ความประทับใจโดยรวม?
   - หัวข้อที่ต้องการขยายหรือย่อ?
   - ต้องการปรับน้ำเสียงไหม?
   - ข้อมูลที่ขาดหายไป?
   - การแก้ไขหรือเขียนใหม่เฉพาะส่วน?

3. **รอการตอบสนองจากผู้ใช้**

### ขั้นตอน 9: Iterate หรือสรุปผล

**ถ้าผู้ใช้ขอการเปลี่ยนแปลง:**
1. บันทึกการแก้ไขที่ขอทั้งหมด
2. กลับไปที่ขั้นตอน 6 พร้อมการปรับ:
   - เพิ่มหมายเลขเวอร์ชัน (v0.2, v0.3 ฯลฯ)
   - รวม feedback ทั้งหมด
   - บันทึกเป็น `draft-v[X.Y].md`
   - ทำซ้ำขั้นตอน 7-8

**ถ้าผู้ใช้อนุมัติ:**
1. ยืนยัน draft เวอร์ชันสุดท้าย
2. อาจเปลี่ยนชื่อเป็น `final.md` ถ้าผู้ใช้ขอ
3. สรุปกระบวนการสร้าง blog post:
   - จำนวนเวอร์ชันที่สร้าง
   - การเปลี่ยนแปลงสำคัญระหว่างเวอร์ชัน
   - จำนวนคำสุดท้าย
   - ไฟล์ที่สร้าง

## การติดตามเวอร์ชัน

Draft ทั้งหมดถูกเก็บรักษาด้วยการกำหนดเวอร์ชันแบบเพิ่มขึ้น:
- `draft-v0.1.md` — Draft เริ่มต้น
- `draft-v0.2.md` — หลัง feedback รอบแรก
- `draft-v0.3.md` — หลัง feedback รอบสอง
- ฯลฯ

วิธีนี้ช่วยให้ติดตามพัฒนาการของ blog post ได้ และย้อนกลับได้หากจำเป็น

## โครงสร้างไฟล์ผลลัพธ์

```
blog-posts/
└── YYYY-MM-DD-topic-name/
    ├── resources/
    │   ├── source-1-name.md
    │   ├── source-2-name.md
    │   └── ...
    ├── OUTLINE.md
    ├── draft-v0.1.md
    ├── draft-v0.2.md (ถ้ามี iteration)
    └── draft-v0.3.md (ถ้ามี iteration เพิ่มเติม)
```

## เคล็ดลับสำหรับคุณภาพ

- **Hook**: เริ่มต้นด้วยคำถาม ข้อเท็จจริงที่น่าประหลาดใจ หรือสถานการณ์ที่เข้าใจได้
- **การไหล**: แต่ละย่อหน้าควรเชื่อมต่อกับย่อหน้าถัดไป
- **หลักฐาน**: สนับสนุนข้ออ้างด้วยข้อมูลจากการวิจัย
- **การอ้างอิง**: ต้องอ้างอิงแหล่งเสมอสำหรับ:
  - สถิติและข้อมูลทั้งหมด (เช่น "อ้างอิงจาก [แหล่ง] 75% ของ...")
  - การเปรียบเทียบระหว่างผลิตภัณฑ์ บริการ หรือแนวทาง (เช่น "X ทำงานเร็วกว่า Y 2 เท่า [แหล่ง]")
  - ข้ออ้างข้อเท็จจริงเกี่ยวกับแนวโน้มตลาด ผลการวิจัย หรือ benchmark
  - ใช้ inline citation ในรูปแบบ: [ชื่อแหล่ง] หรือ [ผู้เขียน, ปี]
- **น้ำเสียง**: รักษา tone ที่สม่ำเสมอตลอด
- **ความยาว**: ปฏิบัติตามจำนวนคำเป้าหมาย
- **การอ่าน**: ใช้ย่อหน้าสั้น bullet point ตามความเหมาะสม
- **CTA**: จบด้วย call-to-action ที่ชัดเจนหรือคำถามที่กระตุ้นความคิด

## หมายเหตุ

- รอการอนุมัติจากผู้ใช้เสมอในจุดตรวจสอบที่ระบุไว้
- เก็บรักษา draft ทุกเวอร์ชันไว้เป็นประวัติ
- ใช้ web search เพื่อหาข้อมูลล่าสุดเมื่อมีการระบุ URL
- หากทรัพยากรไม่เพียงพอ ขอเพิ่มเติมจากผู้ใช้หรือแนะนำการวิจัยเพิ่มเติม
- ปรับน้ำเสียงตามกลุ่มเป้าหมาย (เชิงเทคนิค, ทั่วไป, ธุรกิจ ฯลฯ)
