# การมีส่วนร่วมใน Claude How To

ขอบคุณที่สนใจมีส่วนร่วมในโปรเจกต์นี้ คู่มือนี้จะช่วยให้เข้าใจวิธีการมีส่วนร่วมอย่างมีประสิทธิภาพ

## เกี่ยวกับโปรเจกต์นี้

Claude How To เป็นคู่มือเชิงภาพและตัวอย่างสำหรับ Claude Code เราจัดเตรียม:
- **Mermaid diagram** อธิบายการทำงานของฟีเจอร์
- **Template ระดับ production** ที่ใช้งานได้ทันที
- **ตัวอย่างจากโลกจริง** พร้อม context และแนวปฏิบัติที่ดี
- **เส้นทางการเรียนรู้แบบค่อยเป็นค่อยไป** จากผู้เริ่มต้นถึงขั้นสูง

## ประเภทของการมีส่วนร่วม

### 1. ตัวอย่างหรือ Template ใหม่
เพิ่มตัวอย่างสำหรับฟีเจอร์ที่มีอยู่ (slash command, skill, hook ฯลฯ):
- โค้ดที่พร้อมคัดลอกไปใช้
- คำอธิบายที่ชัดเจนว่าทำงานอย่างไร
- กรณีการใช้งานและประโยชน์
- เคล็ดลับการแก้ไขปัญหา

### 2. การปรับปรุงเอกสาร
- ชี้แจงส่วนที่สับสน
- แก้ไข typo และไวยากรณ์
- เพิ่มข้อมูลที่ขาดหาย
- ปรับปรุงตัวอย่างโค้ด

### 3. คู่มือฟีเจอร์
สร้างคู่มือสำหรับฟีเจอร์ใหม่ของ Claude Code:
- บทเรียนทีละขั้นตอน
- Diagram สถาปัตยกรรม
- รูปแบบทั่วไปและ anti-pattern
- Workflow จากโลกจริง

### 4. รายงานข้อผิดพลาด
รายงานปัญหาที่พบ:
- อธิบายสิ่งที่คาดหวัง
- อธิบายสิ่งที่เกิดขึ้นจริง
- รวมขั้นตอนการทำซ้ำ
- เพิ่มเวอร์ชัน Claude Code และ OS ที่เกี่ยวข้อง

### 5. Feedback และข้อเสนอแนะ
ช่วยปรับปรุงคู่มือ:
- แนะนำคำอธิบายที่ดีกว่า
- ชี้ให้เห็นช่องว่างในการครอบคลุม
- แนะนำส่วนหรือการจัดระเบียบใหม่

## การเริ่มต้น

### 1. Fork และ Clone
```bash
git clone https://github.com/luongnv89/claude-howto.git
cd claude-howto
```

### 2. สร้าง Branch
ใช้ชื่อ branch ที่สื่อความหมาย:
```bash
git checkout -b add/feature-name
git checkout -b fix/issue-description
git checkout -b docs/improvement-area
```

### 3. ตั้งค่าสภาพแวดล้อม

Pre-commit hook รันการตรวจสอบเดียวกับ CI ในเครื่องก่อนทุก commit การตรวจสอบทั้งสี่อย่างต้องผ่านก่อนที่ PR จะได้รับการยอมรับ

**dependencies ที่จำเป็น:**

```bash
# Python tooling (uv เป็น package manager สำหรับโปรเจกต์นี้)
pip install uv
uv venv
source .venv/bin/activate
uv pip install -r scripts/requirements-dev.txt

# Markdown linter (Node.js)
npm install -g markdownlint-cli

# Mermaid diagram validator (Node.js)
npm install -g @mermaid-js/mermaid-cli

# ติดตั้ง pre-commit และเปิดใช้งาน hook
uv pip install pre-commit
pre-commit install
```

**ตรวจสอบการตั้งค่า:**

```bash
pre-commit run --all-files
```

Hook ที่รันในทุก commit:

| Hook | สิ่งที่ตรวจสอบ |
|------|---------------|
| `markdown-lint` | การจัดรูปแบบและโครงสร้าง Markdown |
| `cross-references` | relative link, anchor, code fence |
| `mermaid-syntax` | บล็อก ` ```mermaid ` ทั้งหมด parse ได้ถูกต้อง |
| `link-check` | URL ภายนอกเข้าถึงได้ |
| `build-epub` | EPUB สร้างได้โดยไม่มีข้อผิดพลาด (เมื่อไฟล์ `.md` เปลี่ยนแปลง) |

## วิธีการมีส่วนร่วมตัวอย่าง

### การเพิ่ม Slash Command
1. สร้างไฟล์ `.md` ใน `01-slash-commands/`
2. รวมถึง:
   - คำอธิบายที่ชัดเจนว่าทำอะไร
   - กรณีการใช้งาน
   - คำสั่งติดตั้ง
   - ตัวอย่างการใช้งาน
   - เคล็ดลับการปรับแต่ง
3. อัปเดต `01-slash-commands/README.md`

### การเพิ่ม Skill
1. สร้างไดเรกทอรีใน `03-skills/`
2. รวมถึง:
   - `SKILL.md` — เอกสารหลัก
   - `scripts/` — helper script หากจำเป็น
   - `templates/` — prompt template
   - ตัวอย่างการใช้งานใน README
3. อัปเดต `03-skills/README.md`

### การเพิ่ม Subagent
1. สร้างไฟล์ `.md` ใน `04-subagents/`
2. รวมถึง:
   - จุดประสงค์และความสามารถของ agent
   - โครงสร้าง system prompt
   - กรณีการใช้งานตัวอย่าง
   - ตัวอย่างการผสานรวม
3. อัปเดต `04-subagents/README.md`

### การเพิ่มการกำหนดค่า MCP
1. สร้างไฟล์ `.json` ใน `05-mcp/`
2. รวมถึง:
   - คำอธิบายการกำหนดค่า
   - ตัวแปรสภาพแวดล้อมที่จำเป็น
   - คำสั่งการตั้งค่า
   - ตัวอย่างการใช้งาน
3. อัปเดต `05-mcp/README.md`

### การเพิ่ม Hook
1. สร้างไฟล์ `.sh` ใน `06-hooks/`
2. รวมถึง:
   - shebang และคำอธิบาย
   - comment ที่ชัดเจนอธิบาย logic
   - การจัดการข้อผิดพลาด
   - ข้อพิจารณาด้านความปลอดภัย
3. อัปเดต `06-hooks/README.md`

## แนวทางการเขียน

### รูปแบบ Markdown
- ใช้หัวข้อที่ชัดเจน (H2 สำหรับส่วน, H3 สำหรับหัวข้อย่อย)
- รักษาย่อหน้าให้สั้นและมีโฟกัส
- ใช้ bullet point สำหรับรายการ
- รวม code block พร้อมระบุภาษา
- เพิ่มบรรทัดว่างระหว่างส่วน

### ตัวอย่างโค้ด
- ทำให้ตัวอย่างพร้อมคัดลอกไปใช้
- ใส่ comment สำหรับ logic ที่ไม่ชัดเจน
- รวมทั้งเวอร์ชันง่ายและขั้นสูง
- แสดงกรณีการใช้งานจากโลกจริง
- ไฮไลต์ปัญหาที่อาจเกิดขึ้น

### เอกสาร
- อธิบาย "ทำไม" ไม่ใช่แค่ "อะไร"
- รวมข้อกำหนดเบื้องต้น
- เพิ่มส่วนการแก้ไขปัญหา
- Link ไปยังหัวข้อที่เกี่ยวข้อง
- รักษาให้เข้าใจง่ายสำหรับผู้เริ่มต้น

### JSON/YAML
- ใช้การเยื้องที่ถูกต้อง (2 หรือ 4 space อย่างสม่ำเสมอ)
- เพิ่ม comment อธิบายการกำหนดค่า
- รวมตัวอย่างการ validate

### Diagram
- ใช้ Mermaid เมื่อเป็นไปได้
- รักษา diagram ให้เรียบง่ายและอ่านง่าย
- รวมคำอธิบายด้านล่าง diagram
- Link ไปยังส่วนที่เกี่ยวข้อง

## แนวทาง Commit

ปฏิบัติตามรูปแบบ conventional commit:
```
type(scope): description

[optional body]
```

ประเภท:
- `feat`: ฟีเจอร์ใหม่หรือตัวอย่าง
- `fix`: การแก้ไขข้อผิดพลาด
- `docs`: การเปลี่ยนแปลงเอกสาร
- `refactor`: การปรับโครงสร้างโค้ด
- `style`: การเปลี่ยนแปลงการจัดรูปแบบ
- `test`: การเพิ่มหรือเปลี่ยนแปลงการทดสอบ
- `chore`: build, dependencies ฯลฯ

ตัวอย่าง:
```
feat(slash-commands): Add API documentation generator
docs(memory): Improve personal preferences example
fix(README): Correct table of contents link
docs(skills): Add comprehensive code review skill
```

- [ ] โค้ดปฏิบัติตามรูปแบบและข้อตกลงของโปรเจกต์
- [ ] ตัวอย่างใหม่มีเอกสารที่ชัดเจน

- [ ] ไม่มีข้อมูลที่ละเอียดอ่อน (API key, ข้อมูลประจำตัว)
- [ ] ทดสอบและตรวจสอบว่าตัวอย่างทำงานได้
- [ ] ตรวจสอบ link ว่าถูกต้อง
- [ ] ไฟล์มี permission ที่ถูกต้อง (script ต้องสั่ง execute ได้)
- [ ] Commit message ชัดเจนและสื่อความหมาย

## กระบวนการ Pull Request

1. **สร้าง PR พร้อมคำอธิบายที่ชัดเจน**:
   - สิ่งนี้เพิ่ม/แก้ไขอะไร?
   - ทำไมจึงจำเป็น?
   - Issue ที่เกี่ยวข้อง (ถ้ามี)

2. **รวมรายละเอียดที่เกี่ยวข้อง**:
   - ฟีเจอร์ใหม่? รวมกรณีการใช้งาน
   - เอกสาร? อธิบายการปรับปรุง
   - ตัวอย่าง? แสดงก่อน/หลัง

3. **Link ไปยัง issue**:
   - ใช้ `Closes #123` เพื่อปิด issue ที่เกี่ยวข้องอัตโนมัติ

4. **อดทนกับการ review**:
   - ผู้ดูแลอาจแนะนำการปรับปรุง
   - ปรับปรุงตาม feedback
   - การตัดสินใจสุดท้ายอยู่ที่ผู้ดูแล

## กระบวนการ Code Review

ผู้ review จะตรวจสอบ:
- **ความถูกต้อง**: ทำงานได้ตามที่อธิบายไว้หรือไม่?
- **คุณภาพ**: พร้อมสำหรับ production หรือไม่?
- **ความสอดคล้อง**: เป็นไปตามรูปแบบของโปรเจกต์หรือไม่?
- **เอกสาร**: ชัดเจนและครบถ้วนหรือไม่?
- **ความปลอดภัย**: มีช่องโหว่หรือไม่?

## ความปลอดภัย

เมื่อมีส่วนร่วมกับตัวอย่างและเอกสาร โปรดปฏิบัติตามแนวปฏิบัติการเขียนโค้ดอย่างปลอดภัย:

- **ห้าม hardcode secret หรือ API key** — ใช้ตัวแปรสภาพแวดล้อม
- **แจ้งเตือนเกี่ยวกับผลกระทบด้านความปลอดภัย** — ไฮไลต์ความเสี่ยงที่อาจเกิดขึ้น
- **ใช้ค่าเริ่มต้นที่ปลอดภัย** — เปิดใช้ฟีเจอร์ความปลอดภัยตามค่าเริ่มต้น
- **ตรวจสอบ input** — แสดงการตรวจสอบและทำความสะอาด input อย่างถูกต้อง
- **รวมหมายเหตุด้านความปลอดภัย** — จัดทำเอกสารข้อพิจารณาด้านความปลอดภัย

สำหรับปัญหาด้านความปลอดภัย ดู [SECURITY.md](SECURITY.md) สำหรับกระบวนการรายงานช่องโหว่ของเรา
