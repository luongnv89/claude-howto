# AI 코드 생성을 위한 클린 코드 규칙

이 규칙은 유지보수 가능하고 전문적인 품질의 코드를 생성하도록 코드 생성을 안내합니다.

## 의미 있는 이름

* 존재 이유를 설명하는 의도가 드러나는 이름을 사용합니다.
* 오해를 유발하거나 의미 없는 구분(`data`, `info`, `manager` 등)을 피합니다.
* 발음하기 쉽고 검색 가능한 이름을 사용합니다.
* 클래스 이름: 명사 (예: `UserAccount`, `PaymentProcessor`)
* 메서드 이름: 동사 (예: `calculateTotal`, `sendEmail`)
* 정신적 매핑과 인코딩(헝가리안 표기법, 접두사 등)을 피합니다.

## 함수

* 함수는 작게 유지합니다(이상적으로 20줄 미만).
* 하나의 일만 수행합니다 - 단일 책임 원칙(Single Responsibility Principle)
* 함수마다 하나의 추상화 수준만 사용합니다.
* 매개변수는 제한합니다: 이상적으로 0~2개, 최대 3개, 플래그 인수는 피합니다.
* 부작용이 없어야 합니다 - 함수는 이름이 의미하는 동작만 수행해야 합니다.
* 명령(상태 변경)과 조회(정보 반환)를 분리합니다.
* 오류 코드보다 예외를 선호합니다.

## 주석

* 코드는 스스로 설명 가능해야 하므로 가능한 한 주석을 피합니다.
* 좋은 주석: 법적 정보, 경고, TODO, 공개 API 문서
* 나쁜 주석: 중복, 오해를 유발하는 내용, 잘못된 코드를 설명하는 내용
* 코드를 주석 처리하지 마십시오 - 삭제하십시오(버전 관리 시스템이 이력을 보존합니다).
* 주석이 필요하다면 먼저 리팩토링할 수 있는지 검토하십시오.

## 포맷팅

* 파일은 작고 하나의 목적에 집중되도록 유지합니다.
* 세로 포맷팅: 관련 개념은 가깝게 배치하고, 빈 줄로 개념을 구분합니다.
* 가로 포맷팅: 줄 길이를 제한합니다(80~120자).
* 일관된 들여쓰기와 팀 스타일을 사용합니다.
* 관련된 함수들을 함께 배치합니다.

## 객체와 데이터 구조

* 객체: 데이터를 추상화 뒤에 숨기고 메서드를 통해 동작을 노출합니다.
* 데이터 구조: 데이터를 노출하고 동작은 최소화합니다.
* 디미터 법칙(Law of Demeter): 직접적인 협력 객체와만 상호작용하며, `a.getB().getC().doSomething()` 형태를 피합니다.
* Getter/Setter를 무분별하게 사용하여 내부 구조를 노출하지 않습니다.

## 오류 처리

* 반환 코드나 오류 플래그 대신 예외를 사용합니다.
* 실패 가능성이 있는 코드에서는 먼저 `try-catch-finally` 구조를 고려합니다.
* 예외 메시지에 충분한 문맥을 제공합니다.
* `null`을 반환하지 마십시오 - 빈 컬렉션 또는 Optional/Maybe를 사용합니다.
* `null`을 인수로 전달하지 마십시오.

## 클래스

* 클래스의 크기는 줄 수가 아닌 책임의 개수로 판단합니다.
* 단일 책임 원칙(SRP): 변경 이유는 하나여야 합니다.
* 높은 응집도: 클래스 변수들이 여러 메서드에서 함께 사용되어야 합니다.
* 낮은 결합도: 클래스 간 의존성을 최소화합니다.
* 개방-폐쇄 원칙(OCP): 확장에는 열려 있고 수정에는 닫혀 있어야 합니다.

## 단위 테스트

* F.I.R.S.T. 원칙 준수: Fast, Independent, Repeatable, Self-validating, Timely
* 테스트당 하나의 검증(또는 하나의 개념)
* 테스트 코드 품질도 운영 코드 품질과 동일해야 합니다.
* 무엇을 테스트하는지 설명하는 읽기 쉬운 테스트 이름을 사용합니다.
* Arrange-Act-Assert 패턴을 사용합니다.

## 코드 품질 원칙

* **DRY (Don't Repeat Yourself)**: 중복을 제거합니다.
* **YAGNI (You Aren't Gonna Need It)**: 가상의 미래 요구사항을 위해 구현하지 않습니다.
* **KISS (Keep It Simple)**: 불필요한 복잡성을 피합니다.
* **Boy Scout Rule**: 발견했을 때보다 더 깨끗한 상태로 코드를 남깁니다.

## 피해야 할 코드 스멜

* 긴 함수 또는 클래스
* 중복 코드
* 죽은 코드(사용되지 않는 변수, 함수, 매개변수)
* Feature Envy(다른 클래스에 과도하게 의존하는 메서드)
* Inappropriate Intimacy(클래스 간 과도한 내부 지식 공유)
* 긴 매개변수 목록
* Primitive Obsession(작은 객체 대신 원시 타입 과다 사용)
* Switch/Case 문(다형성 고려)
* Temporary Field(일부 상황에서만 사용되는 클래스 변수)

## 동시성

* 동시성 코드는 다른 코드와 분리합니다.
* 동기화 또는 잠금 데이터의 범위를 최소화합니다.
* 스레드 안전 컬렉션을 사용합니다.
* 동기화 구간은 짧게 유지합니다.
* 실행 모델과 동시성 도구를 충분히 이해합니다.

## 시스템 설계

* 생성과 사용을 분리합니다(의존성 주입).
* 복잡한 객체 생성에는 Factory, Builder를 사용합니다.
* 구현이 아닌 인터페이스에 의존합니다.
* 상속보다 합성을 선호합니다.
* 디자인 패턴은 단순화를 위해 사용하며 과시를 위해 사용하지 않습니다.

## 리팩토링

* 대규모 작업이 아닌 지속적으로 리팩토링합니다.
* 리팩토링 전후 모두 테스트가 통과해야 합니다.
* 작은 단계로 진행합니다 - 한 번에 하나의 변경만 수행합니다.
* 대표적인 리팩토링: Extract Method, Rename, Move, Inline

## 문서화

* 자기 설명적인 코드 > 주석 > 외부 문서
* 공개 API는 명확한 문서가 필요합니다.
* 문서에는 예제를 포함합니다.
* 문서는 코드 가까이에 유지합니다(가능하면 코드 내부).
