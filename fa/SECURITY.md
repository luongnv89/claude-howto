# سیاست امنیتی

## نمای کلی

امنیت پروژه Claude How To برای ما مهم است. این سند رویه‌های امنیتی ما را شرح می‌دهد و توضیح می‌دهد که چگونه آسیب‌پذیری‌های امنیتی را به‌صورت مسئولانه گزارش کنید.

## نسخه‌های پشتیبانی‌شده

ما به‌روزرسانی‌های امنیتی را برای نسخه‌های زیر ارائه می‌دهیم:

| نسخه | وضعیت | پشتیبانی تا |
|---------|--------|---------------|
| آخرین (main) | ✅ فعال | کنونی + ۶ ماه |

**توجه**: به‌عنوان یک پروژه راهنمای آموزشی، تمرکز ما بر حفظ بهترین رویه‌های کنونی و امنیت مستندات است، نه پشتیبانی سنتی از نسخه‌ها. به‌روزرسانی‌ها مستقیماً روی شاخه main اعمال می‌شوند.

## رویه‌های امنیتی

### امنیت کد

1. **مدیریت وابستگی‌ها**
   - تمام وابستگی‌های Python در `requirements.txt` پین شده‌اند
   - به‌روزرسانی‌های منظم از طریق dependabot و بازبینی دستی
   - اسکن امنیتی با Bandit روی هر کامیت
   - هوک‌های pre-commit برای بررسی‌های امنیتی

2. **کیفیت کد**
   - لینت با Ruff مسائل رایج را می‌گیرد
   - بررسی نوع با mypy از آسیب‌پذیری‌های مرتبط با نوع جلوگیری می‌کند
   - هوک‌های pre-commit استانداردها را الزامی می‌کنند
   - همه تغییرات پیش از ادغام بازبینی می‌شوند

3. **کنترل دسترسی**
   - محافظت شاخه روی شاخه `main`
   - بازبینی‌های الزامی پیش از ادغام
   - بررسی‌های وضعیت باید پیش از ادغام موفق شوند
   - دسترسی نوشتن محدود به مخزن

### امنیت مستندات

1. **بدون اسرار در مثال‌ها**
   - همه کلیدهای API در مثال‌ها جای‌نگهدار هستند
   - اعتبارنامه‌ها هرگز به‌صورت سخت‌کدشده نیستند
   - فایل‌های `.env.example` متغیرهای لازم را نشان می‌دهند
   - هشدارهای روشن درباره مدیریت اسرار

2. **بهترین رویه‌های امنیتی**
   - مثال‌ها الگوهای امن را نشان می‌دهند
   - هشدارهای امنیتی در مستندات برجسته شده‌اند
   - پیوند به راهنماهای امنیتی رسمی
   - مدیریت اعتبارنامه در بخش‌های مربوطه بحث می‌شود

3. **بازبینی محتوا**
   - همه مستندات از نظر مسائل امنیتی بازبینی می‌شوند
   - ملاحظات امنیتی در راهنمای مشارکت
   - اعتبارسنجی پیوندها و ارجاع‌های خارجی

### امنیت وابستگی‌ها

1. **اسکن**
   - Bandit همه کدهای Python را برای آسیب‌پذیری‌ها اسکن می‌کند
   - بررسی آسیب‌پذیری وابستگی‌ها از طریق هشدارهای امنیتی GitHub
   - ممیزی‌های امنیتی دستی منظم

2. **به‌روزرسانی‌ها**
   - وصله‌های امنیتی به‌سرعت اعمال می‌شوند
   - نسخه‌های اصلی با دقت ارزیابی می‌شوند
   - تغییرنگار شامل به‌روزرسانی‌های مرتبط با امنیت است

3. **شفافیت**
   - به‌روزرسانی‌های امنیتی در کامیت‌ها مستند می‌شوند
   - افشای آسیب‌پذیری‌ها به‌صورت مسئولانه انجام می‌شود
   - هشدارهای امنیتی عمومی در صورت لزوم

## گزارش یک آسیب‌پذیری

### مسائل امنیتی که برای ما مهم هستند

از گزارش‌های زیر استقبال می‌کنیم:
- **آسیب‌پذیری‌های کد** در اسکریپت‌ها یا مثال‌ها
- **آسیب‌پذیری‌های وابستگی** در بسته‌های Python
- **مسائل رمزنگاری** در هر نمونه کد
- **نقص‌های احراز هویت/مجوزدهی** در مستندات
- **ریسک‌های افشای داده** در نمونه‌های پیکربندی
- **آسیب‌پذیری‌های تزریق** (SQL، فرمان و غیره)
- **مسائل SSRF/XXE/پیمایش مسیر**

### مسائل امنیتی خارج از دامنه

موارد زیر خارج از دامنه این پروژه هستند:
- آسیب‌پذیری‌های خود Claude Code (به Anthropic گزارش دهید)
- مسائل مربوط به سرویس‌ها یا کتابخانه‌های خارجی (به بالادست گزارش دهید)
- مهندسی اجتماعی یا آموزش کاربر (برای این راهنما کاربرد ندارد)
- آسیب‌پذیری‌های نظری بدون اثبات مفهوم
- آسیب‌پذیری‌های وابستگی‌ها که از کانال‌های رسمی گزارش شده‌اند

## نحوه گزارش

### گزارش خصوصی (ترجیحی)

**برای مسائل امنیتی حساس، لطفاً از گزارش خصوصی آسیب‌پذیری GitHub استفاده کنید:**

1. بازدید کنید: https://github.com/luongnv89/claude-howto/security/advisories
2. روی «Report a vulnerability» کلیک کنید
3. جزئیات آسیب‌پذیری را پر کنید
4. موارد زیر را شامل شوید:
   - شرح روشن آسیب‌پذیری
   - مؤلفه تحت تأثیر (فایل، بخش، مثال)
   - تأثیر بالقوه
   - مراحل بازتولید (در صورت کاربرد)
   - اصلاح پیشنهادی (اگر دارید)

**پس از آن چه می‌شود:**
- دریافت گزارش را ظرف ۴۸ ساعت تأیید می‌کنیم
- بررسی می‌کنیم و شدت را ارزیابی می‌کنیم
- برای توسعه اصلاح با شما همکاری می‌کنیم
- زمان‌بندی افشا را هماهنگ می‌کنیم
- در هشدار امنیتی از شما قدردانی می‌کنیم (مگر اینکه ترجیح دهید ناشناس بمانید)

### گزارش عمومی

برای مسائل غیرحساس یا مواردی که از قبل عمومی شده‌اند:

1. **یک Issue در GitHub باز کنید** با برچسب `security`
2. موارد زیر را شامل شوید:
   - عنوان: `[SECURITY]` به‌همراه توضیح کوتاه
   - شرح مفصل
   - فایل یا بخش تحت تأثیر
   - تأثیر بالقوه
   - اصلاح پیشنهادی

## فرایند پاسخ به آسیب‌پذیری

### ارزیابی (۲۴ ساعت)

1. دریافت گزارش را تأیید می‌کنیم
2. شدت را با استفاده از [CVSS v3.1](https://www.first.org/cvss/v3.1/specification-document) ارزیابی می‌کنیم
3. تعیین می‌کنیم که آیا در دامنه است
4. با ارزیابی اولیه با شما تماس می‌گیریم

### توسعه (۱-۷ روز)

1. یک اصلاح توسعه می‌دهیم
2. اصلاح را بازبینی و آزمایش می‌کنیم
3. یک هشدار امنیتی ایجاد می‌کنیم
4. یادداشت‌های انتشار را آماده می‌کنیم

### افشا (بسته به شدت متفاوت است)

**بحرانی (CVSS 9.0-10.0)**
- اصلاح فوراً منتشر می‌شود
- هشدار عمومی صادر می‌شود
- اطلاع ۲۴ ساعته پیش از انتشار به گزارش‌دهندگان

**بالا (CVSS 7.0-8.9)**
- اصلاح ظرف ۴۸-۷۲ ساعت منتشر می‌شود
- اطلاع ۵ روزه پیش از انتشار به گزارش‌دهندگان
- هشدار عمومی هنگام انتشار

**متوسط (CVSS 4.0-6.9)**
- اصلاح در به‌روزرسانی منظم بعدی منتشر می‌شود
- هشدار عمومی هنگام انتشار

**پایین (CVSS 0.1-3.9)**
- اصلاح در به‌روزرسانی منظم بعدی گنجانده می‌شود
- هشدار هنگام انتشار

### انتشار

ما هشدارهای امنیتی را منتشر می‌کنیم که شامل موارد زیر است:
- شرح آسیب‌پذیری
- مؤلفه‌های تحت تأثیر
- ارزیابی شدت (امتیاز CVSS)
- نسخه اصلاح
- راه‌های دور زدن (در صورت کاربرد)
- قدردانی از گزارش‌دهنده (با اجازه)

## بهترین رویه‌ها برای گزارش‌دهندگان

### پیش از گزارش

- **مسئله را بررسی کنید**: آیا می‌توانید آن را به‌طور مداوم بازتولید کنید؟
- **مسائل موجود را جستجو کنید**: آیا قبلاً گزارش شده است؟
- **مستندات را بررسی کنید**: آیا راهنمایی درباره استفاده امن وجود دارد؟
- **اصلاح را آزمایش کنید**: آیا اصلاح پیشنهادی شما کار می‌کند؟

### هنگام گزارش

- **دقیق باشید**: مسیرهای فایل و شماره خطوط دقیق را ارائه دهید
- **زمینه را شامل شوید**: چرا این یک مسئله امنیتی است؟
- **تأثیر را نشان دهید**: یک مهاجم چه کاری می‌تواند انجام دهد؟
- **مراحل را ارائه دهید**: چگونه می‌توانیم آن را بازتولید کنیم؟
- **اصلاح پیشنهاد دهید**: چگونه آن را اصلاح می‌کنید؟

### پس از گزارش

- **صبور باشید**: منابع ما محدود است
- **پاسخگو باشید**: به پرسش‌های بعدی سریع پاسخ دهید
- **محرمانه نگه دارید**: پیش از اصلاح به‌صورت عمومی افشا نکنید
- **به هماهنگی احترام بگذارید**: زمان‌بندی افشای ما را دنبال کنید

## سرآیندها و پیکربندی امنیتی

### امنیت مخزن

- **محافظت شاخه**: شاخه اصلی برای تغییرات به ۲ تأیید نیاز دارد
- **بررسی‌های وضعیت**: همه بررسی‌های CI/CD باید موفق شوند
- **CODEOWNERS**: بازبین‌های تعیین‌شده برای فایل‌های کلیدی
- **کامیت‌های امضاشده**: برای مشارکت‌کنندگان توصیه می‌شود

### امنیت توسعه

```bash
# نصب هوک‌های pre-commit
pre-commit install

# اجرای اسکن‌های امنیتی به‌صورت محلی
bandit -c pyproject.toml -r scripts/
mypy scripts/ --ignore-missing-imports
ruff check scripts/
```

### امنیت وابستگی‌ها

```bash
# بررسی آسیب‌پذیری‌های شناخته‌شده
pip install safety
safety check

# یا استفاده از pip-audit
pip install pip-audit
pip-audit
```

## راهنمای امنیتی برای مشارکت‌کنندگان

### هنگام نوشتن مثال‌ها

1. **هرگز اسرار را سخت‌کد نکنید**
   ```python
   # ❌ بد
   api_key = "sk-1234567890"

   # ✅ خوب
   api_key = os.getenv("API_KEY")
   ```

2. **درباره پیامدهای امنیتی هشدار دهید**
   ```markdown
   ⚠️ **نکته امنیتی**: هرگز فایل‌های `.env` را در git کامیت نکنید.
   بلافاصله به `.gitignore` اضافه کنید.
   ```

3. **از پیش‌فرض‌های امن استفاده کنید**
   - احراز هویت را به‌صورت پیش‌فرض فعال کنید
   - در جایی که کاربرد دارد از HTTPS استفاده کنید
   - ورودی‌ها را اعتبارسنجی و پاک‌سازی کنید
   - از کوئری‌های پارامتری استفاده کنید

4. **ملاحظات امنیتی را مستند کنید**
   - توضیح دهید چرا امنیت مهم است
   - الگوهای امن و ناامن را نشان دهید
   - به منابع معتبر پیوند دهید
   - هشدارها را برجسته بگنجانید

### هنگام بازبینی مشارکت‌ها

1. **اسرار افشاشده را بررسی کنید**
   - الگوهای رایج را اسکن کنید (api_key=، password=)
   - فایل‌های پیکربندی را بازبینی کنید
   - متغیرهای محیطی را بررسی کنید

2. **رویه‌های کدنویسی امن را تأیید کنید**
   - بدون اعتبارنامه سخت‌کدشده
   - اعتبارسنجی مناسب ورودی
   - احراز هویت/مجوزدهی امن
   - مدیریت ایمن فایل

3. **پیامدهای امنیتی را آزمایش کنید**
   - آیا می‌توان از این سوءاستفاده کرد؟
   - بدترین حالت چیست؟
   - آیا موارد لبه‌ای وجود دارد؟
