# انجام commit و push برای همه تغییرات

⚠️ **احتیاط**: همه تغییرات را stage کنید، commit بسازید و به remote push کنید. فقط زمانی از آن استفاده کنید که مطمئن هستید همه تغییرات به هم تعلق دارند.

## گردش کار

### ۱. تحلیل تغییرات
به‌صورت موازی اجرا کنید:
- `git status` - نمایش فایل‌های تغییر‌یافته/افزوده‌شده/حذف‌شده/ردیابی‌نشده
- `git diff --stat` - نمایش آمار تغییرات
- `git log -1 --oneline` - نمایش آخرین commit برای آشنایی با سبک پیام

### ۲. بررسی‌های ایمنی

**❌ در صورت مشاهده موارد زیر متوقف شوید و هشدار دهید:**
- اطلاعات محرمانه: `.env*`، `*.key`، `*.pem`، `credentials.json`، `secrets.yaml`، `id_rsa`، `*.p12`، `*.pfx`، `*.cer`
- کلیدهای API: هر متغیر `*_API_KEY`، `*_SECRET` یا `*_TOKEN` با مقدار واقعی (نه مقدارهای جانگهدار مانند `your-api-key`، `xxx`، `placeholder`)
- فایل‌های حجیم: بزرگ‌تر از `10MB` بدون Git LFS
- خروجی‌های ساخت: `node_modules/`، `dist/`، `build/`، `__pycache__/`، `*.pyc`، `.venv/`
- فایل‌های موقت: `.DS_Store`، `thumbs.db`، `*.swp`، `*.tmp`

**اعتبارسنجی کلید API:**
فایل‌های تغییر‌یافته را برای الگوهایی مانند این بررسی کنید:
```bash
OPENAI_API_KEY=sk-proj-xxxxx  # ❌ کلید واقعی شناسایی شد!
AWS_SECRET_KEY=AKIA...         # ❌ کلید واقعی شناسایی شد!
STRIPE_API_KEY=sk_live_...    # ❌ کلید واقعی شناسایی شد!

# ✅ مقدارهای جانگهدار قابل قبول:
API_KEY=your-api-key-here
SECRET_KEY=placeholder
TOKEN=xxx
API_KEY=<your-key>
SECRET=${YOUR_SECRET}
```

**✅ بررسی کنید:**
- `.gitignore` به‌درستی پیکربندی شده باشد
- هیچ تعارض merge وجود نداشته باشد
- شاخه درست باشد (در صورت main/master هشدار داده شود)
- کلیدهای API فقط مقدار جانگهدار باشند

### ۳. درخواست تأیید

خلاصه را ارائه دهید:
```
📊 خلاصه تغییرات:
- X فایل تغییر‌یافته، Y افزوده‌شده، Z حذف‌شده
- مجموع: +AAA افزوده، -BBB حذف‌شده

🔒 ایمنی: ✅ بدون اطلاعات محرمانه | ✅ بدون فایل حجیم | ⚠️ [هشدارها]
🌿 شاخه: [name] → origin/[name]

این کارها را انجام می‌دهم: git add . → commit → push

برای ادامه «yes» و برای لغو «no» تایپ کنید.
```

**پیش از ادامه، منتظر «yes» صریح بمانید.**

### ۴. اجرا (پس از تأیید)

به‌ترتیب اجرا کنید:
```bash
git add .
git status  # بررسی مرحله‌بندی
```

### ۵. تولید پیام commit

تغییرات را تحلیل کنید و یک conventional commit بسازید:

**قالب:**
```
[type]: خلاصه کوتاه (حداکثر ۷۲ کاراکتر)

- تغییر کلیدی ۱
- تغییر کلیدی ۲
- تغییر کلیدی ۳
```

**انواع:** `feat`، `fix`، `docs`، `style`، `refactor`، `test`، `chore`، `perf`، `build`، `ci`

**مثال:**
```
docs: به‌روزرسانی فایل‌های README مفهوم همراه با مستندات جامع

- افزودن نمودارها و جدول‌های معماری
- گنجاندن مثال‌های کاربردی
- گسترش بخش‌های بهترین شیوه‌ها
```

### ۶. commit و push

```bash
git commit -m "$(cat <<'EOF'
[پیام commit تولیدشده]
EOF
)"
git push  # در صورت شکست: git pull --rebase && git push
git log -1 --oneline --decorate  # بررسی
```

### ۷. تأیید موفقیت

```
✅ با موفقیت به remote push شد!

commit: [hash] [message]
شاخه: [branch] → origin/[branch]
فایل‌های تغییر‌یافته: X (+افزوده، -حذف‌شده)
```

## مدیریت خطاها

- **شکست git add**: مجوزها و فایل‌های قفل‌شده را بررسی کنید و از مقداردهی‌شدن مخزن مطمئن شوید
- **شکست git commit**: هوک‌های pre-commit را اصلاح کنید و پیکربندی git (user.name/email) را بررسی کنید
- **شکست git push**:
  - non-fast-forward: `git pull --rebase && git push`
  - نبود شاخه remote: `git push -u origin [branch]`
  - شاخه محافظت‌شده: به‌جای آن از گردش کار PR استفاده کنید

## زمان استفاده

✅ **مناسب:**
- به‌روزرسانی مستندات در چند فایل
- قابلیت جدید همراه با تست و مستندات
- رفع باگ در چند فایل
- قالب‌بندی/بازسازی در سطح پروژه
- تغییرات پیکربندی

❌ **پرهیز کنید:**
- نامشخص بودن اینکه چه چیزی commit می‌شود
- وجود اطلاعات محرمانه/داده‌های حساس
- شاخه‌های محافظت‌شده بدون بازبینی
- وجود تعارض merge
- تمایل به تاریخچه commit تفکیک‌شده و دقیق
- شکست هوک‌های pre-commit

## جایگزین‌ها

اگر کاربر کنترل بیشتری می‌خواهد، پیشنهاد دهید:
1. **مرحله‌بندی انتخابی**: بازبینی و مرحله‌بندی فایل‌های مشخص
2. **مرحله‌بندی تعاملی**: `git add -p` برای انتخاب patch
3. **گردش کار PR**: ایجاد شاخه → push → PR (از فرمان `/pr` استفاده کنید)

**⚠️ به یاد داشته باشید**: همیشه پیش از push تغییرات را بازبینی کنید. در صورت تردید، از فرمان‌های git به‌صورت جداگانه برای کنترل بیشتر استفاده کنید.
