## مرور کلی

قابلیت‌های پیشرفته در Claude Code قابلیت‌های اصلی را با سازوکارهای برنامه‌ریزی، استدلال، خودکارسازی و کنترل گسترش می‌دهند. این قابلیت‌ها گردش‌کارهای پیچیده‌ای برای وظایف توسعه پیچیده، بازبینی کد، خودکارسازی و مدیریت چندنشستی ممکن می‌کنند.

**قابلیت‌های پیشرفته کلیدی عبارتند از:**
- **حالت برنامه‌ریزی**: ساخت برنامه‌های پیاده‌سازی دقیق پیش از کدنویسی
- **تفکر گسترده**: استدلال عمیق برای مسائل پیچیده
- **حالت خودکار**: طبقه‌بند ایمنی پس‌زمینه هر اقدام را پیش از اجرا بازبینی می‌کند
- **وظایف پس‌زمینه**: اجرای عملیات طولانی بدون مسدود کردن گفتگو
- **حالت‌های مجوز**: کنترل اینکه Claude چه کاری می‌تواند انجام دهد (`manual` — پیش‌تر `default`، `acceptEdits`، `plan`، `auto`، `dontAsk`، `bypassPermissions`)
- **حالت چاپ**: اجرای غیرتعاملی Claude Code برای خودکارسازی و CI/CD (`claude -p`)
- **مدیریت نشست**: مدیریت چندین نشست کاری
- **قابلیت‌های تعاملی**: میان‌برهای صفحه‌کلید، ورودی چندخطی و تاریخچه فرمان‌ها
- **دیکته صوتی**: ورودی صوتی با فشار برای صحبت، با پشتیبانی STT در ۲۰ زبان
- **کانال‌ها**: سرورهای MCP پیام‌ها را به نشست‌های در حال اجرا تزریق می‌کنند (پیش‌نمایش پژوهشی)
- **کنترل از راه دور**: کنترل Claude Code از Claude.ai یا اپلیکیشن Claude
- **نشست‌های وب**: اجرای Claude Code در مرورگر در claude.ai/code
- **اپلیکیشن دسکتاپ**: اپلیکیشن مستقل برای بازبینی بصری تفاوت‌ها و چندین نشست
- **فهرست وظایف**: پیگیری پایدار وظایف در طول فشرده‌سازی‌های زمینه
- **پیشنهادهای پرامپت**: پیشنهادهای هوشمند فرمان بر اساس زمینه
- **درخت‌های کاری Git**: شاخه‌های درخت کاری جداشده برای کار موازی
- **سندباکس**: جداسازی فایل‌سیستم و شبکه در سطح سیستم‌عامل
- **تنظیمات مدیریت‌شده**: استقرار سازمانی از طریق plist، رجیستری یا فایل‌های مدیریت‌شده
- **پیکربندی**: سفارشی‌سازی رفتار با فایل‌های پیکربندی JSON

## حالت برنامه‌ریزی

حالت برنامه‌ریزی به Claude اجازه می‌دهد پیش از پیاده‌سازی، وظایف پیچیده را به‌طور کامل بررسی کند و برنامه‌ای دقیق بسازد که شما بتوانید آن را بازبینی و تأیید کنید.

### حالت برنامه‌ریزی چیست؟

حالت برنامه‌ریزی یک رویکرد دومرحله‌ای است:
1. **مرحله برنامه‌ریزی**: Claude وظیفه را تحلیل می‌کند و یک برنامه پیاده‌سازی دقیق می‌سازد
2. **مرحله پیاده‌سازی**: پس از تأیید، Claude برنامه را اجرا می‌کند

### چه زمانی از حالت برنامه‌ریزی استفاده کنیم

✅ از حالت برنامه‌ریزی استفاده کنید برای:
- ری‌فاکتور پیچیده چندفایلی
- پیاده‌سازی قابلیت‌های جدید
- تغییرات معماری
- مهاجرت پایگاه داده
- بازطراحی‌های عمده API

❌ از حالت برنامه‌ریزی استفاده نکنید برای:
- رفع باگ‌های ساده
- تغییرات قالب‌بندی
- ویرایش تک‌فایلی
- پرسش‌های سریع

### فعال‌سازی حالت برنامه‌ریزی

**دستور اسلش**:
```bash
/plan پیاده‌سازی سیستم احراز هویت کاربر
```

**پرچم CLI**:
```bash
claude --permission-mode plan
```

**تنظیم به‌عنوان پیش‌فرض**:
```json
{
  "permissions": {
    "defaultMode": "plan"
  }
}
```

**میان‌بر صفحه‌کلید**:
- `Shift + Tab` - جابه‌جایی میان حالت‌های مجوز (شامل plan)
- `Alt + M` - جابه‌جایی میان حالت‌های مجوز (فقط ویندوز، زمانی که رانتایم حالت ورودی VT را فعال نکرده باشد)

### مزایای حالت برنامه‌ریزی

- **رویکرد پیاده‌سازی ساختاریافته**: شکست دقیق مراحل پیاده‌سازی
- **بازبینی و تأیید**: تأیید یا تنظیم برنامه پیش از اجرا
- **شناسایی ریسک**: شناسایی مسائل احتمالی پیش از پیاده‌سازی
- **مراحل شفاف**: مراحل و نقاط عطف سازمان‌یافته پیاده‌سازی

### مثال: پیاده‌سازی یک قابلیت

```
کاربر: /plan یک سیستم اعلان بی‌درنگ اضافه کن

Claude: برنامه‌ای برای پیاده‌سازی اعلان‌های بی‌درنگ می‌سازم.

### مرحله ۱: راه‌اندازی زیرساخت

2. راه‌اندازی سرور WebSocket
3. پیکربندی مدیریت اتصال

### مرحله ۲: پیاده‌سازی بک‌اند

5. پیاده‌سازی صف اعلان
6. افزودن طرح‌واره پایگاه داده برای اعلان‌ها
7. ساخت نقاط پایانی API

### مرحله ۳: یکپارچه‌سازی فرانت‌اند
8. راه‌اندازی کلاینت WebSocket
9. ساخت اجزای رابط اعلان
10. پیاده‌سازی مدیریت وضعیت اعلان
11. افزودن مجوزهای اعلان

### مرحله ۴: آزمون و استقرار
12. نوشتن تست‌های واحد
13. نوشتن تست‌های یکپارچه‌سازی
14. به‌روزرسانی مستندات
15. استقرار در محیط آزمایشی

زمان تخمینی: ۳ تا ۴ ساعت
فایل‌هایی که تغییر می‌کنند: ۱۲
فایل‌های جدیدی که ساخته می‌شوند: ۸

آماده ادامه هستید؟ (بله/خیر/اصلاح برنامه)

کاربر: بله

```

### اصلاح برنامه

```
کاربر: برنامه را اصلاح کن - فعلاً از صف صرف‌نظر کن، بعداً اضافه‌اش می‌کنیم

Claude: برنامه به‌روزشده:
[برنامه اصلاح‌شده با صف حذف‌شده را نشان می‌دهد]

کاربر: خوب به نظر می‌رسد، ادامه بده

Claude: [برنامه اصلاح‌شده را پیاده‌سازی می‌کند]
```

### پیکربندی حالت برنامه‌ریزی

حالت برنامه‌ریزی از طریق پرچم CLI یا دستور اسلش فعال می‌شود:

```bash
# فعال‌سازی حالت برنامه از طریق CLI
claude --permission-mode plan

# یا استفاده از دستور اسلش /plan درون REPL
/plan پیاده‌سازی سیستم احراز هویت کاربر
```

**نام مستعار مدل برای برنامه‌ریزی**: از `opusplan` به‌عنوان نام مستعار مدل استفاده کنید تا Opus برای برنامه‌ریزی و Sonnet برای اجرا به کار رود:

```bash
claude --model opusplan "طراحی و پیاده‌سازی API جدید"
```

**ویرایش برنامه به‌صورت بیرونی**: `Ctrl+G` را فشار دهید تا برنامه جاری برای اصلاحات دقیق در ویرایشگر بیرونی شما باز شود.

> **به‌روزرسانی v2.1.112**: فایل‌های برنامه اکنون به نام پرامپتی که آن‌ها را تولید کرده نام‌گذاری می‌شوند (به‌جای واژه‌های تصادفی)، که مرور و استفاده مجدد از آن‌ها را آسان‌تر می‌کند.

> **به‌روزرسانی v2.1.136 — مسدودسازی نوشتن در حالت برنامه بی‌قید و شرط است**: حالت برنامه اکنون همه نوشتن‌های فایل را مسدود می‌کند، از جمله زمانی که یک قاعده `Edit(...)` منطبق در `permissions.allow` وجود دارد. پیش‌تر یک قاعده سهل‌گیرانه `Edit(...)` می‌توانست نوشتن‌ها را در حالت برنامه عبور دهد؛ آن راه فرار بسته شده است. اگر گردش‌کاری به رفتار قدیمی وابسته بود، پیش از ویرایش از حالت برنامه خارج شوید (`Shift+Tab`).

## تفکر گسترده

تفکر گسترده به Claude اجازه می‌دهد پیش از ارائه راه‌حل، زمان بیشتری را صرف استدلال درباره مسائل پیچیده کند.

### تفکر گسترده چیست؟

تفکر گسترده یک فرایند استدلال آگاهانه و گام‌به‌گام است که در آن Claude:
- مسائل پیچیده را تجزیه می‌کند
- رویکردهای متعدد را در نظر می‌گیرد
- موازنه‌ها را ارزیابی می‌کند
- حالت‌های حاشیه‌ای را استدلال می‌کند

### فعال‌سازی تفکر گسترده

**میان‌بر صفحه‌کلید**:
- `Option + T` (مک) / `Alt + T` (ویندوز/لینوکس) - جابه‌جایی تفکر گسترده. روی Opus 5.5 (مدل پیش‌فرض از v2.1.280)، Sonnet 5.5، Haiku 5.5 و مدل‌های Fable، تفکر نمی‌تواند خاموش شود — کلید جابه‌جایی، `alwaysThinkingEnabled` و `MAX_THINKING_TOKENS=0` روی آن‌ها اثری ندارند.

**فعال‌سازی خودکار**:
- به‌طور پیش‌فرض برای همه مدل‌ها فعال است (Opus 5، Opus 4.8، Opus 4.7، Sonnet 4.6، Haiku 4.5)
- Opus 5 / Opus 4.8: استدلال تطبیقی با سطوح تلاش: `low` (○)، `medium` (◐)، `high` (●)، `xhigh`، `max`. پیش‌فرض `medium` روی Opus 5.5 (مدل پیش‌فرض از v2.1.280)، Sonnet 5.5 و Haiku 5.5، `high` روی Opus 5 (v2.1.219)، Sonnet 5، Opus 4.8 (v2.1.154)، Opus 4.6 و Sonnet 4.6، و `xhigh` روی Opus 4.7 است. `xhigh` روی Opus 5.5، Sonnet 5.5، Haiku 5.5، Opus 5، Sonnet 5، Opus 4.8 و Opus 4.7 در دسترس است (روی Opus 4.6 / Sonnet 4.6 به `high` برمی‌گردد). `max` روی Opus 5.5، Sonnet 5.5، Haiku 5.5، Opus 5، Sonnet 5 و Opus 4.8/4.7/4.6 و Sonnet 4.6 کار می‌کند (فقط همان نشست). Haiku 4.5 هیچ سطح تلاشی ندارد. Opus 5، Opus 4.8 و Opus 4.7 یک پنجره زمینه بومی ۱ میلیون توکنی دارند (اصلاح زمینه ۱M در v2.1.117 اعمال شد — پیش از آن، `/context` پنجره Opus 4.7 را ۲۰۰K اشتباه می‌شمرد و فشرده‌سازی خودکار زودهنگام را راه می‌انداخت). از v2.1.129، `/context` تجسم خود را فقط درون رابط کاربری نشان می‌دهد؛ تجسم ASCII دیگر به زمینه گفتگو نشت نمی‌کند (حدود ۱.۶ هزار توکن صرفه‌جویی در هر فراخوانی)، بنابراین فراخوانی `/context` آزادانه بی‌خطر است.
- مشترکان Pro/Max روی Opus 4.6 / Sonnet 4.6: تلاش پیش‌فرض در v2.1.117 از `medium` به `high` افزایش یافت.
- سایر مدل‌ها: بودجه ثابت تا ۳۱٬۹۹۹ توکن

**روش‌های پیکربندی**:
- جابه‌جایی: `Alt+T` / `Option+T`، یا از طریق `/config`
- مشاهده استدلال: `Ctrl+O` (حالت پرمخاطب)
- تنظیم تلاش: فرمان `/effort` یا پرچم `--effort`

**بودجه سفارشی**:
```bash
export MAX_THINKING_TOKENS=1024
```

**سطح تلاش** (پشتیبانی‌شده روی Opus 5.5، Sonnet 5.5، Haiku 5.5، Opus 5، Sonnet 5، Opus 4.8، Opus 4.7، Opus 4.6 و Sonnet 4.6 — نه Haiku 4.5):
```bash
export CLAUDE_CODE_EFFORT_LEVEL=high   # low (○)، medium (◐)، high (●)، xhigh (Opus 5.5، Sonnet 5.5، Haiku 5.5، Opus 5، Sonnet 5، Opus 4.8/4.7)، یا max — پیش‌فرض روی Opus 5 و Opus 4.8 برابر high است
```

**پرچم CLI**:
```bash
claude --effort high "بازبینی پیچیده معماری"
```

**دستور اسلش**:
```
/effort high
```

> **نکته:** کلیدواژه «ultrathink» در پرامپت‌ها حالت استدلال عمیق را فعال می‌کند. سطوح تلاش `low`، `medium`، `high` و `max` روی Opus 5.5، Sonnet 5.5، Haiku 5.5، Opus 5، Sonnet 5، Opus 4.8، Opus 4.7، Opus 4.6 و Sonnet 4.6 پشتیبانی می‌شوند (Haiku 4.5 هیچ‌کدام را ندارد). `xhigh` روی Opus 5.5، Sonnet 5.5، Haiku 5.5، Opus 5، Sonnet 5، Opus 4.8 و Opus 4.7 در دسترس است. تلاش پیش‌فرض روی Opus 5.5، Sonnet 5.5 و Haiku 5.5 برابر `medium`، روی Opus 5، Sonnet 5، Opus 4.8 (و Opus 4.6 / Sonnet 4.6) برابر `high` و روی Opus 4.7 برابر `xhigh` است. برخلاف Opus 4.8 و Opus 4.7 که تلاش پیش‌فرض خود را در نخستین اجرا ثابت می‌کنند، Opus 5 چنین قفلی ندارد — سطحی که پیش‌تر تنظیم کرده‌اید باقی می‌ماند. لغزنده `/effort` همچنین یک کلید **Ultracode** دارد (Tab، یا `/effort ultracode [on|off]`)، که **نه** یک سطح تلاش مدل است — با آن، Claude گردش‌کارهای پویا را در همان سطح تلاشی که نشست در آن اجرا می‌شود هماهنگ می‌کند. از v2.1.284 دیگر `xhigh` را تحمیل نمی‌کند و با تغییر سطح روشن می‌ماند؛ `--effort ultracode` و `effortLevel: "ultracode"` در Agent SDK همچنان `xhigh` را تنظیم می‌کنند.

### بازگشت طبقه‌بند ایمنی روی Opus 5

جدا از تنظیم [`fallbackModel`](#مدل‌های-جایگزین-fallbackmodel) (که اضافه‌بار و در دسترس نبودن را مدیریت می‌کند)، Claude Code زمانی که یک طبقه‌بند ایمنی درخواستی را علامت بزند، یک **بازگشت دسته‌محور** اعمال می‌کند. این به Claude Code نسخه v2.1.219 یا بالاتر نیاز دارد.

- **Opus 5**: درخواست‌های علامت‌خورده در حوزه امنیت سایبری روی Opus 4.8 دوباره اجرا می‌شوند. درخواست‌های علامت‌خورده در حوزه زیست‌شناسی به‌جایش با امتناع پایان می‌یابند، چون Opus 5 طبقه‌بندهای زیست‌شناسی خودش را بدون مدل بازگشتی اجرا می‌کند. این امتناع‌ها از همان نخستین درخواست علامت‌خورده دریافت می‌شوند.
- بارهای کاری در امنیت تهاجمی یا زیست‌شناسی — آزمون نفوذ، تمرین‌های Capture the Flag (CTF) و پایگاه‌های کد نزدیک به زیست‌شناسی — مرتباً بازگشت را فعال می‌کنند، اغلب در نخستین درخواست.

چرا اینجا مهم است: اگر [زیرایجنت‌های security-review](../04-subagents/README.md) یا کار CTF/pentest را روی Opus 5 اجرا می‌کنید، انتظار اجرای مجدد بی‌صدا روی Opus 4.8 (با سقف تلاش و پنجره زمینه متفاوت) برای پرامپت‌های امنیت سایبری، و امتناع صریح برای موارد نزدیک به زیست‌شناسی را داشته باشید. اگر این رفتار مانع کار شد، مدل دیگری را صریحاً پین کنید.

**کنترل این جابه‌جایی** — تنظیم `switchModelsOnFlag` (v2.1.170+، پیش‌فرض `true`) تعیین می‌کند که آیا بازگشت بی‌صدا انجام می‌شود یا نه. آن را `false` کنید و Claude Code به‌جایش توقف می‌کند و به شما اجازه می‌دهد میان تغییر مدل و ویرایش پرامپت انتخاب کنید. در `/config` به‌صورت **Switch models when a message is flagged** ظاهر می‌شود.

```json
{
  "switchModelsOnFlag": false
}
```

## حالت خودکار

حالت خودکار یک حالت مجوز است که از یک طبقه‌بند ایمنی پس‌زمینه برای بررسی هر اقدام پیش از اجرا استفاده می‌کند. این حالت به Claude اجازه می‌دهد به‌صورت خودمختار کار کند و در همان حال عملیات خطرناک را مسدود می‌کند. روی همه پلن‌ها در دسترس است، اما به مدلی واجد شرایط نیاز دارد (Claude Opus 4.6 یا جدیدتر، Sonnet 4.6 یا جدیدتر، Haiku 5.5، یا یک مدل Fable روی Anthropic API و Claude Platform on AWS؛ Sonnet 5 یا جدیدتر، Opus 4.7 یا جدیدتر، Haiku 5.5، یا یک مدل Fable روی Bedrock، Vertex، Foundry و نشست‌های gateway برنامه‌های Claude که وارد شده‌اند). در Team و Enterprise به‌صورت پیش‌فرض روشن است — مدیران می‌توانند آن را برای سازمان در تنظیمات مدیریت‌شده خاموش کنند.

### پیش‌نیازها

حالت خودکار تنها زمانی در دسترس است که حساب شما همه این پیش‌نیازها را برآورده کند:

- **پلن**: همه پلن‌ها.
- **سازمان**: در Team و Enterprise، حالت خودکار به‌صورت پیش‌فرض در دسترس است. مدیران می‌توانند آن را برای سازمان با تنظیم `permissions.disableAutoMode` روی `"disable"` در تنظیمات مدیریت‌شده خاموش کنند.
- **مدل**: روی Anthropic API و Claude Platform on AWS — Claude Opus 4.6 یا جدیدتر، Sonnet 4.6 یا جدیدتر، Haiku 5.5، یا یک مدل Fable. روی Amazon Bedrock، Agent Platform گوگل Claude (Vertex AI)، Microsoft Foundry و نشست‌های gateway برنامه‌های Claude که وارد شده‌اند — تنها Claude Sonnet 5 یا جدیدتر، Opus 4.7 یا جدیدتر، Haiku 5.5 (v2.1.293+) و مدل‌های Fable. مدل‌های قدیمی‌تر — Sonnet 4.5، Opus 4.5، Haiku 4.5 و مدل‌های claude-3 — روی هیچ ارائه‌دهنده‌ای پشتیبانی نمی‌شوند.
- **ارائه‌دهنده**: به‌صورت پیش‌فرض روی Anthropic API، Claude Platform on AWS، Amazon Bedrock، Agent Platform گوگل Claude (Vertex AI)، Microsoft Foundry و نشست‌های gateway برنامه‌های Claude که وارد شده‌اند در دسترس است. در v2.1.158 تا v2.1.206، حالت خودکار روی همه این‌ها به‌جز Anthropic API و Claude Platform on AWS خاموش بود تا زمانی که `CLAUDE_CODE_ENABLE_AUTO_MODE=1` را تنظیم می‌کردید؛ v2.1.207 آن الزام را حذف کرد. این متغیر هنوز برای سازگاری پذیرفته می‌شود و از v2.1.207 به بعد اثری ندارد.
- **طبقه‌بند**: هزینه توکن اضافی دارد، به‌جز در پلن‌های Enterprise و حساب‌های Claude API که v2.1.278+ بررسی را سمت سرور و بدون هزینه اجرا می‌کند

### پیکربندی حالت خودکار

**چاپ قواعد پیش‌فرض به‌صورت JSON**:
```bash
claude auto-mode defaults
```

**بازگرداندن پیکربندی پیش‌فرض حالت خودکار** (v2.1.212)، با یک پرامپت تأیید (`--yes` برای رد کردن آن):
```bash
claude auto-mode reset
claude auto-mode reset --yes
```

**پیکربندی زیرساخت مورد اعتماد** از طریق تنظیم مدیریت‌شده `autoMode.environment` برای استقرارهای سازمانی. این به مدیران اجازه می‌دهد محیط‌های CI/CD مورد اعتماد، اهداف استقرار و الگوهای زیرساخت را تعریف کنند.

#### گسترش پیش‌فرض‌ها با `"$defaults"` (v2.1.118)

از v2.1.118، `autoMode.allow`، `autoMode.soft_deny` و `autoMode.environment` یک توکن `"$defaults"` می‌پذیرند که قواعد شما را به فهرست داخلی **می‌افزاید** به‌جای جایگزینی آن. پیش از v2.1.118، هر آرایه تعریف‌شده توسط کاربر بی‌صدا موارد داخلی را بازنویسی می‌کرد.

#### مسدودی‌های بی‌قید و شرط با `autoMode.hard_deny` (v2.1.136)

`autoMode.hard_deny` (v2.1.136+) آرایه‌ای از قواعد طبقه‌بند است که یک دسته از اقدامات را **بدون توجه به قصد استنباط‌شده کاربر** مسدود می‌کند. از این برای اقداماتی استفاده کنید که هرگز نباید در حالت خودکار اجرا شوند — برای مثال `rm -rf` روی مسیرهای ریشه یا `git push --force` روی شاخه‌های محافظت‌شده. برخلاف `soft_deny`، قواعد hard-deny با طبقه‌بند قابل مذاکره نیستند.

```json
{
  "autoMode": {
    "hard_deny": ["Bash(rm -rf /:*)", "Bash(git push --force*)"]
  }
}
```

**پیش از این (جایگزین موارد داخلی — رفتار پیش از v2.1.118):**

```json
{
  "autoMode": {
    "allow": ["Bash(gh pr list:*)"]
  }
}
```

**پس از این (توسعه موارد داخلی — v2.1.118+):**

```json
{
  "autoMode": {
    "allow": ["$defaults", "Bash(gh pr list:*)"],
    "soft_deny": ["$defaults", "Bash(kubectl delete:*)"],
    "environment": ["$defaults", "trusted-ci.internal"]
  }
}
```

از `"$defaults"` استفاده کنید تا قواعد پایه ارائه‌شده حفظ شوند و افزوده‌های مخصوص سازمان یا پروژه روی آن‌ها لایه‌بندی شود.

#### طبقه‌بندی هر دستور شل با `autoMode.classifyAllShell` (v2.1.193)

`autoMode.classifyAllShell` (بولین، v2.1.193+) **همه** دستورهای Bash/PowerShell را از طبقه‌بند حالت خودکار عبور می‌دهد. آن را فعال کنید وقتی می‌خواهید طبقه‌بند هر دستور شل در نشست را بررسی کند.

```json
{
  "autoMode": {
    "classifyAllShell": true
  }
}
```

همین نسخه یک **دلیل رد** را هنگام مسدود کردن یک اقدام توسط حالت خودکار نشان می‌دهد — قابل مشاهده در ترنسکریپت، اعلان رد، و فهرست اخیراً رد‌شده زیر `/permissions` (v2.1.193+).

#### محافظت درونی مبتنی بر قصد (v2.1.183)

جدا از `hard_deny` پیکربندی‌شده توسط کاربر، حالت خودکار دستورهای مخرب زیر را به‌طور پیش‌فرض مسدود می‌کند مگر اینکه در این نشست صریحاً درخواستشان کرده باشید:

- `git reset --hard`، `git checkout -- .`، `git clean -fd`، `git stash drop`
- `git commit --amend` (وقتی کامیت توسط ایجنت در این نشست انجام نشده باشد)
- `terraform destroy`، `pulumi destroy`، `cdk destroy` (مگر اینکه استک مشخصی را درخواست کرده باشید)

این یک محافظت پیش‌فرض درونی است که با قصد استنباط‌شده هدایت می‌شود — لازم نیست خودتان این‌ها را به `hard_deny` اضافه کنید.

### رفتار بازگشتی

وقتی طبقه‌بند مطمئن نیست، حالت خودکار به پرسش از کاربر بازمی‌گردد:
- پس از **۳ مسدودی متوالی** طبقه‌بند
- پس از **۲۰ مسدودی کل** طبقه‌بند در یک نشست

این تضمین می‌کند که کاربر همیشه کنترل را در دست دارد وقتی طبقه‌بند نمی‌تواند با اطمینان یک اقدام را تأیید کند.

### ایجاد مجوزهای معادل حالت خودکار

اگر رویکرد ساده‌تری بدون طبقه‌بند پس‌زمینه می‌خواهید، می‌توانید `~/.claude/settings.json` خود را با یک خط پایه محافظه‌کارانه از قواعد مجوز ایمن پر کنید. اسکریپت با قواعد فقط‌خواندنی و بازرسی محلی شروع می‌کند، سپس به شما اجازه می‌دهد تنها زمانی که می‌خواهید ویرایش‌ها، تست‌ها، نوشتن‌های محلی git، نصب بسته‌ها و اقدامات نوشتن GitHub را فعال کنید.

**فایل:** `09-advanced-features/setup-auto-mode-permissions.py`

```bash

# افزودن قابلیت بیشتر تنها زمانی که به آن نیاز دارید
```

## وظایف پس‌زمینه

وظایف پس‌زمینه اجازه می‌دهند عملیات طولانی‌مدت بدون مسدود کردن گفت‌وگوی شما اجرا شوند.

### وظایف پس‌زمینه چیست؟

وظایف پس‌زمینه به‌صورت ناهمگام اجرا می‌شوند در حالی که شما به کار ادامه می‌دهید:
- مجموعه‌تست‌های طولانی
- فرآیندهای ساخت
- مهاجرت‌های پایگاه داده
- اسکریپت‌های استقرار
- ابزارهای تحلیل

**استفاده پایه:**
```bash
User: Run tests in background

Claude: Started task bg-1234

/tasks    # مشاهده و مدیریت کارهای پس‌زمینه (شل‌ها و زیرایجنت‌ها)؛ توقف یک وظیفه از همین‌جا
Ctrl+B    # انتقال یک دستور Bash در حال اجرا یا یک ایجنت به پس‌زمینه
```

### شروع وظایف پس‌زمینه

```
User: Run the full test suite in the background

Claude: Starting tests in background (task-id: bg-1234)
You can continue working while tests run.

[You can continue the conversation]

User: Meanwhile, let's refactor the auth module

Claude: [Works on auth module while tests run in background]

[Later, when tests complete]

Claude: 📢 Background task bg-1234 completed:
✅ 245 tests passed
❌ 3 tests failed
View results: /tasks
```

### مدیریت وظایف پس‌زمینه

برای فهرست کردن شل‌ها و زیرایجنت‌های در حال اجرا، باز کردن یکی برای دیدن خروجی آن، یا توقف آن، `/tasks` (نام مستعار `/bashes`) را اجرا کنید. هیچ زیردستور `/task` وجود ندارد.

```text
User: /tasks

[Opens the background-work view: running shells and subagents,
 including subagents that have finished. Select one to see its
 output, or stop it from here.]
```

```

User: While those run, let's implement the new API endpoint

Claude: [Implements API endpoint while build and linter run]
```

### پیکربندی

هیچ بلوک `settings.json` برای وظایف پس‌زمینه وجود ندارد. این ویژگی با یک متغیر محیطی کنترل می‌شود:

```bash
# خاموش کردن اجراهای پس‌زمینهٔ Bash/زیرایجنت و Ctrl+B (taskهای MCP و ابزار Monitor هنوز در پس‌زمینه اجرا می‌شوند)
export CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1
```

> **دسترس‌پذیری (v2.1.310)**: روی Amazon Bedrock، Claude Platform on AWS، Agent Platform گوگل کلاد یا Microsoft Foundry، یا با `DISABLE_TELEMETRY` یا `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` تنظیم‌شده، Monitor به Claude Code نسخهٔ v2.1.310 یا بالاتر نیاز دارد. روی Windows به Git Bash نیاز دارد.

هم‌زمانی نیز تنظیم وظیفه پس‌زمینه نیست — تعداد ایجنت‌هایی که هم‌زمان اجرا می‌شوند توسط `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (پیش‌فرض `20`) کنترل می‌شود.

دستورهای Bash و PowerShell پس‌زمینه فقط در نشست‌های بدون نظارت محدودیت زمانی دارند (v2.1.288): در یک اجرای `-p`، یک نشست Agent SDK، CI یا نشست ابری، دستوری که با `run_in_background` شروع شده پس از `timeout` خود متوقف می‌شود — به‌طور پیش‌فرض ۳۰ دقیقه، حداکثر ۲ ساعت — و Claude هنگام توقف یکی مطلع می‌شود. دستورهای پس‌زمینه در ترمینال، برنامه دسکتاپ یا نشست VS Code محدودیت زمانی ندارند (در v2.1.285–v2.1.287 این محدودیت برای همه نشست‌ها اعمال می‌شد).

## ابزار Monitor (جریان‌های رویدادمحور)

> **جدید در v2.1.98**: ابزار Monitor به Claude اجازه می‌دهد stdout یک دستور پس‌زمینه را زیر نظر بگیرد و همان لحظه‌ای که رویداد منطبقی ظاهر می‌شود واکنش نشان دهد — جایگزین حلقه‌های نظرسنجی و `sleep` برای انتظار روی فرآیندهای طولانی‌مدت.

Monitor به هر دستور شلی که در stdout می‌نویسد متصل می‌شود. هر خط stdout از دستور به یک اعلان تبدیل می‌شود که نشست را بیدار می‌کند. Claude دستور را مشخص می‌کند؛ هارنس خروجی را جریان می‌دهد و رویدادها را هنگام وقوع تحویل می‌دهد. برای راه‌اندازی فرآیندهای زیرین، بخش مرتبط [وظایف پس‌زمینه](#وظایف-پس‌زمینه) را ببینید.

> **مهلت‌ها (v2.1.271)**: هر دیده‌بان Monitor اکنون یک مهلت دارد — حداکثر ۳۰ دقیقه، یا ۱۰ دقیقه در اجراهای تک‌پرامپتی `-p`. وقتی مهلت بگذرد، Claude مطلع می‌شود تا بتواند دیده‌بان را دوباره مسلح کند. دیگر راهی برای مسلح کردن دیده‌بانی که هرگز منقضی نشود وجود ندارد.

### چرا اهمیت دارد

نظرسنجی با `/loop` یا `sleep` در هر چرخه یک رفت‌وبرگشت کامل API مصرف می‌کند، چه چیزی تغییر کرده باشد چه نه. Monitor تا وقوع یک رویداد ساکت می‌ماند و در زمان سکوت دستور **صفر توکن** مصرف می‌کند. وقتی رویدادی رخ می‌دهد، Claude فوراً واکنش نشان می‌دهد — بدون کشف تأخیری در انتظار تیک نظرسنجی بعدی. برای هر چیزی که بیش از چند دقیقه اجرا می‌شود، این هم ارزان‌تر و هم سریع‌تر از حلقه‌های نظرسنجی است.

### دو الگوی رایج

**فیلترهای جریان** خروجی پیوسته یک منبع طولانی‌مدت را زیر نظر می‌گیرند. دستور برای همیشه اجرا می‌شود؛ هر خط منطبق یک رویداد است.

```bash
tail -f /var/log/app.log | grep --line-buffered "ERROR"
```

**فیلترهای نظرسنجی و انتشار** یک منبع را دوره‌ای بررسی می‌کنند و تنها زمانی انتشار می‌دهند که چیزی تغییر کند. از این برای APIها، پایگاه‌های داده یا هر چیزی که جریان بومی ندارد استفاده کنید.

```bash
last=$(date -u +%Y-%m-%dT%H:%M:%SZ)
while true; do
  gh api "repos/owner/repo/issues/123/comments?since=$last" || true
  last=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  sleep 30
done
```

### نمونهٔ عملی

«سرور توسعه‌ام را اجرا کن و آن را برای خطاها پایش کن.» Claude سرور را به‌عنوان یک وظیفهٔ پس‌زمینه اجرا می‌کند، یک فیلتر Monitor وصل می‌کند (`tail -F server.log | grep --line-buffered -E "ERROR|FATAL"`) و نشست بی‌صدا می‌شود. همان لحظه که یک خط خطا در لاگ ظاهر شود، Claude بیدار می‌شود، خطا را می‌خواند و می‌تواند واکنش نشان دهد — سرور را دوباره راه‌اندازی کند، باگ را رفع کند، یا آن را به شما نشان دهد — بدون اینکه لازم باشد شما سر بزنید.

> **هشدار**: هنگام لوله‌کردن به `grep`، **همیشه** از `grep --line-buffered` استفاده کنید. بدون آن، grep خروجی استاندارد را در بلوک‌های ۴ کیلوبایتی بافر می‌کند که می‌تواند رویدادها را در جریان‌های کم‌ترافیک چند دقیقه به تأخیر بیندازد. این رایج‌ترین راهی است که Monitor در عمل خراب می‌شود — اگر فیلتر شما بی‌دلیل ساکت به نظر می‌رسد، اول پرچم `--line-buffered` را بررسی کنید.

## گردش‌کارهای پویا

> **جدید در v2.1.154**

گردش‌کارهای پویا به Claude اجازه می‌دهند ده‌ها تا صدها [زیرایجنت](../04-subagents/README.md) پس‌زمینه را **به‌صورت قطعی** ارکستراسیون کند — پخش‌شعاعی، خطوط لوله و مراحل موازی که در یک اسکریپت کدگذاری می‌شوند، نه اینکه به بداهه‌پردازی مدل واگذار شوند. جایی که یک ایجنت یک پنجرهٔ زمینه دارد، یک گردش‌کار وظیفه را میان بسیاری از ایجنت‌ها تجزیه می‌کند و نتایجشان را دوباره ترکیب می‌کند.

از v2.1.219، گردش‌کارهای پویا به‌طور پیش‌فرض از **راهنمای اندازهٔ متوسط (هدف: کمتر از ۱۰ ایجنت)** استفاده می‌کنند — یا از v2.1.271، وقتی با طرح Pro وارد شده‌اید، از **کوچک**. اندازهٔ دیگری — یا بدون محدودیت — را از طریق **Dynamic workflow size** در `/config` انتخاب کنید، یا کلید `workflowSizeGuideline` را در فایل تنظیمات خود قرار دهید. خط وضعیت گردش‌کار در حال اجرا اندازهٔ فعال را نشان می‌دهد و برای تغییر آن به `/config` اشاره می‌کند.

### چه زمانی از آن‌ها استفاده کنیم

- **پوشش جامع** — ممیزی یا مرور در بسیاری از فایل‌ها/ابعاد به‌صورت موازی.
- **اطمینان** — تولید دیدگاه‌های مستقل، سپس راستی‌آزمایی خصمانهٔ یافته‌ها پیش از ثبت نهایی.
- **مقیاسی فراتر از یک زمینه** — مهاجرت‌های بزرگ، جاروب‌های گسترده، یا پژوهشی که هیچ زمینهٔ واحدی نمی‌تواند در خود جای دهد.

برای یک وظیفهٔ یک‌باره که خودتان آن را می‌فهمید، یک ایجنت واحد (یا یک ویرایش مستقیم) هنوز ابزار درست است — گردش‌کارها وقتی ارزش خود را نشان می‌دهند که کار پخش‌شعاعی می‌شود.

### اجرا و مشاهده

- **اجرا**: از Claude بخواهید برای وظیفه یک گردش‌کار بسازد (مثلاً «یک گردش‌کار اجرا کن تا هر فایل در `src/` را مرور کند»). Claude اسکریپت ارکستراسیون را می‌نویسد و آن را در پس‌زمینه اجرا می‌کند.
- **مشاهده**: دستور `/workflows` اجراهای در حال انجام و تکمیل‌شدهٔ گردش‌کار را با پیشرفت زنده نشان می‌دهد.
- **`ultracode`**: آن را با کلید Ultracode در اسلایدر `/effort` (Tab) یا با `/effort ultracode [on|off]` روشن کنید — Claude سپس به‌طور پیش‌فرض گردش‌کارهای پویا را ارکستراسیون می‌کند، در همان سطح تلاشی که نشست با آن اجرا می‌شود. از v2.1.284 این کلید سطح تلاش را تغییر نمی‌دهد (پیش‌تر `xhigh` را اجباری می‌کرد)؛ `--effort ultracode` و `effortLevel: "ultracode"` در Agent SDK همچنان `xhigh` را تنظیم می‌کنند. `/effort ultracode` تا پایان نشست دوام دارد؛ کلید `ultracode` را در تنظیمات قرار دهید تا هر نشست با آن آغاز شود (`effortLevel` و `CLAUDE_CODE_EFFORT_LEVEL` مقدار `ultracode` را نمی‌پذیرند). (از v2.1.160 کلیدواژهٔ محرک `ultracode` است؛ واژهٔ خالی «workflow» دیگر اجرایی را راه نمی‌اندازد.)

گردش‌کارها بر مدل زیرایجنت بنا شده‌اند — برای اینکه ایجنت‌های منفرد چگونه تعریف و محدود می‌شوند، [زیرایجنت‌ها](../04-subagents/README.md) را ببینید.

## وظایف زمان‌بندی‌شده

وظایف زمان‌بندی‌شده به شما امکان می‌دهند پرامپت‌ها را به‌صورت خودکار روی یک زمان‌بندی تکرارشونده یا به‌عنوان یادآورهای یک‌باره اجرا کنید. وظایف محدود به نشست هستند — تا وقتی Claude Code فعال است اجرا می‌شوند و با پایان نشست پاک می‌شوند. از v2.1.72+ در دسترس است.

> **«Routines» اکنون «cloud scheduled tasks» است (اکتبر ۲۰۲۶)**: مستندات Anthropic نام Routines — وظایف ابری‌ای که با `/schedule` می‌سازید (نام مستعار `/routines`؛ پایین را ببینید) — را به **cloud scheduled tasks (سابقاً routines)** تغییر داده و وظایف `/loop` و cron این صفحه را **وظایف زمان‌بندی‌شدهٔ محدود به نشست** می‌نامد. نام قدیمی در نشانی `claude.ai/code/routines`، API ‏`/fire` و کلید مدیریتی **Scheduled tasks (Was Routines)** باقی مانده است.

### دستور `/loop`

```bash
# فاصلهٔ زمانی صریح
/loop 5m check if the deployment finished

# زبان طبیعی
/loop check build status every 30 minutes
```

عبارات استاندارد کرون پنج‌فیلدی نیز برای زمان‌بندی دقیق پشتیبانی می‌شوند.

### یادآورهای یک‌باره

یادآورهایی تنظیم کنید که یک بار در زمان مشخصی فعال شوند:

```
remind me at 3pm to push the release branch
in 45 minutes, run the integration tests
```

### مدیریت وظایف زمان‌بندی‌شده

| ابزار | توضیح |
|------|-------------|
| `CronCreate` | یک وظیفهٔ زمان‌بندی‌شدهٔ جدید بسازید |
| `CronList` | همهٔ وظایف زمان‌بندی‌شدهٔ فعال را فهرست کنید. از v2.1.136، خروجی همچنین واجدشرط(ها) و متن پرامپت زمان‌بندی‌شده را شامل می‌شود، تا بتوانید بدون بازکردن هر کرون بررسی کنید که چه چیزی اجرا خواهد شد. |
| `CronDelete` | یک وظیفهٔ زمان‌بندی‌شده را حذف کنید |

**محدودیت‌ها و رفتار**:
- حداکثر **۵۰ وظیفهٔ زمان‌بندی‌شده** در هر نشست
- محدود به نشست — با پایان نشست پاک می‌شوند
- وظایف تکرارشونده پس از **۳ روز** به‌طور خودکار منقضی می‌شوند
- وظایف فقط زمانی فعال می‌شوند که Claude Code در حال اجرا باشد — جبرانی برای اجراهای ازدست‌رفته وجود ندارد

### جزئیات رفتار

| جنبه | جزئیات |
|--------|--------|
| **لرزش تکرارشونده** | تا ۱۰٪ فاصله (حداکثر ۱۵ دقیقه) |
| **لرزش یک‌باره** | تا ۹۰ ثانیه روی مرزهای :00/:30 |
| **اجراهای ازدست‌رفته** | بدون جبران — اگر Claude Code در حال اجرا نبوده، نادیده گرفته می‌شود |
| **ماندگاری** | در راه‌اندازی‌های مجدد حفظ نمی‌شود |

### وظایف زمان‌بندی‌شدهٔ ابری

از `/schedule` استفاده کنید تا وظایف زمان‌بندی‌شدهٔ ابری بسازید که روی زیرساخت Anthropic اجرا می‌شوند:

```
/schedule daily at 9am run the test suite and report failures
```

وظایف زمان‌بندی‌شدهٔ ابری در راه‌اندازی‌های مجدد دوام می‌آورند و نیازی ندارند Claude Code به‌صورت محلی در حال اجرا باشد. هر اجرا در حالت خودکار شروع می‌شود مگر اینکه حالت خودکار در دسترس نباشد، بنابراین یک طبقه‌بند اقدامات را تأیید یا مسدود می‌کند؛ اجرایی که یک قاعدهٔ `ask` با آن تطبیق پیدا کند یا به آستانه‌های مسدودسازی مکرر حالت خودکار برسد همچنان متوقف می‌شود و در نشستش منتظر پاسخ می‌ماند. در طرح‌های Enterprise که از نقش‌های سفارشی استفاده می‌کنند، به نقش دیگری با اجازهٔ وظایف زمان‌بندی‌شده هم نیاز دارید.

### غیرفعال‌کردن وظایف زمان‌بندی‌شده

```bash
export CLAUDE_CODE_DISABLE_CRON=1
```

> **`/schedule` به‌طور خودکار توسط سطوح کلید API غیرفعال می‌شود (v2.1.139)**: `/schedule` ابری زمانی بی‌صدا در دسترس نیست که هر یک از `ANTHROPIC_API_KEY`، `ANTHROPIC_AUTH_TOKEN` یا `apiKeyHelper` تنظیم شده باشد — حتی اگر با claude.ai هم وارد شده باشید. همین شرط [کنترل از راه دور](#غیرفعال‌سازی-کنترل-از-راه-دور-disableremotecontrol-v21128)، کانکتورهای MCP در claude.ai و ترجیحات اعلان را غیرفعال می‌کند. کلید API را حذف کنید (یا روی سطح OAuth پرو/مکس اجرا کنید) تا از `/schedule` استفاده کنید. `CronCreate` محلی تحت‌تأثیر نیست.

### مثال: پایش یک استقرار

```
/loop 5m check the deployment status of the staging environment.
        If the deploy succeeded, notify me and stop looping.
        If it failed, show the error logs.
```

> **نکته**: وظایف زمان‌بندی‌شده محدود به نشست هستند. برای خودکارسازی ماندگاری که در راه‌اندازی‌های مجدد دوام می‌آورد، به‌جای آن از خطوط لولهٔ CI/CD، GitHub Actions یا وظایف زمان‌بندی‌شدهٔ اپ دسکتاپ استفاده کنید.

## حالت‌های مجوز

حالت‌های مجوز کنترل می‌کنند که Claude چه اقداماتی را می‌تواند بدون تأیید صریح انجام دهد.

### حالت‌های مجوز موجود

| حالت | رفتار |
|---|---|
| `manual` | فقط خواندن فایل‌ها؛ برای همهٔ اقدامات دیگر پرامپت می‌پرسد. در v2.1.200 از `default` تغییر نام یافت — `default` هنوز به‌عنوان نام مستعار پذیرفته می‌شود |
| `acceptEdits` | خواندن و ویرایش فایل‌ها؛ برای دستورها پرامپت می‌پرسد |
| `plan` | فقط خواندن فایل‌ها (حالت پژوهش، بدون ویرایش) |
| `auto` | همهٔ اقدامات با بررسی‌های طبقه‌بند ایمنی در پس‌زمینه. نیازمند مدل واجدشرط (Sonnet 5 یا بالاتر، Opus 4.7 یا بالاتر، Haiku 5.5، یا یک مدل Fable روی هر ارائه‌دهنده؛ Opus 4.6 و Sonnet 4.6 نیز روی Anthropic API و Claude Platform on AWS واجدشرط‌اند) و ارائه‌دهنده — روی همهٔ طرح‌ها در دسترس است، [حالت خودکار](#حالت-خودکار) را ببینید |
| `bypassPermissions` | همهٔ اقدامات، بدون بررسی مجوز (خطرناک) |
| `dontAsk` | فقط ابزارهای پیش‌تأییدشده اجرا می‌شوند؛ بقیه رد می‌شوند |

> **توجه**: حالت مجوز `default` در v2.1.200 به **Manual** تغییر نام یافت (در CLI، `--help`، VS Code و JetBrains)، و نشان خاکستری ⏸ هنگام فعال بودن آن در نوار پایین نمایش داده می‌شود (v2.1.203). هم `--permission-mode manual` و هم `--permission-mode default` کار می‌کنند، همان‌طور که `"defaultMode": "manual"` و `"defaultMode": "default"` در تنظیمات. توجه کنید که کلید تنظیمات `permissions.defaultMode` است — کلید `permissions.mode` وجود ندارد، بنابراین نمونه‌های زیر از املای متعارف استفاده می‌کنند.

با `Shift+Tab` در CLI بین حالت‌ها بچرخید. یک پیش‌فرض را با پرچم `--permission-mode` یا تنظیم `permissions.defaultMode` تعیین کنید. وقتی هیچ حالت مجوزی پیکربندی نشده باشد، نشست‌های تعاملی ترمینال و VS Code از v2.1.284 روی هر طرح و ارائه‌دهنده در حالت خودکار شروع می‌شوند (v2.1.283 این کار را فقط روی ارائه‌دهندگان شخص ثالث مانند Bedrock، Agent Platform در Google Cloud و Foundry، یا با تلومتری خاموش انجام می‌داد)؛ `permissions.defaultMode` همچنان آن را بازنویسی می‌کند، و نشستی که حالت خودکار در آن در دسترس نیست به‌جای آن در Manual شروع می‌شود. از v2.1.302، یک اجرای `claude -p` یا Agent SDK که هیچ حالت مجوزی تنظیم نکرده باشد در حالت Manual (مقدار تنظیمات `default`) شروع می‌شود و فراخوانی‌های ابزاری که به تأیید نیاز دارند را رد می‌کند؛ `--permission-mode` (مثلاً `auto` یا `acceptEdits`) یا `--allowedTools` را بدهید.

> **حالت برنامه دستورهای شل را به طبقه‌بند واگذار می‌کند (v2.1.218)**: وقتی [حالت خودکار](#حالت-خودکار) در دسترس است و تنظیم `useAutoModeDuringPlan` روشن است — که به‌طور پیش‌فرض روشن است — طبقه‌بند در طول برنامه‌ریزی دستورهای شل را بررسی می‌کند به‌جای اینکه از شما بپرسد. دستورهای تأییدشده اجرا می‌شوند و دستورهای ردشده مسدود می‌شوند. حالت برنامه همچنان نوشتن فایل را بدون قید و شرط مسدود می‌کند.

از v2.1.160، حتی `acceptEdits` پیش از نوشتن فایل‌های راه‌اندازی شل (`.zshenv`، `.zlogin`، `.bash_login`، `~/.config/git/`) و پیکربندی‌های ساخت کد-اجراکننده (`.npmrc`، `.yarnrc*`، `bunfig.toml`، `.bazelrc`، `.pre-commit-config.yaml`، `.devcontainer/`، …) پرامپت می‌پرسد، که در غیر این صورت می‌توانست به اجرای ناخواستهٔ دستور منجر شود.

> **پوشش مسیر گسترده‌تر `--dangerously-skip-permissions` (v2.1.121، v2.1.126)**: پرچم CLI `--dangerously-skip-permissions` (و حالت معادل `bypassPermissions`) اکنون پرامپت‌ها را برای نوشتن در فهرست مجاز بسیار گسترده‌تری دور می‌زند — `.claude/skills/`، `.claude/agents/`، `.claude/commands/`، `.claude/`، `.git/`، `.vscode/` و فایل‌های پیکربندی شل. دستورهای حذف فاجعه‌بار (`rm -rf /` و مانند آن) همچنان در این حالت پرامپت می‌پرسند — از v2.1.281 پرامپت ترمینال ۲ دقیقه صبر می‌کند، سپس دستور را با یک راهنمای بازنویسی رد می‌کند تا نشست‌های بدون نظارت ادامه یابند، و از v2.1.309 اپ دسکتاپ و VS Code بی‌درنگ آن را با همان راهنما رد می‌کنند (`CLAUDE_CODE_DISABLE_DANGEROUS_RM_TIMEOUT=1` مهلت زمانی را خاموش می‌کند). حالت خودکار این حذف‌های مسیر بحرانی را به همین شکل بررسی می‌کند — پرامپت ۲ دقیقه‌ای در ترمینال، رد فوری در جاهای دیگر — و فقط وقتی آن متغیر تنظیم شده باشد آن‌ها را به طبقه‌بند می‌فرستد. از v2.1.304 یک `rm` بازگشتی روی مسیر یک درایو mount‌شده مثل `/Volumes/USB` یا `/mnt/c/Users` در WSL همین رفتار را می‌گیرد، حتی با یک قاعدهٔ مجاز `rm`؛ برای خاموش‌کردن آن پرامپت، Claude Code را با `CLAUDE_CODE_DISABLE_MOUNTED_DRIVE_RM_PROMPT=1` اجرا کنید (بلوک `env` در تنظیمات نادیده گرفته می‌شود). این پرچم را ابزاری تیزتر از قبل بدانید؛ فقط در سندباکس‌های یک‌بارمصرف از آن استفاده کنید.

> **تشخیص شل در ویندوز (v2.1.120، v2.1.126)**: Git for Windows / Git Bash دیگر لازم نیست. وقتی Git Bash وجود ندارد، Claude Code از PowerShell به‌عنوان ابزار شل استفاده می‌کند. از v2.1.126، وقتی ابزار PowerShell فعال باشد، PowerShell شل *اصلی* است و تشخیص شامل PowerShell 7 نصب‌شده از Microsoft Store، MSI بدون PATH، یا به‌عنوان یک `.NET global tool` می‌شود.

> **ابزار PowerShell به‌طور پیش‌فرض در ویندوز برای Bedrock/Vertex/Foundry فعال است (v2.1.143)**: از v2.1.143، ابزار PowerShell **به‌طور پیش‌فرض در ویندوز** برای کاربران Bedrock، Vertex و Foundry فعال است. Claude Code PowerShell را با `-ExecutionPolicy Bypass` فراخوانی می‌کند تا اسکریپت‌ها حتی وقتی سیاست سیستم `Restricted` است اجرا شوند. برای اینکه Claude Code سیاست اجرای سیستم را رعایت کند، `CLAUDE_CODE_POWERSHELL_RESPECT_EXECUTION_POLICY=1` را تنظیم کنید. برای غیرفعال‌کردن کامل ابزار PowerShell، `CLAUDE_CODE_USE_POWERSHELL_TOOL=0` را تنظیم کنید.

## حالت بدون رابط

حالت چاپ (`claude -p`) به Claude Code اجازه می‌دهد بدون ورودی تعاملی اجرا شود؛ ایده‌آل برای خودکارسازی و CI/CD. این همان حالت غیرتعاملی است که جایگزین پرچم قدیمی‌تر `--headless` می‌شود.

### حالت چاپ چیست؟

حالت چاپ این موارد را ممکن می‌کند:
- اجرای خودکار اسکریپت
- یکپارچه‌سازی CI/CD
- پردازش دسته‌ای
- وظایف زمان‌بندی‌شده

### اجرا در حالت چاپ (غیرتعاملی)

```bash
# اجرای یک وظیفهٔ مشخص
claude -p "Run all tests" --permission-mode auto

# پردازش محتوای لوله‌شده
cat error.log | claude -p "Analyze these errors"

# یکپارچه‌سازی CI/CD (GitHub Actions)
- name: AI Code Review
  run: claude -p "Review PR"
```

### نمونه‌های استفادهٔ بیشتر از حالت چاپ

```bash
# اجرای یک وظیفهٔ مشخص با ضبط خروجی
claude -p "Run all tests and generate coverage report" --permission-mode auto

# با خروجی ساختاریافته
claude -p --output-format json "Analyze code quality"

# با ورودی از stdin
echo "Analyze code quality" | claude -p "explain this"
```

### مثال: یکپارچه‌سازی CI/CD

**GitHub Actions**:
```yaml
# .github/workflows/code-review.yml
name: AI Code Review

on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run Claude Code Review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p --output-format json \
            --max-turns 3 \
            "Review this PR for:
            - Code quality issues
            - Security vulnerabilities
            - Performance concerns
            - Test coverage
            Output results as JSON" > review.json

      - name: Post Review Comment
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const review = JSON.parse(fs.readFileSync('review.json', 'utf8'));
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: JSON.stringify(review, null, 2)
            });
```

### پیکربندی حالت چاپ

حالت چاپ (`claude -p`) چندین پرچم برای خودکارسازی پشتیبانی می‌کند:

```bash
# محدودکردن نوبت‌های خودمختار
claude -p --max-turns 5 "refactor this module"

# خروجی JSON ساختاریافته
claude -p --output-format json "analyze this codebase"

# با اعتبارسنجی طرح‌واره
claude -p --json-schema '{"type":"object","properties":{"issues":{"type":"array"}}}' \
  "find bugs in this code"

# غیرفعال‌کردن ماندگاری نشست
claude -p --no-session-persistence "one-off analysis"
```

### حالت امن (عیب‌یابی)

`--safe-mode` (و متغیر محیطی `CLAUDE_CODE_SAFE_MODE`، مثلاً `CLAUDE_CODE_SAFE_MODE=1`) Claude Code را با **همهٔ سفارشی‌سازی‌ها غیرفعال** اجرا می‌کند — CLAUDE.md، پلاگین‌ها، مهارت‌ها، هوک‌ها و سرورهای MCP همگی خاموش می‌شوند.

```bash
# اجرا با غیرفعال بودن همهٔ سفارشی‌سازی‌ها
claude --safe-mode

# معادل آن با متغیر محیطی
CLAUDE_CODE_SAFE_MODE=1 claude
```

این یک ابزار عیب‌یابی است: وقتی یک پیکربندی سفارشی مشکلی ایجاد می‌کند، در حالت امن اجرا کنید تا مشخص شود مشکل در تنظیمات شماست یا در خود Claude Code.

## مدیریت نشست

مدیریت کارآمد چند نشست Claude Code.

### دستورهای مدیریت نشست

| دستور | توضیح |
|---------|-------------|
| `/resume` | از سرگیری یک گفتگو با شناسه یا نام |
| `/rename` | نام‌گذاری نشست جاری |
| `/fork [prompt]` | کپی کردن گفتگو به یک نشست پس‌زمینهٔ مستقل جدید و ادامهٔ کار در اینجا (v2.1.212+) |
| `/subtask <task>` | ایجاد یک زیرایجنت فورک‌شده که کل گفتگو را به ارث می‌برد و نتیجه را همین‌جا گزارش می‌دهد (v2.1.212+) |
| `/branch [name]` | جابه‌جایی به یک کپی از گفتگو در همین نقطه، با حفظ نسخهٔ اصلی |
| `claude -c` | ادامهٔ آخرین گفتگو |
| `claude -r "session"` | از سرگیری نشست با نام یا شناسه |

### از سرگیری نشست‌ها

**ادامهٔ آخرین گفتگو**:
```bash
claude -c
```

**از سرگیری یک نشست نام‌دار**:
```bash
claude -r "auth-refactor" "finish this PR"
```

**تغییر نام نشست جاری** (داخل REPL):
```
/rename auth-refactor
```

> **به‌روزرسانی v2.1.212**: تایپ `/resume` (بدون آرگومان) در نمای ایجنت اکنون یک انتخاب‌گر از نشست‌های گذشته باز می‌کند — از جمله نشست‌هایی که از فهرست قابل مشاهده حذف شده‌اند — و نشست انتخاب‌شده را به‌صورت یک نشست پس‌زمینه از سر می‌گیرد.

> **به‌روزرسانی v2.1.304**: در طرح‌های Pro و Max، از سرگیری یک گفتگوی طولانی بی‌کار که بخش محسوسی از محدودیت مصرف ۵ ساعتهٔ شما را مصرف می‌کند یک گفتگوی **Resume this conversation?** نشان می‌دهد: یا ادامه بدهید، یا یک گفتگوی جدید شروع کنید (اگر به قبلی اشاره کنید Claude هنوز می‌تواند آن را ببیند).

### فورک کردن و شاخه‌بندی نشست‌ها

سه دستور از یک گفتگو کپی می‌سازند و تفاوتشان در *این است که کپی کجا اجرا می‌شود*:

`/subtask <task>` یک زیرایجنت فورک‌شده ایجاد می‌کند که کل گفتگو را به ارث می‌برد و روی وظیفه کار می‌کند در حالی که شما به کار خود ادامه می‌دهید — با ردیف مستقل خودش در `claude agents` و نتیجه پس از پایان به گفتگوی شما بازگردانده می‌شود:

```
/subtask Investigate why the auth tests are flaky
```

`/fork [prompt]` در عوض گفتگو را به یک **نشست پس‌زمینه** جدید کپی می‌کند. کپی با همه‌چیز تا این لحظه شروع می‌شود و مستقل اجرا می‌شود — چیزی به این گفتگو بازنمی‌گردد:

```
/fork Try the OAuth approach end to end
```

برای اینکه خودتان به یک کپی جابه‌جا شوید و اصلاً کار را واگذار نکنید، از `/branch [name]` استفاده کنید که نسخهٔ اصلی را حفظ می‌کند و اجازه می‌دهد با `/resume` به آن بازگردید:

```
/branch try-oauth-instead
```

> **توجه**: `/fork` و `/subtask` در **v2.1.212** نقش‌هایشان را عوض کردند. پیش از v2.1.161، `/fork` نام مستعار `/branch` بود؛ از v2.1.161 تا v2.1.211 یک زیرایجنت فورک‌شده راه‌اندازی می‌کرد — رفتاری که اکنون `/subtask` آن را دارد. وقتی نمای ایجنت خاموش باشد، `/subtask` در دسترس نیست و `/fork` رفتار زیرایجنت فورک‌شده را حفظ می‌کند.

یا از CLI فورک کنید:
```bash
claude --resume auth-refactor --fork-session "try OAuth instead"
```

### ماندگاری نشست

نشست‌ها به‌صورت خودکار ذخیره می‌شوند و می‌توان آن‌ها را از سر گرفت:

```bash
# ادامهٔ آخرین گفتگو

# از سرگیری نشست مشخص با نام یا شناسه

# از سرگیری و فورک کردن برای آزمایش
```

### ادامهٔ خودکار در سقف مصرف (v2.1.234)

از **v2.1.234**، نشستی که به‌خاطر سقف مصرف claude.ai متوقف شده باشد، پس از بازنشانی آن سقف به‌صورت خودکار ادامه می‌یابد — بدون نیاز به پرامپت دستی دوباره. این را از `/config` زیر «ادامهٔ خودکار در سقف مصرف» روشن/خاموش کنید.

### خلاصهٔ نشست (v2.1.108)

وقتی پس از مدتی دور بودن به یک نشست بازمی‌گردید، Claude می‌تواند خلاصه‌ای کوتاه از آنچه انجام شده نشان دهد. این قابلیت برای هر پلن و هر ارائه‌دهنده به‌صورت پیش‌فرض روشن است؛ آن را از `/config` → **خلاصهٔ نشست** خاموش کنید.

> **تلومتری OTEL — فعال‌سازی مجدد نظرسنجی بازخورد (v2.1.136+)**: سازمان‌هایی که داده‌های OpenTelemetry جمع‌آوری می‌کنند می‌توانند با تنظیم `CLAUDE_CODE_ENABLE_FEEDBACK_SURVEY_FOR_OTEL=1` نظرسنجی کیفیت نشست Anthropic را دوباره فعال کنند. این نظرسنجی در استقرارهای OTEL به‌صورت پیش‌فرض خاموش است، چون پیش‌تر از مسیرهای خط لولهٔ تلومتری منحرف شده بود.

> **تلومتری OTEL — رویداد لاگ `assistant_response` (v2.1.193+)**: Claude Code یک رویداد لاگ OpenTelemetry با نام `claude_code.assistant_response` منتشر می‌کند که متن پاسخ مدل را حمل می‌کند و به خط لوله‌های OTEL اجازه می‌دهد در کنار تلومتری موجود ابزار/رویداد، آنچه Claude گفته است را نیز ثبت کنند.

> **تلومتری OTEL — ویژگی‌های کش و GenAI (v2.1.300)**: رویدادهای `api_request` ویژگی‌های `cache_creation_5m_tokens`/`cache_creation_1h_tokens` را اضافه می‌کنند و spanها ویژگی‌های قرارداد معنایی GenAI مانند `gen_ai.provider.name` را حمل می‌کنند.

> **تلومتری OTEL — ویژگی‌های `tool_decision` (v2.1.301)**: رویدادهای `tool_decision` ویژگی‌های `classifier_verdict` و `permission_mode` را اضافه می‌کنند.

> **تلومتری OTEL — `safety_event` (v2.1.307)**: رویداد لاگ جدید `claude_code.safety_event` برای هر فراخوانی ابزاری که یک قاعدهٔ مجوز، حالت خودکار، یک بررسی ایمنی، یک هوک یا سندباکس رد کرده، دربارهٔ آن پرسیده یا آن را بازفرستاده باشد اجرا می‌شود، با ویژگی‌های `category`، `decision` (`accept`/`reject`/`sent_back`) و `decision_source`. هیچ متن دستور، مسیر فایل یا نام میزبانی حمل نمی‌کند.

> **تلومتری OTEL — ویژگی‌های پیوند (v2.1.310)**: رویدادهای `tool_decision` و `tool_result` ویژگی `request_id` را برای پیوند یک فراخوانی به پاسخ API‌اش اضافه می‌کنند، و رویدادهای زیرایجنت `parent_agent_id` را حمل می‌کنند.

**کنترل رفتار خلاصه:**

```bash
/recap                                 # اجرای دستی یک خلاصه
/config                                # روشن/خاموش کردن خلاصهٔ خودکار
```

یا از طریق متغیر محیطی:
```bash
CLAUDE_CODE_ENABLE_AWAY_SUMMARY=0 claude   # غیرفعال کردن خلاصه
CLAUDE_CODE_ENABLE_AWAY_SUMMARY=1 claude   # اجبار به فعال‌سازی خلاصه
```

## پیام‌رسانی بین نشست‌ها

> **افزوده‌شده در v2.1.224**، و در v2.1.239 گسترش یافت. روی **macOS، Linux و (از v2.1.239) Windows** در دسترس است.

نشست‌ها پیش‌تر جزیره‌هایی جدا بودند. پیام‌رسانی بین نشست‌ها به یک نشست Claude Code اجازه می‌دهد
با نشستی دیگر صحبت کند — از جمله نشست‌های روی ماشین‌های دیگرتان و نشست‌های ابری شما — تا بتوانید
یک پرسش را به نشستی بسپارید که از قبل زمینهٔ لازم را در خود دارد، به‌جای اینکه
دوباره آن را توضیح دهید.

### کشف نشست‌ها

`ListAgents` همهٔ چیزهایی را که می‌توانید مخاطب قرار دهید فهرست می‌کند: زیرایجنت‌هایی که ساخته‌اید، دیگر نشست‌های محلی
روی این ماشین، نشست‌های ابری شما، و (وقتی Remote Control متصل است) نشست‌های
روی ماشین‌های دیگرتان. هر ردیف با نوعش برچسب می‌خورد و از v2.1.229 ردیف‌ها برچسب‌های
`offline` و `cloud` را نیز دارند تا بتوانید نشست در دسترس را از نشست خفته تشخیص دهید.

**نام در هر ردیف همان نشانی است** — همان چیزی که به آن پیام می‌فرستید.

### ارسال پیام

`SendMessage` مقصد و پیام را می‌گیرد:

```text
SendMessage({ to: "<session name>", message: "What did you conclude about the retry logic?" })
```

از v2.1.232، یک نام خالی کافی است — دیگر لازم نیست یک ارجاع رفع‌ابهام اضافه کنید
مگر اینکه دو ردیف واقعاً نام یکسان داشته باشند.

### انتظار برای بی‌کار شدن یک نشست (`notify_when_idle`، v2.1.236)

وقتی نشستی که به آن پیام می‌دهید در میانهٔ کار است، معمولاً می‌خواهید بدانید کِی تمام می‌شود
نه اینکه مدام آن را نظرسنجی کنید. `SendMessage` برای همین کار ورودی `notify_when_idle` را می‌پذیرد:

```text
SendMessage({
  to: "auth-refactor",
  message: "ping me when the migration finishes",
  notify_when_idle: true
})
```

این قابلیت **اختیاری و یک‌بارمصرف** است — نشست مقصد بار بعدی که
بی‌کار شود یک اعلان می‌فرستد و سپس اشتراک تمام می‌شود. هیچ حلقهٔ نظرسنجی و هیچ اعلان تکراری
وجود ندارد اگر نشست دوباره مشغول و سپس بی‌کار شود.

دو تغییر مرتبط در v2.1.239: `ListAgents` اکنون **نام خود نشست** را نیز گزارش می‌کند (تا
یک نشست بتواند به دیگران بگوید چگونه آن را مخاطب قرار دهند) در کنار هم‌تیمی‌های زنده‌اش، و پیام‌رسانی
بین نشست‌ها روی **Windows** در دسترس شد.

### مختصر اشاره با `@` (v2.1.232)

به‌جای فراخوانی صریح ابزار، می‌توانید مستقیماً در پرامپت خود با `@` به یک نشست
اشاره کنید تا به آن برسید:

```text
@auth-refactor did the migration tests pass?
```

### کنترل آنچه می‌رسد: `crossSessionInbound`

پیام‌های ورودی با تنظیم `crossSessionInbound` کنترل می‌شوند (v2.1.224+):

| مقدار | رفتار |
|---|---|
| `"accept"` | پیام‌های ورودی در این نشست به Claude تحویل داده می‌شوند |
| `"hold"` | اعلانی می‌بینید که پیامی رسیده است؛ پیام تحویل نمی‌شود |
| `"refuse"` | پیام‌های ورودی دور ریخته می‌شوند |

این مقادیر یک نردبان می‌سازند — `accept < hold < refuse` — و **تنظیمات پروژه و محلی
فقط زمانی اعمال می‌شوند که سخت‌گیرانه‌تر** از مقدار سطح کاربر باشند. یک پروژه می‌تواند تحویل
ورودی را سخت‌تر کند، اما هرگز نمی‌تواند آن را شل‌تر کند. از v2.1.232 این تنظیم یک ردیف در `/config` هم دارد:
«پیام‌ها از نشست‌های دیگر شما.»

### دامنهٔ دسترسی و محدودیت‌ها

- نشست‌های محلی روی همان ماشین، به‌علاوهٔ نشست‌های ابری شما.
- نشست‌های Remote Control روی ماشین‌های دیگرتان، قابل خطاب قرار دادن با نام (v2.1.225).
- یک نشست ابری پیام شما را **دریافت** می‌کند اما هنوز نمی‌تواند به یک نشست محلی پیام بدهد —
  پاسخش را در رونوشت خودش بخوانید.
- macOS و Linux از v2.1.224؛ Windows از v2.1.239.

با اجرای `/keybindings` میان‌برهای صفحه‌کلید سفارشی بسازید؛ این دستور `~/.claude/keybindings.json` را برای ویرایش باز می‌کند (v2.1.18+).

### پشتیبانی از آکورد

کلیدبندها توالی‌های آکورد (ترکیب چند کلید) را پشتیبانی می‌کنند:

```
"ctrl+k ctrl+s"   → توالی دو کلیدی: ctrl+k را بزنید، سپس ctrl+s
"ctrl+shift+p"    → کلیدهای اصلاح‌کنندهٔ هم‌زمان
```

**نحو ورودی کلید**:
- **اصلاح‌کننده‌ها**: `ctrl` (یا `control`)، `alt` (یا `opt`، `option`، `meta`)، `shift` و `cmd` (یا `command`، `super`، `win`) — `cmd` یک اصلاح‌کنندهٔ جداگانه است، نه نام مستعار `meta`، و فقط در ترمینال‌هایی تشخیص داده می‌شود که کلید Super را گزارش می‌کنند
- **حروف بزرگ یعنی Shift**: `K` معادل `shift+k` است
- **کلیدهای ویژه**: `escape`، `enter`، `return`، `tab`، `space`، `backspace`، `delete`، کلیدهای جهت‌دار

### حالت ویم

کلیدبایندهای Vi/Vim را برای ویرایش متن فعال کنید:

**فعال‌سازی**:
- فعال‌سازی از طریق `/config` (کلید «Editor / Vim mode») یا در `~/.claude/settings.json` زیر `editorMode: "vim"`. دستور اسلش مستقل `/vim` حذف شده است (نگاه کنید به [ایشو #43370](https://github.com/anthropics/claude-code/issues/43370))؛ حالت ویم اکنون پیکربندی‌محور است.
- جابه‌جایی بین حالت‌ها با `Esc` برای NORMAL، `i/a/o` برای INSERT، `v` برای VISUAL و `V` برای VISUAL-LINE (نسخهٔ v2.1.118+)

**کلیدهای پیمایش**:
- `h` / `l` - حرکت به چپ/راست
- `j` / `k` - حرکت به پایین/بالا
- `w` / `b` / `e` - حرکت کلمه‌به‌کلمه
- `0` / `$` - رفتن به ابتدا/انتهای خط
- `gg` / `G` - پرش به ابتدا/انتهای متن
- `%` - پرش به براکت متناظر؛ ترکیب با `d`، `c`، `y` (نسخهٔ v2.1.301)

**اشیای متنی**:
- `iw` / `aw` - درون/پیرامون کلمه
- `i"` / `a"` - درون/پیرامون رشتهٔ درون گیومه
- `i(` / `a(` - درون/پیرامون پرانتزها

**حالت‌های بصری (نسخهٔ v2.1.118+)**:

| کلید | حالت | رفتار |
|-----|------|----------|
| `v` | بصری | انتخاب نویسه‌به‌نویسه با بازخورد بصری؛ با کلیدهای حرکت گسترش دهید |
| `V` | خط‌بصری | انتخاب خط‌به‌خط؛ همیشه خطوط کامل را انتخاب می‌کند |
| `y` | کشیدن | کپی انتخاب بصری جاری |
| `d` / `x` | حذف | حذف انتخاب بصری جاری |
| `c` | تغییر | حذف انتخاب و ورود به حالت INSERT |
| `Esc` | خروج | بازگشت به حالت NORMAL |

انتخاب‌های بصری در فیلد ورودی برجسته می‌شوند تا دقیقاً ببینید چه چیزی پیش از اعمال عملگر کشیده، حذف یا تغییر داده خواهد شد.

## سبک‌های خروجی

سبک‌های خروجی تغییر می‌دهند که Claude **چگونه** پاسخ می‌دهد، نه اینکه چه چیزی می‌داند. آن‌ها پرامپت سیستم را تغییر می‌دهند تا نقش، لحن و قالب پیش‌فرض پاسخ را تعیین کنند. زمانی به سراغ یکی بروید که هر نوبت مجبورید دوباره همان لحن را درخواست کنید، یا می‌خواهید Claude در نقشی غیر از مهندس نرم‌افزار عمل کند.

برای دستورهای مربوط به پروژه یا کدبیس خود، به‌جای آن از [CLAUDE.md](../02-memory/) استفاده کنید — آن سازوکاری متفاوت با توازن‌های متفاوت است.

### سبک‌های داخلی

| سبک | رفتار |
|-------|----------|
| **Default** | پرامپت سیستم استاندارد، تنظیم‌شده برای انجام کارآمد وظایف مهندسی نرم‌افزار |
| **Proactive** | Claude فوراً اجرا می‌کند و به‌جای توقف برای تصمیم‌های معمول، فرض‌های معقول می‌گیرد. راهنمایی قوی‌تر برای اجرای خودمختار نسبت به حالت خودکار، اما حالت مجوز شما را **تغییر نمی‌دهد** — همچنان پرامپت‌های مجوز را می‌بینید |
| **Explanatory** | بین مراحل «بینش»های آموزشی می‌افزاید و انتخاب‌های پیاده‌سازی و الگوهای کدبیس را توضیح می‌دهد |
| **Learning** | یادگیری مشارکتی از طریق انجام کار. Claude هم بینش‌ها را به اشتراک می‌گذارد و هم نشانگرهای `TODO(human)` را باقی می‌گذارد تا خودتان قطعه‌های کوچک و راهبردی را پیاده‌سازی کنید |
| **Concise** (نسخهٔ v2.1.237) | Claude با نتیجه شروع می‌کند و مقدمه و روایت را حذف می‌کند. جامعیت تغییر نمی‌کند — فقط چارچوب اطراف پاسخ حذف می‌شود. آن را در `/config` → Output style انتخاب کنید، یا `"outputStyle": "Concise"` را تنظیم کنید |

### انتخاب یک سبک

`/config` را اجرا کنید و **Output style** را انتخاب کنید، یا `/output-style <style>` را اجرا کنید تا مستقیماً جابه‌جا شوید — بدون آرگومان، سبک‌های موجود را فهرست می‌کند و سبک جاری را نشانه‌گذاری می‌کند. در هر دو حالت انتخاب در `.claude/settings.local.json` ذخیره می‌شود. برای تنظیم بدون منو، تنظیم را مستقیماً ویرایش کنید:

```json
{
  "outputStyle": "Explanatory"
}
```

> **نکته**: دستور مستقل `/output-style` در نسخهٔ v2.1.73 منسوخ و در نسخهٔ v2.1.91 حذف شد، اما **در نسخهٔ v2.1.269 بازگشت** و در نسخهٔ v2.1.278 فعال است. در نشست‌های بدون رابط و Remote Control نیز کار می‌کند. `/config` و تنظیم `outputStyle` هم همچنان کار می‌کنند.

سبک خروجی بخشی از پرامپت سیستم است که Claude Code یک بار در شروع نشست آن را می‌خواند — تغییرها پس از `/clear` یا در یک نشست جدید اعمال می‌شوند.

### سبک‌های خروجی سفارشی

سبک سفارشی یک فایل Markdown با frontmatter است که در یکی از سه سطح ذخیره می‌شود:

- کاربر: `~/.claude/output-styles/`
- پروژه: `.claude/output-styles/`
- سیاست مدیریت‌شده: `.claude/output-styles/` درون پوشهٔ تنظیمات مدیریت‌شده

سبک‌های پروژه از هر `.claude/output-styles/` بین پوشهٔ کاری و ریشهٔ مخزن بارگذاری می‌شوند. از نسخهٔ v2.1.178، وقتی پوشه‌های تودرتو نام سبک یکسانی تعریف می‌کنند، آن‌که به پوشهٔ کاری نزدیک‌تر است برنده می‌شود.

```markdown
---
name: Diagrams first
description: Lead every explanation with a diagram
keep-coding-instructions: true
---

When explaining code, architecture, or data flow, start with a Mermaid diagram
showing the structure, then explain in prose.
```

| Frontmatter | هدف | پیش‌فرض |
|-------------|---------|---------|
| `name` | نام سبک، اگر با نام فایل متفاوت باشد | از نام فایل به ارث می‌رسد |
| `description` | در انتخابگر `/config` نمایش داده می‌شود | هیچ |
| `keep-coding-instructions` | حفظ دستورهای داخلی مهندسی نرم‌افزار Claude Code | `false` |
| `force-for-plugin` | فقط سبک‌های پلاگین: هر زمان پلاگین فعال است به‌طور خودکار اعمال شود و `outputStyle` کاربر را نادیده بگیرد | `false` |

**`keep-coding-instructions: true` را تنظیم کنید** زمانی که شیوهٔ ارتباط Claude را تغییر می‌دهید اما همچنان می‌خواهید به همان شکل کدنویسی کند. وقتی Claude اصلاً مهندسی نرم‌افزار انجام نمی‌دهد — مثلاً دستیار نوشتن یا تحلیلگر داده — آن را حذف کنید.

### دامنه و هزینه

سبک‌های خروجی فقط بر **گفت‌وگوی اصلی** اعمال می‌شوند. زیرایجنت پرامپت سیستم خودش را اجرا می‌کند، بنابراین سبک‌ها نحوهٔ پاسخ زیرایجنت‌ها را تغییر نمی‌دهند؛ fork استثناست، چون پرامپت سیستم کامل والد را به ارث می‌برد.

افزودن دستورها توکن‌های ورودی را افزایش می‌دهد، هرچند کش پرامپت بیشتر آن را پس از نخستین درخواست جذب می‌کند. Explanatory و Learning به‌طور طراحی‌شده پاسخ‌های بلندتری تولید می‌کنند که توکن‌های خروجی را افزایش می‌دهد.

### مقایسه

| ویژگی | نحوهٔ کار | چه زمانی استفاده کنید |
|---------|--------------|-------------|
| سبک‌های خروجی | پرامپت سیستم را تغییر می‌دهد | می‌خواهید هر نوبت نقش، لحن یا قالب متفاوتی داشته باشید |
| [CLAUDE.md](../02-memory/) | پس از پرامپت سیستم یک پیام کاربر می‌افزاید | Claude باید همیشه قراردادهای پروژهٔ شما را بداند |
| `--append-system-prompt` | بدون حذف چیزی به پرامپت سیستم می‌افزاید | یک افزودن موردی برای یک فراخوانی واحد |
| [زیرایجنت‌ها](../04-subagents/) | با پرامپت سیستم، مدل و ابزارهای خودش اجرا می‌شود | دستیار جداگانه‌ای با دامنهٔ مشخص می‌خواهید |
| [مهارت‌ها](../03-skills/) | هنگام فراخوانی دستورهای مخصوص وظیفه را بارگذاری می‌کند | جریان کاری قابل استفادهٔ مجدد دارید |

## خط وضعیت

خط وضعیت یک دستور سفارشی است که خروجی آن در پایین نشست نمایش داده می‌شود. آن را با `/statusline` پیکربندی کنید، یا مستقیماً تنظیم کنید:

```json
{
  "statusLine": {
    "type": "command",
    "command": "~/.claude/statusline.sh",
    "padding": 0
  }
}
```

مقدار پیش‌فرض `padding` برابر `0` است. Claude Code یک شیء JSON را از طریق stdin به دستور می‌فرستد، بنابراین اسکریپت تصمیم می‌گیرد چه چیزی نمایش دهد.

### فیلدهای ورودی موجود

| گروه | فیلدها |
|-------|--------|
| Session | `session_id`، `session_name`، `prompt_id`، `transcript_path`، `cwd`، `version` |
| Model | `model.id`، `output_style.name`، `effort.level`، `fast_mode`، `thinking.enabled` |
| Agent | `agent.name`، `vim.mode` |
| Cost | `cost.total_cost_usd`، `cost.total_duration_ms`، `cost.total_api_duration_ms`، `cost.total_lines_added` |
| Context | `context_window.context_window_size`، `.current_usage`، `.remaining_percentage`، `.total_input_tokens`، `.used_percentage` |
| Limits | `rate_limits.five_hour.used_percentage`، `.resets_at` |
| Repo | `pr.number`، `pr.review_state`، `workspace.project_dir`، `workspace.added_dirs`، `workspace.git_worktree`، `workspace.repo.host` |
| Worktree | `worktree.name`، `.branch`، `.path`، `.original_branch`، `.original_cwd` |

### مثال

```bash
#!/bin/bash
# ~/.claude/statusline.sh — مدل، مصرف زمینه و هزینه
input=$(cat)
model=$(echo "$input" | jq -r '.model.id')
used=$(echo "$input" | jq -r '.context_window.used_percentage')
cost=$(echo "$input" | jq -r '.cost.total_cost_usd')
printf '%s | ctx %.0f%% | $%.2f' "$model" "$used" "$cost"
```

> **نکته**: `statusLine` نیازمند اعتماد به فضای کاری است. اسکریپت‌های خط وضعیت همچنین `COLUMNS` و `LINES` را در محیط خود دریافت می‌کنند (نسخهٔ v2.1.153+) تا بتوانند اندازهٔ خروجی را با ترمینال هماهنگ کنند.

## حالت TUI (تمام‌صفحه)

> **جدید در نسخهٔ v2.1.110**

حالت TUI (رابط کاربری متنی) Claude Code را به‌صورت تمام‌صفحه با خروجی بدون سوسو نمایش می‌دهد — ایده‌آل برای مالتی‌پلکسرهای ترمینال مانند tmux یا پنجره‌های تقسیم‌شدهٔ iTerm2.

| تنظیم | توضیحات | پیش‌فرض |

## کانال‌ها

کانال‌ها یک ویژگی Research Preview است که رویدادها را از سرویس‌های خارجی از طریق سرورهای MCP به یک نشست در حال اجرای Claude Code می‌فرستد. منابع شامل Telegram، Discord، iMessage و وبهوک‌های دلخواه است و به Claude اجازه می‌دهد بدون نظرسنجی دوره‌ای به اعلان‌های زمان‌واقعی واکنش نشان دهد.

> **احراز هویت (نسخهٔ v2.1.128+)**: `--channels` اکنون هم با OAuth پرو/مکس **و هم** با احراز هویت کلید API (کنسول) کار می‌کند. نسخه‌های پیشین نیازمند OAuth بودند.

### اشتراک در کانال‌ها

```bash
# اشتراک در پلاگین کانال هنگام راه‌اندازی
claude --channels plugin:telegram@claude-plugins-official

# اشتراک در چند منبع (جداشده با فاصله)
claude --channels plugin:discord@claude-plugins-official plugin:telegram@claude-plugins-official
```

### یکپارچه‌سازی‌های پشتیبانی‌شده

| یکپارچه‌سازی | توضیحات |
|-------------|-------------|
| **Discord** | دریافت و پاسخ به پیام‌های Discord در نشست شما |
| **Telegram** | دریافت و پاسخ به پیام‌های Telegram در نشست شما |
| **iMessage** | دریافت اعلان‌های iMessage در نشست شما |
| **وبهوک‌ها** | دریافت رویدادها از منابع وبهوک دلخواه |

### پیکربندی

کانال‌ها را هنگام راه‌اندازی با فلگ `--channels` پیکربندی کنید. برای استقرارهای سازمانی، از تنظیمات مدیریت‌شده استفاده کنید تا کنترل کنید کدام پلاگین‌های کانال مجاز هستند:

```json
{
  "channelsEnabled": true,
  "allowedChannelPlugins": [
    { "marketplace": "claude-plugins-official", "plugin": "discord" },
    { "marketplace": "claude-plugins-official", "plugin": "telegram" }
  ]
}
```

تنظیم مدیریت‌شده‌ی `allowedChannelPlugins` کنترل می‌کند که کدام پلاگین‌های کانال در سراسر سازمان مجاز باشند. این تنظیم جایگزین فهرست مجاز نگهداری‌شده توسط Anthropic می‌شود و به `channelsEnabled: true` نیاز دارد.

### نحوه کار

1. سرورهای MCP به‌عنوان پلاگین‌های کانال عمل می‌کنند که به سرویس‌های خارجی متصل می‌شوند
2. پیام‌ها و رویدادهای ورودی به نشست فعال Claude Code هل داده می‌شوند
3. Claude می‌تواند پیام‌ها را در بافت نشست بخواند و به آن‌ها پاسخ دهد
4. پلاگین‌های کانال باید در فهرست مجاز نگهداری‌شده توسط Anthropic باشند، یا وقتی مدیر فهرستی تعیین می‌کند، در فهرست `allowedChannelPlugins` سازمان شما قرار داشته باشند
5. نیازی به نظرسنجی دوره‌ای نیست — رویدادها در زمان واقعی هل داده می‌شوند

## یکپارچه‌سازی با Chrome

یکپارچه‌سازی با Chrome، Claude Code را به مرورگر Chrome یا Microsoft Edge شما متصل می‌کند تا خودکارسازی و اشکال‌زدایی زنده‌ی وب ممکن شود. این یک ویژگی بتا است که از v2.0.73+ در دسترس است (نیازمند افزونه‌ی Claude in Chrome نسخه‌ی v1.0.36+).

### فعال‌سازی یکپارچه‌سازی با Chrome

**هنگام راه‌اندازی**:

```bash
claude --chrome      # فعال‌سازی اتصال Chrome
claude --no-chrome   # غیرفعال‌سازی اتصال Chrome
```

**درون یک نشست**:

```
/chrome
```

گزینه‌ی «Enabled by default» را انتخاب کنید تا یکپارچه‌سازی با Chrome برای همه‌ی نشست‌های آینده فعال شود. Claude Code وضعیت ورود مرورگر شما را به اشتراک می‌گذارد، بنابراین می‌تواند با اپ‌های وب احراز هویت‌شده تعامل کند.

> **توجه**: از v2.1.290 به بعد، فایل‌های تنظیمات یک پروژه نمی‌توانند یکپارچه‌سازی با Chrome را روشن کنند — از `--chrome`، `/chrome` یا تنظیمات کاربری خود استفاده کنید.

### قابلیت‌ها

| قابلیت | توضیح |
|------------|-------------|
| **اشکال‌زدایی زنده** | خواندن لاگ‌های کنسول، بررسی عناصر DOM، اشکال‌زدایی جاوااسکریپت در زمان واقعی |
| **تأیید طراحی** | مقایسه‌ی صفحات رندرشده با ماکت‌های طراحی |
| **اعتبارسنجی فرم** | آزمایش ارسال فرم‌ها، اعتبارسنجی ورودی و مدیریت خطا |
| **آزمایش اپ وب** | تعامل با اپ‌های احراز هویت‌شده (Gmail، Google Docs، Notion و غیره) |
| **استخراج داده** | استخراج و پردازش محتوا از صفحات وب |
| **ضبط نشست** | ضبط تعاملات مرورگر به‌صورت فایل‌های GIF |

### مجوزهای سطح سایت

افزونه‌ی Chrome دسترسی را به‌صورت جداگانه برای هر سایت مدیریت می‌کند. هر زمان که بخواهید می‌توانید از طریق پنجره‌ی بازشوی افزونه، دسترسی به سایت‌های مشخص را اعطا یا لغو کنید. Claude Code فقط با سایت‌هایی تعامل می‌کند که صراحتاً به آن‌ها اجازه داده‌اید.

### نحوه کار

Claude Code مرورگر را در یک پنجره‌ی قابل مشاهده کنترل می‌کند — می‌توانید اقدامات را در زمان واقعی تماشا کنید. وقتی مرورگر به صفحه‌ی ورود یا CAPTCHA برمی‌خورد، Claude مکث می‌کند و منتظر می‌ماند تا شما آن را به‌صورت دستی انجام دهید و سپس ادامه می‌دهد.

### محدودیت‌های شناخته‌شده

- **پشتیبانی مرورگر**: Chrome و Edge؛ Claude Code در سایر مرورگرهای مبتنی بر Chromium مانند Brave، Arc، Vivaldi و Opera نیز متصل می‌شود
- **WSL**: در زیرسیستم ویندوز برای لینوکس در دسترس نیست
- **ارائه‌دهندگان شخص ثالث**: با ارائه‌دهندگان API مانند Bedrock، Vertex یا Foundry پشتیبانی نمی‌شود
- **بیکار شدن service worker**: ممکن است service worker افزونه‌ی Chrome در نشست‌های طولانی بیکار شود

> **نکته**: یکپارچه‌سازی با Chrome یک ویژگی بتا است. پشتیبانی مرورگر ممکن است در نسخه‌های آینده گسترش یابد.

## کنترل از راه دور

کنترل از راه دور به شما اجازه می‌دهد یک نشست Claude Code را که به‌صورت محلی در حال اجراست، از گوشی، تبلت یا هر مرورگری ادامه دهید. نشست محلی شما روی دستگاه خودتان به کار ادامه می‌دهد — هیچ چیز به فضای ابری منتقل نمی‌شود. در پلن‌های Pro، Max، Team و Enterprise در دسترس است (v2.1.51+). اگر نقش‌های سفارشی Enterprise دسترسی شما را تعیین می‌کنند، به نقشي با هر دو اجازهٔ نشست‌های ابری و اجازهٔ **Claude Code remote control** نیاز دارید.

کنترل از راه دور دیگر **پیش‌نمایش پژوهشی نیست** — این برچسب در هفته‌ی ۳۴ سال ۲۰۲۶ حذف شد. هر دستگاهی که `claude remote-control` را اجرا می‌کند اکنون به‌عنوان یک **کارت دستگاه** در تب Code اپ Claude ظاهر می‌شود، بنابراین می‌توانید نشستی را روی آن دستگاه مستقیماً از گوشی خود شروع کنید، به‌جای اینکه ابتدا روی دستگاه نشستی شروع کنید و سپس به آن متصل شوید.

### شروع کنترل از راه دور

**از CLI**:

```bash
# شروع با نام نشست پیش‌فرض
claude remote-control

# شروع با یک نام سفارشی
claude remote-control --name "Auth Refactor"
```

**از داخل یک نشست**:

```
/remote-control
/remote-control "Auth Refactor"
```

**فلگ‌های موجود**:

| فلگ | توضیح |
|------|-------------|
| `--name "title"` | عنوان سفارشی نشست برای شناسایی آسان |
| `--verbose` | نمایش لاگ‌های تفصیلی اتصال |

> **توجه (v2.1.300)**: `claude remote-control` دیگر `--sandbox` یا `--no-sandbox` را نمی‌پذیرد (این دو هرگز تأثیری نداشتند؛ ارسال هرکدام اکنون با خطا خارج می‌شود). برای سندباکس کردن نشست‌های کنترل از راه دور، `sandbox.enabled` را در یک فایل تنظیمات مشخص کنید.

### اتصال به یک نشست

سه روش برای اتصال از دستگاه دیگر وجود دارد:

1. **URL نشست** — هنگام شروع نشست در ترمینال چاپ می‌شود؛ آن را در هر مرورگری باز کنید
2. **کد QR** — پس از شروع، `spacebar` را فشار دهید تا یک کد QR قابل اسکن نمایش داده شود
3. **یافتن با نام** — نشست‌های خود را در claude.ai/code یا در اپ موبایل Claude (iOS/Android) مرور کنید

### امنیت

- **هیچ پورت ورودی** روی دستگاه شما باز نمی‌شود
- **فقط HTTPS خروجی** روی TLS
- **اعتبارنامه‌های محدود** — چندین توکن کوتاه‌عمر با دامنه‌ی محدود
- **جداسازی نشست** — هر نشست راه دور مستقل است

### کنترل از راه دور در برابر Claude Code روی وب

| جنبه | کنترل از راه دور | Claude Code روی وب |
|--------|---------------|-------------------|
| **اجرا** | روی دستگاه شما اجرا می‌شود | روی فضای ابری Anthropic اجرا می‌شود |
| **ابزارهای محلی** | دسترسی کامل به سرورهای MCP محلی، فایل‌ها و CLI | هیچ وابستگی محلی ندارد |
| **مورد استفاده** | ادامه‌ی کار محلی از دستگاه دیگر | شروع تازه از هر مرورگری |

### محدودیت‌ها

- یک نشست راه دور به‌ازای هر فرآیند تعاملی Claude Code — حالت سرور (`claude remote-control`) به‌طور همزمان به چند نشست سرویس می‌دهد (`--capacity`، پیش‌فرض ۳۲)
- ترمینال باید روی دستگاه میزبان باز بماند
- اگر شبکه در دسترس نباشد، حالت سرور پس از حدود ۱۰ دقیقه خارج می‌شود؛ یک نشست تعاملی به تلاش ادامه می‌دهد و وقتی شبکه برگردد دوباره متصل می‌شود

### موارد استفاده

- کنترل Claude Code از یک دستگاه موبایل یا تبلت در زمانی که دور از میز خود هستید
- استفاده از رابط کاربری غنی‌تر claude.ai در حالی که اجرای ابزارها به‌صورت محلی حفظ می‌شود
- مرور سریع کد در حال حرکت با محیط توسعه‌ی محلی کامل خود

### اعلان‌های پوش (v2.1.110)

وقتی کنترل از راه دور فعال است و «Push when Claude decides» در `/config` روشن است، Claude می‌تواند اعلان‌های پوش موبایل به گوشی شما بفرستد — مثلاً وقتی یک وظیفه‌ی طولانی کامل می‌شود یا به ورودی شما نیاز دارد.

برای فعال‌سازی:
1. کنترل از راه دور را فعال کنید: `/remote-control` یا `claude --rc`
2. `/config` را باز کنید و **Push when Claude decides** را فعال کنید

اعلان‌های پوش نیازمند اشتراک Claude و اپ موبایل Claude هستند.

### غیرفعال‌سازی کنترل از راه دور (`disableRemoteControl`، v2.1.128+)

مدیران در پلن‌های Team یا Enterprise می‌توانند کنترل از راه دور را کاملاً با تنظیم `disableRemoteControl` مسدود کنند. وقتی `true` باشد، هم `claude remote-control` و هم `/remote-control` از شروع خودداری می‌کنند.

```json
{
  "disableRemoteControl": true
}
```

این تنظیم در دامنه‌ی **مدیریت‌شده/سیاست** رعایت می‌شود (مثلاً `/Library/Application Support/ClaudeCode/managed-settings.json` در macOS) تا کاربران منفرد نتوانند آن را بازنویسی کنند. زمانی مفید است که اجرای فقط-محلی باید در سراسر سازمان اعمال شود.

> **وقتی کنترل از راه دور به‌صورت خودکار توسط سطوح کلید API غیرفعال می‌شود (v2.1.139)**: کنترل از راه دور هر زمان که یکی از موارد زیر تنظیم شده باشد **بی‌صدا غیرفعال می‌شود**، حتی اگر همزمان با claude.ai وارد شده باشید:
>
> - `ANTHROPIC_API_KEY`
> - `ANTHROPIC_AUTH_TOKEN`
> - `apiKeyHelper` (settings.json)
>
> همین شرط [`/schedule`](#وظایف-زمان‌بندی‌شده)، اتصال‌دهنده‌های MCP در claude.ai و ترجیحات اعلان را غیرفعال می‌کند — هر چهار سطح پل‌شده به claude.ai به این وابسته‌اند که ورود OAuth اعتبارنامه‌ی فعال باشد. کلید API را حذف کنید (یا روی سطح OAuth پلن Pro/Max اجرا کنید) تا از این ویژگی‌ها استفاده کنید.

## نشست‌های وب

نشست‌های وب به شما اجازه می‌دهند Claude Code را مستقیماً در مرورگر در claude.ai/code اجرا کنید، یا نشست‌های وب را از CLI ایجاد کنید.

### ایجاد یک نشست وب

```bash
# ایجاد یک نشست وب جدید از CLI
claude --cloud "implement the new API endpoints"   # --remote نام مستعار منسوخ است
```

این کار یک نشست Claude Code روی claude.ai شروع می‌کند که می‌توانید از هر مرورگری به آن دسترسی داشته باشید.

### ازسرگیری نشست‌های وب به‌صورت محلی

اگر نشستی را روی وب شروع کرده‌اید و می‌خواهید آن را به‌صورت محلی ادامه دهید:

```bash
# ازسرگیری یک نشست وب در ترمینال محلی — یک انتخاب‌گر از نشست‌های وب شما باز می‌کند
claude --teleport
```

یا از داخل یک REPL تعاملی:

```text
/teleport
```

`/tp` نام مستعار `/teleport` است. هر دو نیازمند اشتراک claude.ai هستند. نشست‌های ابری
یک راهنمای `/teleport` نشان می‌دهند که نحوه‌ی ادامه‌ی محلی را توضیح می‌دهد (v2.1.223).

> **برگرفته از changelog**: تغییرات نسخه‌ی v2.1.223 یک شکل آرگومانی نشان می‌دهد،
> `claude --teleport <session id>`، که مستقیماً به یک نشست شناخته‌شده می‌پرد. مرجع CLI
> تنها شکل انتخاب‌گر خالی را مستند کرده است، بنابراین `claude --teleport` را ترجیح دهید مگر
> اینکه از قبل شناسه‌ی نشست را در دست داشته باشید.

### موارد استفاده

- شروع کار روی یک دستگاه و ادامه‌ی آن روی دستگاه دیگر
- اشتراک‌گذاری URL یک نشست با اعضای تیم
- استفاده از رابط کاربری وب برای مرور تفاوت‌های بصری، سپس جابه‌جایی به ترمینال برای اجرا

## اپلیکیشن دسکتاپ

اپلیکیشن دسکتاپ Claude Code یک برنامه‌ی مستقل با مرور تفاوت‌های بصری، نشست‌های موازی و اتصال‌دهنده‌های یکپارچه ارائه می‌دهد. برای macOS و Windows در دسترس است (پلن‌های Pro، Max، Team و Enterprise).

### نصب

از [claude.ai](https://claude.ai) نسخه‌ی مناسب پلتفرم خود را دانلود کنید:
- **macOS**: بیلد یونیورسال (Apple Silicon و Intel)
- **Windows**: نصب‌کننده‌های x64 و ARM64 موجود است

برای دستورالعمل‌های راه‌اندازی، [شروع سریع دسکتاپ](https://code.claude.com/docs/en/desktop-quickstart) را ببینید.

### واگذاری از CLI

| ویژگی | توضیح |

| حالت | رفتار |
|------|----------|
| **دستی** (پیش‌فرض) | مرور و تأیید هر ویرایش و فرمان |
| **پذیرش ویرایش‌ها** | ویرایش فایل‌ها به‌صورت خودکار تأیید می‌شود؛ فرمان‌ها نیازمند تأیید دستی هستند |
| **برنامه** | مرور رویکرد پیش از اعمال هر تغییری |
| **خودکار** | بدون پرامپت‌های روتین اجرا می‌شود؛ یک طبقه‌بند پس‌زمینه ابتدا اقدامات را بررسی می‌کند |
| **عبور از مجوزها** | اجرای خودکار (فقط سندباکس، تحت کنترل مدیر) |

### ویژگی‌های سازمانی

- **کنسول مدیر**: کنترل دسترسی تب Code و تنظیمات مجوز برای سازمان
- **استقرار MDM**: استقرار از طریق MDM در macOS یا MSIX در Windows
- **یکپارچه‌سازی SSO**: الزام ورود یکپارچه برای اعضای سازمان
- **تنظیمات مدیریت‌شده**: مدیریت متمرکز پیکربندی تیم و در دسترس بودن مدل

## فهرست وظایف

ویژگی فهرست وظایف، پیگیری پایدار وظایف را فراهم می‌کند که از فشرده‌سازی‌های زمینه جان سالم به در می‌برد (زمانی که تاریخچه‌ی گفتگو برای جا شدن در پنجره‌ی زمینه کوتاه می‌شود).

### روشن/خاموش کردن فهرست وظایف

در طول یک نشست، `Ctrl+T` را فشار دهید تا نمای فهرست وظایف روشن یا خاموش شود.

### وظایف پایدار

وظایف در میان فشرده‌سازی‌های زمینه پایدار می‌مانند و تضمین می‌کنند که اقلام کاری طولانی‌مدت هنگام کوتاه شدن زمینه‌ی گفتگو از دست نروند. این امر به‌ویژه برای پیاده‌سازی‌های پیچیده و چندمرحله‌ای مفید است.

### پوشه‌های نام‌دار وظایف

از متغیر محیطی `CLAUDE_CODE_TASK_LIST_ID` برای ایجاد پوشه‌های نام‌دار وظایف که میان نشست‌ها به اشتراک گذاشته می‌شوند استفاده کنید:

```bash
export CLAUDE_CODE_TASK_LIST_ID=my-project-sprint-3
```

این امکان به چندین نشست اجازه می‌دهد تا فهرست وظایف یکسانی را به اشتراک بگذارند و برای گردش‌کارهای تیمی یا پروژه‌های چندنشستی مفید است.

## درخت‌های کاری گیت

درخت‌های کاری گیت به شما اجازه می‌دهند Claude Code را در یک درخت کاری جداگانه اجرا کنید و بدون stash یا جابه‌جایی شاخه، به‌صورت موازی روی شاخه‌های مختلف کار کنید.

### شروع در یک درخت کاری

```bash
# اجرای Claude Code در یک درخت کاری جداگانه
claude --worktree
# یا
claude -w
```

### محل درخت کاری

درخت‌های کاری در مسیر زیر ایجاد می‌شوند:
```
<repo>/.claude/worktrees/<name>
```

### چک‌اوت پراکنده برای مونوریپوها

از تنظیم `worktree.sparsePaths` برای انجام چک‌اوت پراکنده در مونوریپوها استفاده کنید تا مصرف دیسک و زمان کلون کاهش یابد:

```json
{
  "worktree": {
    "sparsePaths": ["packages/my-package", "shared/"]
  }
}
```

### مرجع شاخهٔ پایه (`worktree.baseRef`)

**`worktree.baseRef`** (افزوده‌شده در v2.1.133) — کنترل می‌کند که `claude --worktree` از `origin/<default>` یا از `HEAD` محلی شاخه بگیرد.

- `"fresh"` (پیش‌فرض) — شاخه‌گیری از `origin/<default-branch>` با نادیده‌گرفتن کامیت‌های محلی ارسال‌نشده. **این رفتار معرفی‌شده در v2.1.128 را برمی‌گرداند**، بنابراین کاربرانی که پس از v2.1.128 به شاخه‌گیری از HEAD محلی تکیه کرده‌اند باید دوباره آن را فعال کنند.
- `"head"` — شاخه‌گیری از `HEAD` محلی با حفظ کامیت‌های ارسال‌نشده.

در `~/.claude/settings.json` تنظیم کنید:

```json
{ "worktree": { "baseRef": "head" } }
```

### جداسازی نشست پس‌زمینه (`worktree.bgIsolation`)

**`worktree.bgIsolation`** (افزوده‌شده در v2.1.143) — کنترل می‌کند که نشست‌های پس‌زمینه (مثلاً از `/bg`، `claude --bg` یا نمای ایجنت) درخت کاری اختصاصی خود را بگیرند یا مستقیماً نسخهٔ کاری پیش‌زمینه را ویرایش کنند.

- *(پیش‌فرض)* — نشست‌های پس‌زمینه یک درخت کاری جداگانه زیر `<repo>/.claude/worktrees/` ایجاد می‌کنند، دقیقاً مثل `--worktree`.
- `"none"` — نشست‌های پس‌زمینه مستقیماً نسخهٔ کاری فعلی را ویرایش می‌کنند. زمانی از این استفاده کنید که درخت‌های کاری غیرعملی هستند (مثلاً آرتیفکت‌های سنگین بیلد بومی) یا وقتی یک ایجنت پس‌زمینه باید ویرایش‌ها را با نشست پیش‌زمینه هماهنگ کند.

```json
{ "worktree": { "bgIsolation": "none" } }
```

بده‌بستان: `"none"` تور ایمنی جداسازی درخت کاری را حذف می‌کند — ویرایش‌های هم‌زمان از نشست‌های پس‌زمینه و پیش‌زمینه می‌توانند در نسخهٔ کاری زنده تعارض ادغام ایجاد کنند.

### ابزارها و هوک‌های درخت کاری

| مورد | توضیح |
|------|-------------|
| `EnterWorktree` | ابزاری برای ورود به یک درخت کاری؛ از v2.1.157 می‌تواند در میانهٔ نشست بین درخت‌های کاری مدیریت‌شده توسط Claude جابه‌جا شود |
| `ExitWorktree` | ابزاری برای خروج و پاک‌سازی درخت کاری فعلی |
| `WorktreeCreate` | رویداد هوکی که هنگام ایجاد یک درخت کاری اجرا می‌شود |
| `WorktreeRemove` | رویداد هوکی که هنگام حذف یک درخت کاری اجرا می‌شود |

از v2.1.157، درخت‌های کاری مدیریت‌شده توسط Claude هنگام پایان کار ایجنت قفل‌نشده باقی می‌مانند تا `git worktree remove`/`prune` بتوانند آن‌ها را پاک کنند.

### پاک‌سازی خودکار

وقتی از یک نشست تعاملی درخت کاری خارج می‌شوید و درخت کاری هیچ تغییری ندارد، Claude آن را و شاخه‌اش را خودکار حذف می‌کند (یک نشست نام‌دار اول می‌پرسد). اگر تغییری یا commit جدیدی داشته باشد، یا شاخهٔ دیگری با commit جدید در آن checkout شده باشد (از v2.1.304)، Claude می‌پرسد که نگهش دارد یا حذفش کند. اجراهای غیرتعاملی `-p` درخت‌های کاری خود را سر جایشان می‌گذارند.

### موارد استفاده

- کار روی یک شاخهٔ ویژگی بدون دست‌زدن به شاخهٔ اصلی
- اجرای تست‌ها به‌صورت جداگانه بدون تأثیر بر پوشهٔ کاری
- امتحان تغییرات آزمایشی در محیطی یک‌بارمصرف
- چک‌اوت پراکندهٔ بسته‌های خاص در مونوریپوها برای راه‌اندازی سریع‌تر

## سندباکس‌کردن

سندباکس‌کردن جداسازی فایل‌سیستم و شبکه در سطح سیستم‌عامل را برای دستورهای Bash که Claude Code اجرا می‌کند فراهم می‌کند. این مکمل قواعد مجوز است و یک لایهٔ امنیتی اضافی ارائه می‌دهد.

### فعال‌کردن سندباکس

**دستور اسلش** (انتخاب شما را برای این پروژه در `.claude/settings.local.json` ذخیره می‌کند):
```text
/sandbox
```

**فایل تنظیمات** (همهٔ پروژه‌ها): `"sandbox": { "enabled": true }` را در `~/.claude/settings.json` تنظیم کنید.

**به‌ازای هر نشست**، بدون نوشتن فایل تنظیمات:
```bash
claude --settings '{"sandbox": {"enabled": true}}'
```

> هیچ فلگ `claude --sandbox` / `--no-sandbox` وجود ندارد. از v2.1.300، ارسال آن‌ها به `claude remote-control` با خطا خارج می‌شود.

### تنظیمات پیکربندی

| تنظیم | توضیح |
|---------|-------------|
| `sandbox.enabled` | فعال یا غیرفعال‌کردن سندباکس |
| `sandbox.failIfUnavailable` | در صورت ناتوانی در فعال‌سازی سندباکس، شکست بخورد |
| `sandbox.filesystem.allowWrite` | مسیرهای مجاز برای دسترسی نوشتن |
| `sandbox.filesystem.allowRead` | مسیرهای مجاز برای دسترسی خواندن |
| `sandbox.filesystem.denyRead` | مسیرهای ممنوع برای دسترسی خواندن |
| `sandbox.network.allowedDomains` | دامنه‌هایی که فرایندهای اجراشده توسط Bash مجاز به دسترسی به آن‌ها هستند (از wildcard `*.` پشتیبانی می‌کند) |
| `sandbox.network.deniedDomains` | دامنه‌هایی که باید مسدود شوند، حتی وقتی wildcard مربوط به `allowedDomains` در غیر این صورت آن‌ها را مجاز می‌کرد (v2.1.113+) |
| `sandbox.network.strictAllowlist` | (v2.1.219) رد میزبان‌های غیرمجاز برای دستورهای سندباکس‌شده بدون پرسیدن |
| `sandbox.enableWeakerNetworkIsolation` | فعال‌کردن جداسازی شبکهٔ ضعیف‌تر در macOS |
| `sandbox.bwrapPath` | (v2.1.133+، Linux/WSL) مسیر باینری `bubblewrap`. پیش‌فرض: جستجو در `$PATH`. |
| `sandbox.socatPath` | (v2.1.133+، Linux/WSL) مسیر باینری `socat`. پیش‌فرض: جستجو در `$PATH`. |
| `sandbox.credentials` | (v2.1.187+) مسدودکردن دستورهای سندباکس‌شده از خواندن فایل‌های اعتبارنامه و متغیرهای محیطی محرمانه. |
| `sandbox.allowAppleEvents` | (v2.1.181+، macOS) فعال‌کردن اجازه به دستورهای سندباکس‌شده برای ارسال Apple Events. |
| `sandbox.filesystem.disabled` | (v2.1.216+) نادیده‌گرفتن کامل جداسازی فایل‌سیستم در حالی که جداسازی شبکه اعمال می‌شود — زمانی مفید است که سندباکس فایل ابزارها را مختل می‌کند اما کنترل خروج شبکه باید فعال بماند. فقط از تنظیمات کاربر، تنظیمات مدیریت‌شده یا `--settings` پذیرفته می‌شود؛ تنظیمات پروژه نمی‌تواند آن را تعیین کند. |
| `sandbox.excludedCommands` | الگوهای دستور با نحو قواعد `Bash(...)`، مثل `"docker compose *"`، که بیرون از سندباکس اجرا می‌شوند و از جریان مجوز عادی می‌گذرند. از v2.1.309، وقتی سندباکس فعال است اما نمی‌تواند اجرا شود، پیش از نوشتن در مسیرهای فهرست نوشتن سندباکس می‌پرسند |
| `sandbox.allowNestedUserNamespaces` | (v2.1.305+، Linux/WSL2) اجازهٔ ساخت user namespace به دستورهای سندباکس‌شده (سندباکس‌های Chromium/Electron، bubblewrap تودرتو، `unshare`). این یک مرز امنیتی را خاموش می‌کند؛ فقط از تنظیمات کاربر یا مدیریت‌شده یا `--settings` پذیرفته می‌شود. برای Podman بدون root به‌جایش از `excludedCommands` استفاده کنید |

**مسیرهای باینری Linux/WSL** (v2.1.133+) — Claude Code را به محل‌های نصب غیراستاندارد اشاره دهید:

```json
{
  "sandbox": {
    "bwrapPath": "/opt/bubblewrap/bin/bwrap",
    "socatPath": "/opt/socat/bin/socat"
  }
}
```

نمونه‌ای از اولویت `deniedDomains` بر یک wildcard گسترده (v2.1.113+):

```json
{
  "sandbox": {
    "network": {
      "allowedDomains": ["*.example.com"],
      "deniedDomains": ["evil.example.com"]
    }
  }
}
```

wildcard به همه‌چیز روی `example.com` اجازهٔ عبور می‌دهد، اما `deniedDomains` همچنان میزبان مشخص‌شده را مسدود می‌کند.

> **توجه** (v2.1.243): پرامپت مجوز ابزار Bash سندباکس‌شده **دیگر میزبان‌های شبکهٔ مجاز را فهرست نمی‌کند**. Claude صرفاً درخواست را امتحان می‌کند و شما هر میزبان جدید را هنگام ظاهر شدن تأیید می‌کنید — پس انتظار نداشته باشید که پرامپت فهرست مجاز را از قبل نشان دهد. همین نسخه همچنین دیگر جزئیات نقض شبکه را حذف نمی‌کند وقتی دستور مسدودشده با کد `0` خارج می‌شود؛ بنابراین یک موفقیت به‌ظاهر بی‌صدا اکنون همچنان گزارش می‌دهد چه چیزی مسدود شده است.

### پوشاندن اعتبارنامه‌ها (v2.1.221، v2.1.224)

> **برگرفته از تغییرات**: این گزینه‌های `sandbox.credentials` از ورودی‌های تغییرات v2.1.221 و
> v2.1.224 می‌آیند؛ مرجع تنظیمات هنوز جزئیات آن‌ها را ارائه نمی‌دهد.

پیش از v2.1.221، `sandbox.credentials` فقط می‌توانست یک فایل اعتبارنامه را `deny` کند — یک دستور
سندباکس‌شده که به اعتبارنامه نیاز داشت به‌سادگی شکست می‌خورد. `mode: "mask"` دستور را در حال کار نگه می‌دارد
بدون افشای راز: فرایند سندباکس‌شده یک نسخهٔ **نگهبان (sentinel)** از فایل را می‌خواند،
و پروکسی سندباکس مقدار واقعی را در مسیر خروج به شبکه جایگزین می‌کند.

```json
{
  "sandbox": {
    "network": { "tlsTerminate": true },
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "mask" }
      ]
    }
  }
}
```

| قابلیت | از نسخه | چه کاری انجام می‌دهد |
|---|---|---|
| `mode: "mask"` برای **فایل‌های** اعتبارنامه | v2.1.221 | دستورهای سندباکس‌شده یک sentinel می‌خوانند؛ پروکسی مقدار واقعی را هنگام خروج جایگزین می‌کند. **فقط Linux و WSL** — در macOS پوشاندن فایل به `deny` بازمی‌گردد. |
| `extract` / `onExtractNoMatch` | v2.1.224 | پوشاندن یک فیلد درون یک مقدار محیطی ساختاریافته به‌جای کل متغیر، و تصمیم‌گیری دربارهٔ آنچه هنگام عدم تطابق الگو رخ می‌دهد. |
| `decode: "jwt"` با `maskClaims` | v2.1.224 | رمزگشایی یک JWT و پوشاندن فقط claimهای نام‌برده‌شده، با باقی‌گذاشتن بقیه به‌صورت خوانا. |
| `awsPairs` / `sigv4` | v2.1.224 | امضای مجدد درخواست‌های AWS SigV4 در پروکسی پس از جایگزینی کلید دسترسی واقعی. |

**دو محدودیت که آسان است از دست بروند:**

- همهٔ پوشاندن‌ها نیازمند `network.tlsTerminate` هستند — پروکسی باید داخل درخواست را ببیند تا
  مقدار را جایگزین کند.
- این گزینه‌ها **فقط** از تنظیمات کاربر، تنظیمات مدیریت‌شده یا `--settings` پذیرفته می‌شوند.
  تنظیمات پروژه نمی‌تواند پوشاندن را فعال کند یا تغییر دهد چه چیزی پوشانده شود.

### نمونهٔ پیکربندی

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "filesystem": {
      "allowWrite": ["/Users/me/project"],
      "allowRead": ["/Users/me/project", "/usr/local/lib"],
      "denyRead": ["/Users/me/.ssh", "/Users/me/.aws"]
    }
  }
}
```

### نحوهٔ کار

- دستورهای Bash در محیطی سندباکس‌شده با دسترسی محدود به فایل‌سیستم اجرا می‌شوند
- دسترسی شبکه می‌تواند جداسازی شود تا از اتصال‌های خارجی ناخواسته جلوگیری شود
- در کنار قواعد مجوز برای دفاع لایه‌ای کار می‌کند
- در macOS، Seatbelt همهٔ اتصال‌های شبکه را مسدود می‌کند به‌جز اتصال به پروکسی سندباکس؛ `sandbox.enableWeakerNetworkIsolation` آن جداسازی را **ضعیف** می‌کند و فقط برای ابزارهایی مانند CLIهای Go پشت پروکسی MITM `httpProxyPort` است

### موارد استفاده

- اجرای ایمن کد غیرقابل‌اعتماد یا تولیدشده
- جلوگیری از تغییرات تصادفی در فایل‌های بیرون پروژه
- محدودکردن دسترسی شبکه در طول وظایف خودکار

## تنظیمات مدیریت‌شده (سازمانی)

تنظیمات مدیریت‌شده به مدیران سازمانی امکان می‌دهد پیکربندی Claude Code را در سراسر سازمان با استفاده از ابزارهای مدیریت بومی پلتفرم مستقر کنند.

### روش‌های استقرار

| پلتفرم | روش | از نسخه |
|----------|--------|-------|
| macOS | فایل‌های plist مدیریت‌شده (MDM) | v2.1.51+ |
| Windows | رجیستری ویندوز | v2.1.51+ |
| چندسکویی | فایل‌های پیکربندی مدیریت‌شده | v2.1.51+ |
| چندسکویی | drop-inهای مدیریت‌شده (پوشهٔ `managed-settings.d/`) | v2.1.83+ |

### drop-inهای مدیریت‌شده

از v2.1.83، مدیران می‌توانند چندین فایل تنظیمات مدیریت‌شده را در پوشهٔ `managed-settings.d/` مستقر کنند. فایل‌ها به ترتیب حروف الفبا ادغام می‌شوند و پیکربندی ماژولار در تیم‌ها را ممکن می‌سازند. این پوشه در کنار `managed-settings.json` در پوشهٔ سیستم قرار دارد (`/Library/Application Support/ClaudeCode/` در macOS، `/etc/claude-code/` در Linux، `C:\Program Files\ClaudeCode\` در Windows):

```
/etc/claude-code/managed-settings.d/
  00-org-defaults.json
  10-team-policies.json
  20-project-overrides.json
```

### تنظیمات مدیریت‌شدهٔ موجود

| تنظیم | توضیح |
|---------|-------------|
| `permissions.disableBypassPermissionsMode` | روی `"disable"` تنظیم کنید تا کاربران نتوانند حالت عبور از مجوزها را فعال کنند |
| `availableModels` | محدودکردن مدل‌هایی که کاربران می‌توانند انتخاب کنند |
| `enforceAvailableModels` | (v2.1.175) وقتی `true` باشد، فهرست مجاز `availableModels` *همچنین* مدل **Default** را محدود می‌کند — اگر پیش‌فرض پیکربندی‌شده در فهرست نباشد، Claude Code به اولین مدل مجاز بازمی‌گردد. تنظیمات کاربر و پروژه دیگر نمی‌توانند فهرست `availableModels` مدیریت‌شده را گسترش دهند. |
| `allowedChannelPlugins` | کنترل اینکه کدام پلاگین‌های کانال مجاز هستند |
| `autoMode.environment` | پیکربندی زیرساخت مورداعتماد برای حالت خودکار |
| `workflowSizeGuideline` | (v2.1.219) تعیین [راهنمای اندازهٔ گردش‌کار پویا](#گردش‌کارهای-پویا) به‌صورت توصیه‌ای. از هر فایل تنظیماتی قابل خواندن است، نه فقط تنظیمات مدیریت‌شده؛ تا زمانی که یکی آن را تعیین کند، ردیف **Dynamic workflow size** از `/config` پنهان می‌شود |
| `wslInheritsWindowsSettings` | فقط Windows/WSL (v2.1.118+): وقتی `true` باشد، Claude Code در حال اجرا داخل WSL تنظیمات مدیریت‌شده را از میزبان ویندوز به ارث می‌برد تا سیاست‌های سازمانی مستقرشده از طریق Registry/MDM به‌طور یکنواخت در پوسته‌های Windows و WSL اعمال شوند |
| `parentSettingsBehavior` | (v2.1.133+، سطح مدیر) کنترل نحوهٔ ادغام `managedSettings` در SDK با تنظیمات فرایند والد. `"first-wins"` اولویت موجود را حفظ می‌کند (تنظیم قبلی در تعارض برنده می‌شود)؛ `"merge"` مقادیر را عمیقاً ادغام می‌کند. |
| سیاست‌های سفارشی | سیاست‌های مجوز و ابزار مخصوص سازمان |

### نمونه: plist در macOS

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>permissions</key>
  <dict>

    <string>disable</string>
  </dict>
  <key>availableModels</key>
  <array>
    <string>claude-sonnet-4-6</string>
    <string>claude-haiku-4-5</string>
  </array>
</dict>
</plist>
```

## پیکربندی و تنظیمات

### محل‌های فایل پیکربندی

1. **تنظیمات کاربر**: `~/.claude/settings.json`
2. **تنظیمات پروژه**: `.claude/settings.json` (ثبت‌شده در مخزن)
3. **تنظیمات محلی پروژه**: `.claude/settings.local.json` (ثبت‌نشده در مخزن)
4. **تنظیمات مدیریت‌شده**: `managed-settings.json` در پوشهٔ سیستم (نگاه کنید به [تنظیمات مدیریت‌شده](#تنظیمات-مدیریت‌شده-سازمانی))

### نمونهٔ کامل پیکربندی

**پیکربندی اصلی قابلیت‌های پیشرفته** (`.claude/settings.json`):

```json
{
  "permissions": {
    "defaultMode": "manual"
  },
  "hooks": {
    "PreToolUse": [
      { "matcher": "Edit", "hooks": [{ "type": "command", "command": "~/.claude/hooks/eslint-fix.sh" }] }
    ],
    "PostToolUse": [
      { "matcher": "Write", "hooks": [{ "type": "command", "command": "~/.claude/hooks/security-scan.sh" }] }
    ]
  }
}
```

اسکریپت‌های هوک ورودی ابزار را به‌صورت JSON روی stdin دریافت می‌کنند (برای نمونه `tool_input.file_path`)؛ هیچ جایگزینی برای `${file_path}` وجود ندارد. سرورهای MCP یک کلید تنظیمات نیستند — آن‌ها را در `.mcp.json` در ریشه پروژه تعریف کنید:

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": { "Authorization": "Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}" }
    }
  }
}
```

**نمونه پیکربندی گسترده:**

```json
{
  "permissions": {
    "defaultMode": "manual",
    "allow": ["Bash(git log:*)", "Read"],
    "deny": ["Bash(rm -rf:*)"]
  },

  "hooks": {
    "PreToolUse": [{ "matcher": "Edit", "hooks": [{ "type": "command", "command": "~/.claude/hooks/eslint-fix.sh" }] }],
    "PostToolUse": [{ "matcher": "Write", "hooks": [{ "type": "command", "command": "~/.claude/hooks/security-scan.sh" }] }],
    "Stop": [{ "hooks": [{ "type": "command", "command": "~/.claude/hooks/notify.sh" }] }]
  }
}
```

سرور MCP گیت‌هاب برای این راه‌اندازی در `.mcp.json` قرار می‌گیرد، همان‌طور که در بالا نشان داده شد.

### تنظیمات اضافی به‌ازای هر کاربر

این کلیدها در `~/.claude/settings.json` (یا `.claude/settings.json` پروژه) قرار می‌گیرند و رفتار تعاملی را برای کاربر به‌صورت فردی کنترل می‌کنند:

| تنظیم | توضیح |
|---------|-------------|
| `askUserQuestionTimeout` | یک گفت‌وگوی بی‌پاسخ `AskUserQuestion` را پس از یک بازه بی‌کاری به‌طور خودکار ادامه می‌دهد. از **v2.1.200** به بعد، گفت‌وگوها به‌طور پیش‌فرض دیگر خودکار ادامه نمی‌یابند — برای بازگشت به ادامه خودکار زمان‌دار، این را تنظیم کنید. |
| `enableArtifact` | فعال یا غیرفعال کردن ابزار Artifact به‌ازای هر کاربر (v2.1.196). |
| `crossSessionInbound` | (v2.1.224) نحوه برخورد با [پیام‌های بین‌نشستی](#پیام‌رسانی-بین-نشست‌ها) ورودی — `"accept"`، `"hold"` یا `"refuse"`. مقادیر پروژه و محلی فقط زمانی اعمال می‌شوند که در نردبان `accept < hold < refuse` *سخت‌گیرانه‌تر* باشند. از v2.1.232 در `/config` با عنوان «پیام‌های سایر نشست‌های شما» نمایش داده می‌شود. |
| `dialogExpiry` | (v2.1.224) مدت زمانی که یک گفت‌وگوی بی‌پاسخ باز می‌ماند. پیش‌فرض `"5m"`؛ مقادیر `"60s"`، `"5m"`، `"10m"` یا `"never"` را می‌پذیرد. با `CLAUDE_CODE_USER_DIALOG_TIMEOUT_MS` بازنویسی می‌شود. از v2.1.232 در `/config` با عنوان «انقضای گفت‌وگو» نمایش داده می‌شود. |
| `modelPicker` | (v2.1.243) انتخاب کنید که انتخاب‌گر `/model` کدام مدل‌ها را فهرست کند، با ترتیب و برچسب‌های دلخواه خودتان. یکی از معدود تنظیماتی که در لایه‌های تنظیمات **جایگزین می‌شود نه ادغام** — مقدار نزدیک‌ترین دامنه کاملاً برنده است. |
| `promptCacheTtl` | (v2.1.243) عمر کش پرامپت را برای گفت‌وگوی اصلی انتخاب کنید. |
| `subagentPromptCacheTtl` | (v2.1.243) همان انتخاب برای زیرایجنت‌ها و سایر درخواست‌های خارج از گفت‌وگوی اصلی. |
| `modelPricing` | (v2.1.243) **تنظیم مدیریت‌شده.** نرخ‌های قراردادی سازمان شما را تأمین می‌کند تا `/cost`، خط وضعیت و تله‌متری به‌جای قیمت فهرست، همان نرخ‌ها را گزارش کنند. |
| `keybindingFlavor` | **از v2.1.261 منسوخ شده و هیچ اثری ندارد.** کلیدهای ویرایش واژه در پرامپت همیشه از قواعد readline پیروی می‌کنند، همانند Bash: `Ctrl+W` تا فاصله قبلی را حذف می‌کند، `Alt+F` و `Alt+D` در پایان واژه متوقف می‌شوند و نشانه‌گذاری، واژه‌ها را جدا می‌کند. Claude Code هنوز کلید را می‌پذیرد، بنابراین فایل تنظیماتی که آن را تنظیم کند معتبر می‌ماند. (در v2.1.238–v2.1.260 بین `"classic"` و `"readline"` انتخاب می‌کرد.) |
| `spellcheck` | (v2.1.235) واژه‌های غلط املایی را در ورودی پرامپت زیرخط‌دار می‌کند، با استفاده از هر یک از `aspell`، `hunspell` یا `ispell` که روی `PATH` شما باشد و به همین ترتیب امتحان می‌شوند. مقدارشیء است — `{"enabled": true, "language": "en_GB"}` — و به‌طور پیش‌فرض خاموش است. **فقط از تنظیمات کاربر، پرچم `--settings` و تنظیمات مدیریت‌شده خوانده می‌شود**: بلوک `spellcheck` در `.claude/settings.json` پروژه یا `.claude/settings.local.json` نادیده گرفته می‌شود. |
| `bashOutputMaxChars` | (v2.1.261) چند کاراکتر از خروجی یک دستور **موفق** Bash یا PowerShell به‌صورت درون‌خطی به Claude می‌رسد، حداکثر تا 128K. بیش از این حد، Claude Code خروجی را در فایلی ذخیره می‌کند و Claude یک پیش‌نمایش کوتاه به‌همراه مسیر دریافت می‌کند. تنظیم آن باعث می‌شود Claude Code مقدار `BASH_MAX_OUTPUT_LENGTH` را نادیده بگیرد. |
| `taskOutputMaxChars` | (v2.1.261) **در v2.1.278 جایگزین شده و هیچ اثری ندارد.** پیش‌تر سقف تعداد کاراکترهای خروجی یک **تسک پس‌زمینه** را تعیین می‌کرد که Claude هنگام خواندن با ابزار `TaskOutput` به‌صورت درون‌خطی دریافت می‌کرد. نسخه v2.1.278 ابزار `TaskOutput` را حذف کرد — Claude اکنون فایل خروجی یک تسک پس‌زمینه را با `Read` می‌خواند — بنابراین این کلید و `TASK_MAX_OUTPUT_LENGTH` هر دو بی‌اثرند. Claude Code هنوز کلید را می‌پذیرد، بنابراین فایل تنظیماتی که آن را تنظیم کند معتبر می‌ماند. |
| `maxEffortLevel` | (v2.1.267) سقف سطح تلاشی را که Claude Code می‌تواند استفاده کند تعیین می‌کند، روی هر ارائه‌دهنده از جمله Bedrock، Vertex و Foundry. آن را در سطح بالا یا به‌ازای هر مدل زیر `modelSettings` تنظیم کنید. کاربران همچنان می‌توانند سطح پایین‌تری انتخاب کنند. |
| `bashEditDiffEnabled` | (v2.1.269) نتایج ابزار Bash شامل تفاوت (diff) فایل‌هایی است که دستور تغییر داده است. |
| `syncClaudeAiSkills` / `syncClaudeAiPlugins` | (v2.1.275) هر یک را `false` کنید تا از همگام‌سازی مهارت‌ها یا پلاگین‌هایی که در حساب claude.ai خود فعال کرده‌اید با نشست‌های ترمینال انصراف دهید. |

### مدل‌های جایگزین (`fallbackModel`)

تنظیم `fallbackModel` به شما امکان می‌دهد **حداکثر سه** مدل جایگزین را پیکربندی کنید که وقتی مدل اصلی بارگذاری‌شده یا در دسترس نیست، به ترتیب امتحان می‌شوند.

```json
{
  "fallbackModel": ["claude-opus-4-8", "claude-sonnet-4-6", "claude-haiku-4-5"]
}
```

از **v2.1.166** پرچم `--fallback-model` روی نشست‌های تعاملی هم اعمال می‌شود (نه فقط حالت headless). در حالت جایگزین، Claude Code یک خطای غیرمنتظره غیرقابل‌تلاش را یک بار دوباره امتحان می‌کند؛ خطاهای احراز هویت، محدودیت نرخ، اندازه درخواست و انتقال همچنان فوراً شکست می‌خورند.

### متغیرهای محیطی

پیکربندی را با متغیرهای محیطی بازنویسی کنید:

```bash
# انتخاب مدل
export ANTHROPIC_MODEL=claude-opus-4-8
export ANTHROPIC_DEFAULT_MODEL=claude-opus-4-8   # (v2.1.236) مدلی که نشست‌های جدید با آن شروع می‌شوند. برخلاف ANTHROPIC_MODEL، انتخاب /model همچنان آن را بازنویسی می‌کند — و آن انتخاب در راه‌اندازی‌های مجدد باقی می‌ماند
export ANTHROPIC_DEFAULT_OPUS_MODEL=claude-opus-4-8
export ANTHROPIC_DEFAULT_SONNET_MODEL=claude-sonnet-4-6
export ANTHROPIC_DEFAULT_HAIKU_MODEL=claude-haiku-4-5

# پیکربندی API
export ANTHROPIC_API_KEY=sk-ant-...

# پیکربندی تفکر
export MAX_THINKING_TOKENS=16000
export CLAUDE_CODE_EFFORT_LEVEL=high   # low، medium، high، xhigh (روی Opus 5.5، Sonnet 5.5، Haiku 5.5، Opus 5، Sonnet 5، Opus 4.8/4.7) یا max — پیش‌فرض روی Opus 5 و Opus 4.8 برابر high است (پشتیبانی‌شده روی Opus 5.5، Sonnet 5.5، Haiku 5.5، Opus 5، Sonnet 5، Opus 4.8، Opus 4.7، Opus 4.6، Sonnet 4.6)

# کلیدهای فعال‌سازی قابلیت‌ها
export CLAUDE_CODE_DISABLE_AUTO_MEMORY=1    # غیرفعال کردن حافظه خودکار (هیچ فایل حافظه خودکاری ساخته یا بارگذاری نمی‌شود)
export CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=true
export CLAUDE_CODE_DISABLE_CRON=1
export CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=true
export CLAUDE_CODE_DISABLE_TERMINAL_TITLE=true
export CLAUDE_CODE_DISABLE_1M_CONTEXT=true
export CLAUDE_CODE_DISABLE_NONSTREAMING_FALLBACK=true
export CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=false
export CLAUDE_CODE_ENABLE_TASKS=0          # ابزارهای تسک پیش‌فرض هستند؛ مقدار 0 به ابزار قدیمی TodoWrite بازمی‌گردد
export CLAUDE_CODE_SIMPLE=true              # با پرچم --bare تنظیم می‌شود

# پیکربندی MCP
export MAX_MCP_OUTPUT_TOKENS=50000
export ENABLE_TOOL_SEARCH=true

# کش پرامپت
export ENABLE_PROMPT_CACHING_1H=1      # درخواست TTL یک‌ساعته کش برای همه درخواست‌ها (پیش‌فرض: ۱ ساعت برای گفت‌وگوی اصلی روی اشتراک، ۵ دقیقه روی کلید API یا ارائه‌دهندگان ابری)

# مدیریت تسک
export CLAUDE_CODE_TASK_LIST_ID=my-project-tasks

# تیم‌های ایجنت (آزمایشی)
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1

# پیکربندی زیرایجنت و پلاگین
export CLAUDE_CODE_SUBAGENT_MODEL=sonnet
export CLAUDE_CODE_PLUGIN_SEED_DIR=./my-plugins
export CLAUDE_CODE_NEW_INIT=1

# زیرفرایند و استریم
export CLAUDE_CODE_SUBPROCESS_ENV_SCRUB="SECRET_KEY,DB_PASSWORD"
export CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=80
export CLAUDE_STREAM_IDLE_TIMEOUT_MS=30000
export ANTHROPIC_CUSTOM_MODEL_OPTION=my-custom-model
export SLASH_COMMAND_TOOL_CHAR_BUDGET=50000

# خروجی و مدیر بسته (v2.1.129+)
export CLAUDE_CODE_FORCE_SYNC_OUTPUT=1                      # اجبار خروجی همگام برای ترمینال‌هایی که تشخیص خودکار را از دست می‌دهد (Emacs eat و مانند آن)
export CLAUDE_CODE_PACKAGE_MANAGER_AUTO_UPDATE=1            # فعال کردن ارتقای پس‌زمینه برای نصب‌های Homebrew/WinGet
export CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1         # انصراف از کشف مدل‌های درگاه /v1/models وقتی ANTHROPIC_BASE_URL تنظیم شده است

# فدراسیون هویت بار کاری (v2.1.141+)

# سقف ایمنی هوک Stop (v2.1.143+)
export CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=8                    # حداکثر مسدودسازی‌های متوالی هوک Stop پیش از پایان نشست با یک هشدار. برای حذف سقف، 0 بگذارید.

# سقف‌های ایجاد در سطح نشست (v2.1.212)
```

### دستورهای مدیریت پیکربندی

```
کاربر: /config
[منوی پیکربندی تعاملی باز می‌شود]
```

دستور `/config` یک منوی تعاملی برای روشن یا خاموش کردن تنظیماتی مانند موارد زیر فراهم می‌کند:
- تفکر گسترده روشن/خاموش
- خروجی پرجزئیات
- حالت مجوز
- انتخاب مدل
- اندازه جریان کاری پویا (v2.1.219) — وقتی `workflowSizeGuideline` در فایل تنظیمات تنظیم شده باشد پنهان می‌شود، [جریان‌های کاری پویا](#گردش‌کارهای-پویا) را ببینید
- فشرده‌سازی در حالت بی‌کار (v2.1.302)

در منوی تعاملی، برای تغییر تنظیم انتخاب‌شده Enter یا Space را فشار دهید و برای ذخیره و بستن Esc را بزنید (v2.1.183+).

همچنین می‌توانید تنظیمی را مستقیماً از پرامپت و بدون باز کردن منو تعیین کنید:

```bash
/config thinking=false      # تنظیم یک تنظیم به‌صورت درون‌خطی (v2.1.181+)
/config --help              # فهرست کلیدهای مختصر موجود (v2.1.183+)
```

مختصرنویسی `key=value` در نشست‌های تعاملی، با `-p` و در Remote Control کار می‌کند.

### پیکربندی به‌ازای هر پروژه

فایل `.claude/settings.json` را در پروژه خود ایجاد کنید:

```json
{
  "hooks": {
    "PreToolUse": [{ "matcher": "Bash", "hooks": [{ "type": "command", "command": "npm test && npm run lint" }] }]
  },
  "permissions": {
    "defaultMode": "manual"
  }
}
```

سرورهای MCP پروژه را در `.mcp.json` در ریشه پروژه قرار دهید:

```json
{
  "mcpServers": {
    "project-db": {
      "command": "mcp-postgres",
      "env": {
        "DATABASE_URL": "${PROJECT_DB_URL}"
      }
    }
  }
}
```

برای `PROJECT_DB_URL` از یک کاربر فقط-خواندنی پایگاه‌داده استفاده کنید؛ پیکربندی فقط-خواندنی را در [MCP → نمونهٔ پایگاه‌داده](../05-mcp/README.md) ببینید.

## دامنه اعتماد و مجوزها

> **برگرفته از تغییرنگار (v2.1.222، v2.1.232)**: این سخت‌گیری‌ها از تغییرنگار می‌آیند؛
> مرجع تنظیمات هنوز آن‌ها را به‌روشنی بیان نکرده است.

یک مضمون تکرارشونده در نسخه‌های اخیر: تنظیمات مرتبط با امنیت دیگر نمی‌توانند
توسط مخزنی که کلون کرده‌اید گسترده‌تر شوند. سه تغییر که باید بدانید.

**مخزن‌های تودرتو به تأیید اعتماد جداگانه خود نیاز دارند (v2.1.232).** یک مخزن گیت
داخل یک پوشه والد مورد اعتماد دیگر آن اعتماد را به ارث نمی‌برد. اگر به
`~/work/monorepo` اعتماد کنید و آن یک زیرماژول فروشنده‌شده داشته باشد،
نخستین بار که Claude Code داخل آن کار کند از شما خواسته می‌شود جداگانه به زیرماژول اعتماد کنید.

**`sandbox.ripgrep` فقط در دامنه کاربر است (v2.1.232).** تنظیمی که باینری ripgrep
مورد استفاده سندباکس را مشخص می‌کند، فقط از تنظیمات کاربر، تنظیمات مدیریت‌شده یا
`--settings` پذیرفته می‌شود. تنظیمات پروژه دیگر نمی‌توانند سندباکس را به باینری دیگری اشاره دهند.

**شروع خودکار Remote Control فقط در دامنه کاربر است (v2.1.222).** تنظیمات محلی مخزن نمی‌توانند
شروع خودکار Remote Control را فعال کنند؛ این فقط در دامنه کاربر و از طریق `/config` روشن می‌شود.

الگویی که باید درونی کنید: اگر تنظیمی به یک فایل ثبت‌شده در مخزن اجازه دهد دامنه کارهای مجاز
Claude Code روی ماشین شما را گسترش دهد، فرض کنید که اکنون فقط در دامنه کاربر است.

## تیم‌های ایجنت

تیم‌های ایجنت یک قابلیت آزمایشی است که به چند نمونه Claude Code امکان می‌دهد روی یک تسک همکاری کنند. به‌طور پیش‌فرض غیرفعال است.

### فعال‌سازی تیم‌های ایجنت

فعال‌سازی از طریق متغیر محیطی یا تنظیمات:

```bash
# متغیر محیطی
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

یا به JSON تنظیمات خود اضافه کنید:

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

### تیم‌های ایجنت چگونه کار می‌کنند

- یک **سرگروه** تسک کلی را هماهنگ می‌کند و زیرتسک‌ها را به هم‌تیمی‌ها می‌سپارد
- **هم‌تیمی‌ها** مستقل کار می‌کنند، هر یک با پنجره زمینه خودش
- یک **فهرست تسک مشترک** هماهنگی خودکار میان اعضای تیم را ممکن می‌کند
- از تعریف‌های زیرایجنت (`.claude/agents/` یا پرچم `--agents`) برای تعیین نقش‌ها و تخصص‌های هم‌تیمی استفاده کنید

### حالت‌های نمایش

تیم‌های ایجنت دو حالت نمایش را پشتیبانی می‌کنند که با پرچم `--teammate-mode` پیکربندی می‌شوند:

| حالت | توضیح |
|------|-------------|
| `in-process` (پیش‌فرض) | هم‌تیمی‌ها در همان فرایند ترمینال اجرا می‌شوند |
| `tmux` | هر هم‌تیمی یک پنجره تقسیم‌شده اختصاصی می‌گیرد (نیازمند tmux یا iTerm2) |
| `auto` | بهترین حالت نمایش را به‌طور خودکار انتخاب می‌کند |

```bash
# استفاده از پنجره‌های تقسیم‌شده tmux برای نمایش هم‌تیمی‌ها
claude --teammate-mode tmux

# استفاده صریح از حالت in-process
claude --teammate-mode in-process
```

### موارد استفاده

- کارهای ری‌فاکتور بزرگ که در آن‌ها هم‌تیمی‌های مختلف ماژول‌های مختلف را بر عهده می‌گیرند
- بازبینی و پیاده‌سازی موازی کد
- تغییرات هماهنگ چندفایلی در یک کدبیس

> **توجه**: تیم‌های ایجنت آزمایشی است و ممکن است در نسخه‌های آینده تغییر کند. برای مرجع کامل [code.claude.com/docs/en/agent-teams](https://code.claude.com/docs/en/agent-teams) را ببینید.

## بهترین شیوه‌ها

### حالت برنامه‌ریزی
- ✅ برای تسک‌های پیچیده چندمرحله‌ای استفاده کنید
- ✅ پیش از تأیید، برنامه‌ها را بازبینی کنید
- ✅ برنامه‌ها را در صورت نیاز تغییر دهید
- ❌ برای تسک‌های ساده استفاده نکنید

### تفکر گسترده
- ✅ برای تصمیم‌های معماری استفاده کنید
- ✅ برای حل مسائل پیچیده استفاده کنید
- ✅ فرایند تفکر را بازبینی کنید
- ❌ برای پرس‌وجوهای ساده استفاده نکنید

### وظایف پس‌زمینه
- ✅ برای عملیات طولانی‌مدت استفاده کنید
- ✅ پیشرفت کار را پایش کنید
- ✅ خطاهای وظیفه را به‌شکل مناسب مدیریت کنید
- ❌ وظایف هم‌زمان بیش از حد را شروع نکنید

### مجوزها
- ✅ از `plan` برای بازبینی کد (فقط‌خواندنی) استفاده کنید
- ✅ از `default` برای توسعه تعاملی استفاده کنید
- ✅ از `acceptEdits` برای جریان‌های کاری خودکارسازی استفاده کنید
- ✅ از `auto` برای کار خودمختار با حفاظ‌های ایمنی استفاده کنید
- ❌ از `bypassPermissions` استفاده نکنید مگر آن‌که کاملاً ضروری باشد

### نشست‌ها
- ✅ برای وظایف مختلف از نشست‌های جداگانه استفاده کنید
- ✅ وضعیت‌های مهم نشست را ذخیره کنید
- ✅ نشست‌های قدیمی را پاک‌سازی کنید
- ❌ کارهای نامرتبط را در یک نشست مخلوط نکنید
