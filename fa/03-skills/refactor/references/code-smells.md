# کاتالوگ بوی کد

مرجعی جامع از بوی کدها بر اساس کتاب *Refactoring* (ویرایش دوم) مارتین فاولر. بوی کد نشانه‌های مشکلات عمیق‌تر است — نشان می‌دهد ممکن است چیزی در طراحی کد شما اشتباه باشد.

> «بوی کد یک نشانه سطحی است که معمولاً به مشکلی عمیق‌تر در سیستم اشاره می‌کند.» — مارتین فاولر

---

## متورم‌ها (Bloaters)

بوی کدهایی که نشان می‌دهند چیزی آن‌قدر بزرگ شده که دیگر به‌طور مؤثر قابل مدیریت نیست.

### متد طولانی

**نشانه‌ها:**
- متد بیش از ۳۰ تا ۵۰ خط
- برای دیدن کل متد باید اسکرول کنید
- چند سطح تودرتویی
- توضیحاتی که می‌گویند هر بخش چه کار می‌کند

**چرا بد است:**
- درک آن دشوار است
- تست جداگانه آن مشکل است
- تغییرات پیامدهای ناخواسته دارند
- منطق تکراری درون آن پنهان می‌شود

**ری‌فاکتورها:**
- استخراج متد (Extract Method)
- جایگزینی متغیر موقت با پرس‌وجو (Replace Temp with Query)
- معرفی شیء پارامتر (Introduce Parameter Object)
- جایگزینی متد با شیء متد (Replace Method with Method Object)
- تجزیه شرطی (Decompose Conditional)

**مثال (قبل):**
```javascript
function processOrder(order) {
  // اعتبارسنجی سفارش (۲۰ خط)
  if (!order.items) throw new Error('No items');
  if (order.items.length === 0) throw new Error('Empty order');
  // ... اعتبارسنجی بیشتر

  // محاسبه جمع‌ها (۳۰ خط)
  let subtotal = 0;
  for (const item of order.items) {
    subtotal += item.price * item.quantity;
  }
  // ... مالیات، حمل‌ونقل، تخفیف‌ها

  // ارسال اعلان‌ها (۲۰ خط)
  // ... منطق ایمیل
}
```

**مثال (بعد):**
```javascript
function processOrder(order) {
  validateOrder(order);
  const totals = calculateOrderTotals(order);
  sendOrderNotifications(order, totals);
  return { order, totals };
}
```

### کلاس بزرگ

**نشانه‌ها:**
- کلاس متغیرهای نمونه زیادی دارد (بیش از ۷ تا ۱۰)
- کلاس متدهای زیادی دارد (بیش از ۱۵ تا ۲۰)
- نام کلاس مبهم است (Manager، Handler، Processor)
- متدها از همه متغیرهای نمونه استفاده نمی‌کنند

**چرا بد است:**
- اصل مسئولیت واحد را نقض می‌کند
- تست آن دشوار است
- تغییرات به قابلیت‌های نامرتبط سرریز می‌شود
- استفاده مجدد از بخش‌ها دشوار است

**ری‌فاکتورها:**
- استخراج کلاس (Extract Class)
- استخراج زیرکلاس (Extract Subclass)
- استخراج رابط (Extract Interface)

**تشخیص:**
```
Lines of code > 300
Number of methods > 15
Number of fields > 10
```

### وسواس به انواع ابتدایی

**نشانه‌ها:**
- استفاده از انواع ابتدایی برای مفاهیم دامنه (رشته برای ایمیل، عدد صحیح برای پول)
- آرایه‌ای از انواع ابتدایی به‌جای اشیاء
- ثابت‌های رشته‌ای برای کدهای نوع
- اعداد/رشته‌های جادویی

**چرا بد است:**
- بدون اعتبارسنجی در سطح نوع
- منطق در سراسر کدبیس پراکنده است
- به‌راحتی مقادیر اشتباه منتقل می‌شوند
- مفاهیم دامنه مفقودند

**ری‌فاکتورها:**
- جایگزینی نوع ابتدایی با شیء (Replace Primitive with Object)
- جایگزینی کد نوع با کلاس (Replace Type Code with Class)
- جایگزینی کد نوع با زیرکلاس‌ها (Replace Type Code with Subclasses)
- جایگزینی کد نوع با State/Strategy

**مثال (قبل):**
```javascript
const user = {
  email: 'john@example.com',     // فقط یک رشته
  phone: '1234567890',           // فقط یک رشته
  status: 'active',              // رشته جادویی
  balance: 10050                 // سنت به‌صورت عدد صحیح
};
```

**مثال (بعد):**
```javascript
const user = {
  email: new Email('john@example.com'),
  phone: new PhoneNumber('1234567890'),
  status: UserStatus.ACTIVE,
  balance: Money.cents(10050)
};
```

### فهرست پارامتر طولانی

**نشانه‌ها:**
- متدهایی با ۴ پارامتر یا بیشتر
- پارامترهایی که همیشه با هم ظاهر می‌شوند
- پرچم‌های بولی که رفتار متد را تغییر می‌دهند
- null/undefined که مکرراً منتقل می‌شود

**چرا بد است:**
- فراخوانی صحیح دشوار است
- سردرگمی در ترتیب پارامترها
- نشان می‌دهد متد کارهای زیادی انجام می‌دهد
- افزودن پارامتر جدید دشوار است

**ری‌فاکتورها:**
- معرفی شیء پارامتر (Introduce Parameter Object)
- حفظ شیء کامل (Preserve Whole Object)
- جایگزینی پارامتر با فراخوانی متد (Replace Parameter with Method Call)
- حذف آرگومان پرچم (Remove Flag Argument)

**مثال (قبل):**
```javascript
function createUser(firstName, lastName, email, phone,
                    street, city, state, zip,
                    isAdmin, isActive, createdBy) {
  // ...
}
```

**مثال (بعد):**
```javascript
function createUser(personalInfo, address, options) {
  // personalInfo: { firstName, lastName, email, phone }
  // address: { street, city, state, zip }
  // options: { isAdmin, isActive, createdBy }
}
```

### خوشه‌های داده (Data Clumps)

**نشانه‌ها:**
- همان ۳ فیلد یا بیشتر مکرراً با هم ظاهر می‌شوند
- پارامترهایی که همیشه با هم سفر می‌کنند
- کلاس‌هایی با زیرمجموعه فیلدهایی که به هم تعلق دارند

**چرا بد است:**
- منطق مدیریت تکراری
- انتزاع مفقود
- گسترش دشوارتر
- نشان‌دهنده کلاس پنهان

**ری‌فاکتورها:**
- استخراج کلاس (Extract Class)
- معرفی شیء پارامتر (Introduce Parameter Object)
- حفظ شیء کامل (Preserve Whole Object)

**مثال:**
```javascript
// خوشه داده: مختصات (x, y, z)
function movePoint(x, y, z, dx, dy, dz) { }
function scalePoint(x, y, z, factor) { }
function distanceBetween(x1, y1, z1, x2, y2, z2) { }

// استخراج کلاس Point3D
class Point3D {
  constructor(x, y, z) { }
  move(delta) { }
  scale(factor) { }
  distanceTo(other) { }
}
```

## سوءاستفاده‌کنندگان از شیءگرایی

بوی کدهایی که نشان‌دهنده استفاده ناقص یا نادرست از اصول شیءگرایی هستند.

### دستورات switch

**نشانه‌ها:**
- زنجیره‌های طولانی switch/case یا if/else
- همان switch در چند جا
- switch روی کدهای نوع
- افزودن حالت جدید نیازمند تغییر در همه جا است

**چرا بد است:**
- اصل باز/بسته را نقض می‌کند
- تغییرات به همه محل‌های switch سرریز می‌کند
- گسترش دشوار است
- اغلب نشان‌دهنده چندریختی مفقود است

**ری‌فاکتورها:**
- جایگزینی شرطی با چندریختی (Replace Conditional with Polymorphism)
- جایگزینی کد نوع با زیرکلاس‌ها
- جایگزینی کد نوع با State/Strategy

**مثال (قبل):**
```javascript
function calculatePay(employee) {
  switch (employee.type) {
    case 'hourly':
      return employee.hours * employee.rate;
    case 'salaried':
      return employee.salary / 12;
    case 'commissioned':
      return employee.sales * employee.commission;
  }
}
```

**مثال (بعد):**
```javascript
class HourlyEmployee {
  calculatePay() {
    return this.hours * this.rate;
  }
}

class SalariedEmployee {
  calculatePay() {
    return this.salary / 12;
  }
}
```

### فیلد موقت

**نشانه‌ها:**
- متغیرهای نمونه که فقط در برخی متدها استفاده می‌شوند
- فیلدهایی که به‌صورت شرطی مقدار می‌گیرند
- مقداردهی اولیه پیچیده برای موارد خاص

**چرا بد است:**
- گیج‌کننده — فیلد وجود دارد اما ممکن است null باشد
- درک وضعیت شیء دشوار است
- نشان‌دهنده منطق شرطی پنهان است

**ری‌فاکتورها:**
- استخراج کلاس (Extract Class)
- معرفی شیء null (Introduce Null Object)
- جایگزینی فیلد موقت با متغیر محلی

---

### ارث‌بری ردشده (Refused Bequest)

**نشانه‌ها:**
- زیرکلاس از متدها/داده‌های ارث‌برده استفاده نمی‌کند
- زیرکلاس بازنویسی می‌کند تا هیچ کاری انجام ندهد
- ارث‌بری برای استفاده مجدد از کد به کار می‌رود، نه رابطه IS-A

**چرا بد است:**
- انتزاع اشتباه
- اصل جانشینی لیسکوف را نقض می‌کند
- سلسله‌مراتب گمراه‌کننده

**ری‌فاکتورها:**
- هل دادن متد/فیلد به پایین (Push Down Method/Field)
- جایگزینی زیرکلاس با واگذاری (Replace Subclass with Delegate)
- جایگزینی ارث‌بری با واگذاری (Replace Inheritance with Delegation)

---

### کلاس‌های جایگزین با رابط‌های متفاوت

**نشانه‌ها:**
- دو کلاس که کارهای مشابه انجام می‌دهند
- نام متدهای متفاوت برای مفهوم یکسان
- می‌توانند به‌جای هم استفاده شوند

**چرا بد است:**
- پیاده‌سازی‌های تکراری
- بدون رابط مشترک
- جابه‌جایی بین آن‌ها دشوار است

**ری‌فاکتورها:**
- تغییر نام متد (Rename Method)
- انتقال متد (Move Method)
- استخراج ابرکلاس (Extract Superclass)
- استخراج رابط (Extract Interface)

## بازدارنده‌های تغییر

بوی کدهایی که تغییر را دشوار می‌کنند — تغییر یک چیز نیازمند تغییر بسیاری چیزهای دیگر است.

### تغییر واگرا (Divergent Change)

**نشانه‌ها:**
- یک کلاس به دلایل مختلف تغییر می‌کند
- تغییرات در حوزه‌های مختلف ویرایش همان کلاس را برمی‌انگیزند
- کلاس یک «کلاس خدا» است

**چرا بد است:**
- اصل مسئولیت واحد را نقض می‌کند
- فراوانی تغییر بالا
- تعارض‌های ادغام

**ری‌فاکتورها:**
- استخراج کلاس (Extract Class)
- استخراج ابرکلاس (Extract Superclass)
- استخراج زیرکلاس (Extract Subclass)

**مثال:**
یک کلاس `User` به این دلایل تغییر می‌کند:
- تغییرات احراز هویت
- تغییرات پروفایل
- تغییرات صورت‌حساب
- تغییرات اعلان

→ استخراج: `AuthService`، `ProfileService`، `BillingService`، `NotificationService`

---

### جراحی با شاتگان (Shotgun Surgery)

**نشانه‌ها:**
- یک تغییر نیازمند ویرایش در بسیاری کلاس است
- یک قابلیت کوچک نیاز به دست زدن به بیش از ۱۰ فایل دارد
- تغییرات پراکنده‌اند و یافتن همه آن‌ها دشوار است

**چرا بد است:**
- به‌راحتی جایی از قلم می‌افتد
- وابستگی بالا
- تغییرات مستعد خطا هستند

**ری‌فاکتورها:**
- انتقال متد (Move Method)
- انتقال فیلد (Move Field)
- درون‌خطی کردن کلاس (Inline Class)

**تشخیص:**
به این نگاه کنید: افزودن یک فیلد نیازمند تغییر در بیش از ۵ فایل است.

---

### سلسله‌مراتب ارث‌بری موازی

**نشانه‌ها:**
- ساخت زیرکلاس در یک سلسله‌مراتب نیازمند زیرکلاس در دیگری است
- پیشوندهای کلاس مطابقت دارند (مثلاً `DatabaseOrder`، `DatabaseProduct`)

**چرا بد است:**
- نگهداری دوبرابر
- وابستگی بین سلسله‌مراتب‌ها
- فراموش کردن یک طرف آسان است

**ری‌فاکتورها:**
- انتقال متد (Move Method)
- انتقال فیلد (Move Field)
- حذف یک سلسله‌مراتب

## دورریزها (Dispensables)

چیزی غیرضروری که باید حذف شود.

### توضیحات (بیش از حد)

**نشانه‌ها:**
- توضیحاتی که می‌گویند کد چه کار می‌کند
- کد کامنت‌شده
- TODO/FIXME که تا ابد باقی می‌مانند
- عذرخواهی در توضیحات

**چرا بد است:**
- توضیحات دروغ می‌گویند (از همگامی خارج می‌شوند)
- کد باید خودمستند باشد
- کد مرده سردرگمی ایجاد می‌کند

**ری‌فاکتورها:**
- استخراج متد (نام توضیح می‌دهد چه کار می‌کند)
- تغییر نام (شفافیت بدون توضیح)
- حذف کد کامنت‌شده
- معرفی assertion (Introduce Assertion)

**توضیح خوب در برابر بد:**
```javascript
// بد: توضیح «چیستی»
// روی کاربران حلقه بزن و بررسی کن فعال هستند
for (const user of users) {
  if (user.status === 'active') { }
}

// خوب: توضیح «چرایی»
// فقط کاربران فعال - غیرفعال‌ها توسط کار پاک‌سازی مدیریت می‌شوند
const activeUsers = users.filter(u => u.isActive);
```

### کد تکراری

**نشانه‌ها:**
- همان کد در چند جا
- کد مشابه با تغییرات کوچک
- الگوهای کپی-چسباندن

**چرا بد است:**
- رفع باگ در چند جا لازم است
- ریسک ناسازگاری
- کدبیس متورم

**ری‌فاکتورها:**
- استخراج متد (Extract Method)
- استخراج کلاس (Extract Class)
- کشیدن متد به بالا (Pull Up Method، در سلسله‌مراتب‌ها)
- شکل‌دهی متد قالب (Form Template Method)

**قاعده تشخیص:**
هر کدی که ۳ بار یا بیشتر تکرار شده باید استخراج شود.

### کلاس تنبل

**نشانه‌ها:**
- کلاس به‌اندازه‌ای که وجودش را توجیه کند کار نمی‌کند
- پوششی بدون ارزش افزوده
- نتیجه مهندسی بیش از حد

**چرا بد است:**
- سربار نگهداری
- غیرمستقیم‌سازی غیرضروری
- پیچیدگی بدون سود

**ری‌فاکتورها:**
- درون‌خطی کردن کلاس (Inline Class)
- فروپاشی سلسله‌مراتب (Collapse Hierarchy)

---

### کد مرده

**نشانه‌ها:**
- کد دسترسی‌ناپذیر
- متغیرها/متدها/کلاس‌های استفاده‌نشده
- کد کامنت‌شده
- کد پشت شرط‌های غیرممکن

**چرا بد است:**
- سردرگمی
- بار نگهداری
- درک را کند می‌کند

**ری‌فاکتورها:**
- حذف کد مرده (Remove Dead Code)
- حذف ایمن (Safe Delete)

**تشخیص:**
```bash
# به دنبال خروجی‌های استفاده‌نشده بگردید
# به دنبال توابع ارجاع‌نشده بگردید
# هشدارهای «unused» در IDE
```

---

### کلیت حدسی (Speculative Generality)

**نشانه‌ها:**
- کلاس‌های انتزاعی با یک زیرکلاس
- پارامترهای استفاده‌نشده «برای استفاده آینده»
- متدهایی که فقط واگذار می‌کنند
- «چارچوب» برای یک مورد استفاده

**چرا بد است:**
- پیچیدگی بدون سود
- YAGNI (به آن نیازی نخواهید داشت)
- درک آن دشوارتر است

**ری‌فاکتورها:**
- فروپاشی سلسله‌مراتب (Collapse Hierarchy)
- درون‌خطی کردن کلاس (Inline Class)
- حذف پارامتر (Remove Parameter)
- تغییر نام متد (Rename Method)

## جفت‌کننده‌ها (Couplers)

بوی کدهایی که وابستگی بیش از حد بین کلاس‌ها را نشان می‌دهند.

### حسادت به ویژگی (Feature Envy)

**نشانه‌ها:**
- متد بیشتر از داده‌های کلاس دیگر استفاده می‌کند تا داده‌های خودش
- فراخوانی‌های زیاد getter روی شیء دیگر
- داده و رفتار از هم جدا شده‌اند

**چرا بد است:**
- مکان اشتباه برای رفتار
- کپسوله‌سازی ضعیف
- نگهداری دشوار

**ری‌فاکتورها:**
- انتقال متد (Move Method)
- انتقال فیلد (Move Field)
- استخراج متد (سپس انتقال)

**مثال (قبل):**
```javascript
class Order {
  getDiscountedPrice(customer) {
    // به‌شدت از داده‌های مشتری استفاده می‌کند
    if (customer.loyaltyYears > 5) {
      return this.price * customer.discountRate;
    }
    return this.price;
  }
}
```

**مثال (بعد):**
```javascript
class Customer {
  getDiscountedPriceFor(price) {
    if (this.loyaltyYears > 5) {
      return price * this.discountRate;
    }
    return price;
  }
}
```

### صمیمیت نامناسب

**نشانه‌ها:**
- کلاس‌ها به بخش‌های خصوصی یکدیگر دسترسی دارند
- ارجاع‌های دوسویه
- زیرکلاس‌ها درباره والدها بیش از حد می‌دانند

**چرا بد است:**
- وابستگی بالا
- تغییرات آبشاری
- تغییر یکی بدون دیگری دشوار است

**ری‌فاکتورها:**
- انتقال متد (Move Method)
- انتقال فیلد (Move Field)
- تبدیل دوسویه به یک‌سویه
- استخراج کلاس (Extract Class)
- پنهان‌سازی واگذار (Hide Delegate)

### زنجیره‌های پیام

**نشانه‌ها:**
- زنجیره‌های طولانی فراخوانی متد: `a.getB().getC().getD().getValue()`
- کلاینت به ساختار پیمایش وابسته است
- کد «تصادف قطار»

**چرا بد است:**
- شکننده — هر تغییری زنجیره را می‌شکند
- قانون دیمیتر را نقض می‌کند
- وابستگی به ساختار

**ری‌فاکتورها:**
- پنهان‌سازی واگذار (Hide Delegate)
- استخراج متد (Extract Method)
- انتقال متد (Move Method)

**مثال:**
```javascript
// بد: زنجیره پیام
const managerName = employee.getDepartment().getManager().getName();

// بهتر: پنهان‌سازی واگذاری
const managerName = employee.getManagerName();
```

### واسطه (Middle Man)

**نشانه‌ها:**
- کلاسی که فقط به دیگری واگذار می‌کند
- نیمی از متدها واگذاری هستند
- بدون ارزش افزوده

**چرا بد است:**
- غیرمستقیم‌سازی غیرضروری
- سربار نگهداری
- معماری گیج‌کننده

**ری‌فاکتورها:**
- حذف واسطه (Remove Middle Man)
- درون‌خطی کردن متد (Inline Method)

## راهنمای شدت بوی کد

| شدت | توضیح | اقدام |
|----------|-------------|--------|
| **حیاتی** | توسعه را مسدود می‌کند، باگ ایجاد می‌کند | فوراً رفع کنید |
| **بالا** | سربار نگهداری قابل توجه | در اسپرینت فعلی رفع کنید |
| **متوسط** | قابل توجه اما قابل مدیریت | برای آینده نزدیک برنامه‌ریزی کنید |
| **پایین** | ناراحتی جزئی | فرصت‌طلبانه رفع کنید |
